## ADDED Requirements

### Requirement: 評価のやり直し
issueの評価がエラー、キュー待ち、ロック中のどれかで終わったとき、エージェントは、そのissueを後のポーリングで評価し直さなければならない（MUST）。
同じプロジェクトの別のissueを評価できても、評価の終わっていないissueは、評価し直す対象から外れない。

#### Scenario: キューの消化で一時的に失敗した
- **WHEN** `max_parallel: 1` の端末で、1つ目の実行の間に2つ目のissueに `agent:ready` が付き、同じプロジェクトの別のissueも更新される。1つ目が終わって2つ目を取り出すとき、フォージへの要求が1回失敗する
- **THEN** 次のポーリングで2つ目のissueが評価し直され、`agent:running` になる

#### Scenario: ポーリングで一時的に失敗した
- **WHEN** 1回のポーリングで、issue 3の評価がフォージの502で失敗し、issue 3より1分以上後に更新されたissue 4の評価は成功する
- **THEN** 次のポーリングでissue 3が評価し直される

### Requirement: 評価のやり直しの打ち切り
評価し直すissueがフォージに見つからないとき、エージェントは、そのissueの評価のやり直しをやめなければならない（MUST）。

#### Scenario: 削除されたissue
- **WHEN** 評価し直すissueが削除され、フォージが「見つからない」と答える
- **THEN** エージェントはそのissueを評価し直さなくなり、ほかのissueのポーリングは続く

### Requirement: やり直しの間隔
書き戻しの再試行か、エラーまたはロック中で評価できなかったissueがある間、エージェントは、`poll_interval` ごとにそれらをやり直さなければならない（MUST）。
中継につながっていて、全プロジェクトが `relay.hooks` に載っているときも同じとする。キュー待ちのissueは、ここでいうやり直しの対象に含めない。

#### Scenario: 中継につながっているときの評価の失敗
- **WHEN** `poll_interval: 60s`、`reconcile_interval: 10m` で中継につながり、全プロジェクトが `relay.hooks` に載っている。あるissueの評価がフォージの502で失敗する
- **THEN** 約60秒後のポーリングで、そのissueが評価し直される

### Requirement: 着手の途中の評価
着手のコメントの投稿からラベルの付け替えまでの間、エージェントは、ラベルがまだ `agent:running` でないことを理由に、そのissueの実行を取り消してはならない（MUST NOT）。

#### Scenario: 着手の途中にポーリングが当たる
- **WHEN** 実行が待ちで終わったときに返答が届いていて、次の実行の着手の途中に、ポーリングがそのissueを評価する
- **THEN** 次の実行は取り消されずに始まり、issueは `agent:running` になる

### Requirement: 着手の付け替えの失敗
着手のコメントを投稿したあとで `agent:running` への付け替えが失敗したとき、エージェントは、次のポーリングでissueを読み直さなければならない（MUST）。
読み直したラベルが `agent:running` なら、エージェントは、その実行を中断として待ちにする。待ちの理由は `error` とする。読み直したラベルが始めるラベルのままなら、エージェントは着手をやり直す。

#### Scenario: 付け替えが反映されていた
- **WHEN** 着手のときの付け替えで、ラベルの変更は成功し、その後の取り直しが失敗する
- **THEN** 次のポーリングでissueは待ちになり、中断を説明するコメントが付く

#### Scenario: 付け替えが反映されていなかった
- **WHEN** 着手のときの付け替えで、ラベルの変更が失敗し、issueは `agent:ready` のまま残る
- **THEN** 次のポーリングで着手がやり直され、issueは `agent:running` になる

### Requirement: 起動時の回復の失敗
起動時の回復で、あるissueの書き戻しが失敗したとき、エージェントは起動を続け、その書き戻しを再試行しなければならない（MUST）。
`agent:running` のissueの検索が失敗したときは、起動を失敗とする。

#### Scenario: 回復の書き戻しが一時的に失敗する
- **WHEN** `agent:running` のissueが残った状態で `switchboard agent run` を起動し、そのissueのコメントの投稿が1回失敗する
- **THEN** エージェントは起動してほかのissueのポーリングを始め、次のポーリングでそのissueが待ちになる

### Requirement: 再試行のあとに届いていた返答
書き戻しの再試行でissueを待ちにしたとき、信頼済みの返答が既に届いていれば、エージェントは、待たずに次の実行を始めなければならない（MUST）。

#### Scenario: 再試行の間に返答が届いた
- **WHEN** 書き戻しのラベルの付け替えが失敗し、その間にマスターが返答を書く。次のポーリングで再試行が成功する
- **THEN** issueは待ちを経て、直ちに `agent:running` に戻り、返答を含むプロンプトで次の実行が始まる

## MODIFIED Requirements

### Requirement: 状態の表示
`switchboard agent status` は、この端末の担当プロジェクトと、実行中のissue、最後の実行の結果を表示しなければならない（MUST）。
書き戻しの再試行を待つ実行があるとき、`switchboard agent status` は、それを書き戻し待ちとして、実行中のissueとは別に表示しなければならない（MUST）。

#### Scenario: 実行中の表示
- **WHEN** issue 12の実行中に `switchboard agent status` を実行する
- **THEN** issue 12が実行中として、開始時刻とともに表示される

#### Scenario: 書き戻し待ちの表示
- **WHEN** issue 12の実行の書き戻しが失敗し、次のポーリングの前に `switchboard agent status` を実行する
- **THEN** issue 12が書き戻し待ちとして表示され、実行中のissueとしては表示されない

### Requirement: 消えたプロジェクト
設定の読み直しで担当プロジェクトが消えたとき、エージェントは、そのプロジェクトの新しい実行を始めてはならない（MUST NOT）。実行中の実行は、最後まで続ける。
実行が待ちで終わったときに届いていた返答による次の実行も、新しい実行に含む。
消えたプロジェクトの実行の書き戻しが失敗したとき、エージェントは、書き戻せるまで再試行を続けなければならない（MUST）。

#### Scenario: 実行中に設定から消した
- **WHEN** `gh:uskanda/notes` のissueを実行している間に、そのプロジェクトを設定から手で消す
- **THEN** 実行は最後まで続き、結果が投稿される。そのあと、そのプロジェクトのissueは扱われない

#### Scenario: 消したあとに待ちで終わった
- **WHEN** `gh:uskanda/notes` のissueの実行中に、マスターが返答を書き、そのプロジェクトを設定から消す。実行は質問を残して終わる
- **THEN** issueは待ちになり、次の実行は始まらない

#### Scenario: 消したあとで書き戻しに失敗した
- **WHEN** `gh:uskanda/notes` のissueの実行中に、そのプロジェクトを設定から消す。実行の書き戻しのラベルの付け替えが1回失敗する
- **THEN** 次のポーリングで再試行され、issueは待ちになる
