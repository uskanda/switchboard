# Design

## Context

受信箱のサービス（`switchboard inbox serve`）は、起動のときに各フォージの受信箱のトークンでクライアントを1つずつ作り、すべての要求に使っている。Web表示（`switchboard-web`）はトークンを持たず、Unixソケットの `<inboxapi>` を通して受信箱のサービスを呼ぶ（ADR-037）。

ログイン、セッション、GitLabのOAuthのトークンの取得と更新は、Web表示の認証（issue #15）の変更で作る。この変更は、その結果として、受信箱のサービスが要求ごとに「利用者の文脈」を引けることを前提にする。利用者の文脈は、GitLabのユーザー名、所属するグループのフルパス、その時点で有効なアクセストークン、更新用のトークンを取り直す手段である。文脈をソケットでどう渡すかは、Web表示の認証の変更で決める。

## Goals / Non-Goals

**Goals:**

- 認証を設定したとき、Web表示からのGitLabへの書き込みを、ログインした人の身元にそろえる
- 共有の受信箱のトークンを、読み取りとownerのGitHubへの書き込みだけに使う
- `<inbox.auth>` の無い構成のコードの経路を変えない

**Non-Goals:**

- ログインの画面、セッション、トークンの取得と更新（issue #15）
- GitHubでの利用者ごとの書き込み（#152）
- エージェントとCLIの書き込みの身元

## Decisions

### 認証の設定を `config.yaml` に置く

`<inbox.auth>` は、核の `config.yaml` の `inbox` 節に置く。権限を判定してトークンで書き込むのは受信箱のサービスで、Web表示の `web.yaml` は核の設定を知らない（ADR-037）。grillingで仮に呼んだ名前は、この置き場所に合わせて改める。

```yaml
inbox:
  auth:
    owner: alice                  # GitLab user; admin, and the only one who may write to GitHub projects
    member_groups: [team]
    admin_groups: [team/leads]
```

検証（GitLabの設定の有無、空の節、エージェントの身元と `trusted_authors` の重なり）は、設定の読み込みの検証に足す。エージェントも同じ設定を読むので、エージェントの起動でも誤りになる。

### 要求ごとに「書き手」を選ぶ

受信箱のサービスの書き込みの経路（返答、承認、issueの作成、マージ、draftの解除、自動のマージ）は、今は `Server` が持つフォージのクライアントを使う。これを、要求の利用者の文脈から書き手を選ぶ関数に通す。

- 認証が無い：今のクライアント（共有のトークン）
- GitLabのプロジェクト：利用者のアクセストークンで、要求ごとに `gitlab.New(token, baseURL)` を作る。クライアントは軽いので使い回さない
- GitHubのプロジェクトで、利用者がowner：今のクライアント（共有のトークン）
- それ以外：権限が無いことを示す誤り

読み取り（一覧、1件、マージの状態、アイコン）は、これまでどおり共有のトークンで行い、結果を利用者で絞る。読み取りを利用者のトークンで行うと、一覧のキャッシュとSSEのための取り直しが人数分に増えるためである。

代わりに検討した案は、利用者ごとに受信箱の全体（キャッシュとSSE）を持つ形である。読めるものの判定がフォージに任せられる利点はあるが、フォージへの問い合わせが人数に比例して増え、検索の制限（30回/分）に当たる。

### 読めるプロジェクトの判定

GitLabのプロジェクトごとに、利用者のトークンで `GET /projects/:id` を呼び、200なら読める、404か403なら読めないとする。結果は、利用者とプロジェクトの組で10分間キャッシュする。誤り（ネットワークなど）のときは、読めないものとして扱い、キャッシュしない。

一覧、1件の表示、issueを作れる先の一覧、マージの状態、アイコンの各応答の前に絞る。SSEの変化の知らせは中身を持たず、受け取った画面が一覧を取り直すので、絞るのは一覧の応答だけでよい。

### 信頼されるかの判定

1件の表示の応答に、ログインした人の返答がエージェントに指示として扱われるかを足す。GitLabのプロジェクトでは、利用者のユーザー名が `trusted_authors.gitlab` にあるかで決める。GitHubのプロジェクトでは、ownerだけが見られるので、GitHubの受信箱のトークンの持ち主が `trusted_authors.github` にあるかで決める。認証が無いときは、今までどおり判定しない。

### adminだけの経路

追加の指示（`/v1/instructions`）とプロジェクト（`/v1/projects`）は、利用者がadminでなければ断る。Web表示は、admin以外には設定の画面への導線を出さない。

### 自動のマージの身元

自動のマージの記録（`automerge.Store`）に、頼んだ人のユーザー名を足す。更新用のトークンを取り直す手段は、記録とは別に、メモリーの表で持つ。表は受信箱のサービスの再起動で消える。自動のマージを試すとき、表に手段が無い記録は、理由「受信箱のサービスが再起動したため」で取り消し、今の結果の知らせ（ADR-048）に載せる。

### エージェントの特例

ADR-056の特例を判定する箇所に、`<inbox.auth>` の有無を渡す。認証を設定した構成では、エージェントの身元と `trusted_authors` が重ならないことを設定の検証が保証する。そのため、特例は働かない。仕様では、それをはっきり書く。

### 監査ログ

受信箱のサービスが書く監査ログの行に、`actor` の項目を足す。認証が無いときは書かない。

### Androidのアプリ

一覧の応答に、認証を設定しているかを足す。アプリは、通知のボタンを押されたとき、最後に読んだ一覧の値を見る。認証があれば、裏のタスクで送らずに、そのissueの画面を開く。値をまだ読んでいなければ、安全のため開く側にする。

### ADR

ADR-059を足す。ADR-059は、認証を設定した構成について、次のADRを改めると書く。

- ADR-015：エージェントが本人のアカウントで投稿する
- ADR-036：Web表示に認証が無い
- ADR-040：受信箱のトークンでissueを作る
- ADR-043：マージを受信箱のトークンで行う
- ADR-056：エージェントと信頼するユーザーが同じアカウントのときの特例

## Risks / Trade-offs

- リスク：利用者のトークンが、要求の途中で失効する。対策：利用者の文脈が、有効なトークンを返す前に更新する。更新に失敗したら、ログインし直しを求める誤りを返す。
- リスク：読めるかの判定のキャッシュの10分の間は、権限を外された人も読める。対策：受け入れる。グループから外れた人は、セッションの確認で入れなくなる。
- リスク：共有のトークンで読んだ一覧を絞るので、絞りの漏れがそのまま情報の漏れになる。対策：絞る関数を必ず通すことを、経路ごとのテストで確かめる。経路は、一覧、1件、作れる先、マージの状態、アイコンである。
- リスク：ownerのセッションを奪った人は、共有のトークンでGitHubに書ける。対策：セッションの守りは、Web表示の認証の変更に依る。ownerは1人に限る。
- リスク：自動のマージ待ちが、受信箱のサービスの再起動で消える。対策：取り消したことを知らせ、人がもう一度押す。

## Migration Plan

1. 認証なしの構成は、そのまま動く
2. 認証を使うときは、エージェント用のbot（またはProject Access Token）を作り、`agent_identity` と `token_ref` を移す。`trusted_authors` から自分以外の身元を外す
3. GitLabの受信箱のトークンを `read_api` のものに替える
4. `<inbox.auth>` を書き、`switchboard doctor` で警告が無いことを確かめる
5. 戻すときは、`<inbox.auth>` を消して受信箱のサービスを再起動する
