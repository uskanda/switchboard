# grilling 記録: add-run-allow-and-instructions

switchboardの自動実行でも、OpenSpecを使うプロジェクトでOpenSpecの流れを守らせるための計画である。調べたところ、利用者の `~/.claude/CLAUDE.md` は実行に届いていた。それでも流れが守られない原因は3つあった。1つ目は、実装する実行の許可リストにSkillツールと `openspec` のCLIが無く、`dontAsk` で拒否されること。2つ目は、計画の実行が読み取りの権限で動き、変更を捨てるので、grillingと提案がissueのコメントにしか残らないこと。3つ目は、実装する実行のsystem promptがOpenSpecに触れないことである。実装する実行68件のうち、`openspec/changes/` に書いたのは13件だった。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 仕組みの形 | 汎用の仕組みだけを足す。追加で許可するツールの設定と、実装する実行への利用者の追加の指示である。「OpenSpecを使う」は利用者の指示に書き、製品はOpenSpecを知らないままにする（ADR-021） | 第1ラウンド Q1 |
| changeを作る段階 | 計画は今のままissueのコメントで往復する。承認のあとの実装の実行が、最初のコミットでchangeを作る。issue上の質問と回答を `grilling.md` に、承認された計画をproposal、design、tasksに写す。計画のモードを通らない直接の実行では、grillingを省いた記録にして同じように作る。これは利用者の指示の中身として書く | 第1ラウンド Q2 |
| スキルの利用 | Skillツールを許可できるようにする。対話が要るスキルを使わないことは、利用者の指示に書く | 第1ラウンド Q3 |
| 追加の許可の置き場所 | 設定ファイルの全体の `<agent.allow_tools_extra>` と、プロジェクトごとの `<projects[].allow_tools_extra>` の両方に置き、つなげる。Web表示からは編集させない | 第2ラウンド Q4 |
| 追加の許可の制限 | 設定の読み込みのときに検査する。組み込みのdenyに当たる項目と、無制限の `Bash`、`Bash(*)` は誤りとして起動を止める。それ以外は書かれたとおりに通す | 第2ラウンド Q5 |
| 追加の許可を使う実行 | ファイルを書く実行のすべて（直接の実装、承認のあとの実装、CIとpushの失敗を直す実行、baseとの衝突を直す実行）。計画の実行は読み取りの権限のままにする | 第2ラウンド Q6 |
| 実装する実行への追加の指示 | `plan.md` とは別に `<run.md>`（全体とプロジェクトごと）を作り、ファイルを書く実行のsystem promptに入れる。置き場所、検査（32 KiB、秘密の検査）、監査ログ、CLIとWeb表示での編集は `plan.md` と同じにする | 第2ラウンド Q7 |
| OpenSpec向けの指示の置き場所 | `docs/` に、OpenSpecを使うプロジェクト向けの `<run.md>` と `<allow_tools_extra>` の記入例を載せる。開発者の端末の `<instructions/run.md>` への書き込みは、tasksの最後に手作業の手順として入れる | 第3ラウンド Q8 |
| ADR | ADR-045を足す。ADR-038の追加の指示は計画用（`plan.md`）として残す。SECURITY.mdのT7に、追加の許可は設定ファイルにしか書けないことと、読み込みのときの検査を足す | 第3ラウンド Q9 |

## 後回しにしたもの

- 計画の実行に、`openspec list` などの読み取りのコマンドを許すこと
- 実行ごとに、使った追加の許可と `<run.md>` のハッシュを監査ログに残すこと
