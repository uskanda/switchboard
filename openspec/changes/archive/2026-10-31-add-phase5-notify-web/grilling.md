# grilling 記録: add-phase5-notify-web

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| この変更の範囲 | Phase 5の3項目のうち、待ちの通知とWeb表示（WUI）を作る。運用ログからのループ改善は、失敗の実例がたまってから別の変更にする | 第1ラウンド Q1 |
| スマホからusknasへの経路 | LANのアドレスで待つ。家の外からは見られない。Tailscaleは使わない | 第1ラウンド Q2 |
| 通知の経路 | Telegram。usknasでは、既に別の用途の通知をTelegramで運用している | 第1ラウンド Q3 |
| 通知に載せる内容 | プロジェクト、issue番号、待ちの理由、開くためのURLに加えて、issueのタイトルと質問の抜粋まで載せる | 第2ラウンド Q4' |
| 通知する事象と送り手 | 待ちになったとき（理由4つすべて）と、完了したときに通知する。送り手は、そのコメントを投稿したエージェントとする | 第2ラウンド Q4' |
| Telegramのトークンの置き場所 | Secret Serviceの `switchboard/telegram` に置く。chat idは設定ファイルに書く。サービスには暗号化したクレデンシャルで渡す | 第2ラウンド Q6 |
| WUIでできること | 一覧の表示と返答 | 第2ラウンド Q7 |
| WUIを動かすプロセス | usknasのsystemdのサービスとして常駐させる | 第2ラウンド Q8 |
| 一覧の更新とAPIの制限（V14） | サーバーの側で一覧を60秒キャッシュし、自動では更新しない。開くか再読み込みしたときに取る。GraphQLへの切り替え（V14）は先送りする | 第2ラウンド Q10 |
| この変更の完了条件 | issueが待ちになるとTelegramに通知が届き、そこからブラウザで受信箱を開いて返答すると、実行が再開する | 第2ラウンド Q11 |
| WUIの対象の画面 | スマホだけでなくデスクトップも対象にする。モバイル専用のUIにしない | 第2ラウンドの回答で指定 |
| 通知のリンク先 | フォージのissueのURL。`web_url` が設定にあれば、WUIへのリンクを2つ目として足す | 第3ラウンド Q12 |
| 完了の通知の中身 | プロジェクト、issue番号、作ったPRかMRのURL、issueのURL | 第3ラウンド Q13 |
| 通知に失敗したとき | 実行は止めず、監査ログに `<notify.failed>` を残す。再送はしない | 第3ラウンド Q14 |
| WUIで見せる範囲 | 一覧には `inbox --json` の項目を出す。1件を開くと、`show` と同じ質問の全文、フォージへのリンク、返答の欄を出す。スレッド全体は出さない | 第3ラウンド Q15 |
| WUIの待ち受けのアドレス | 既定は無し。`<web.listen>` にLANのアドレスを明示させ、`0.0.0.0` は拒否する | 第3ラウンド Q16 |
| フロントエンドの構成 | Vite、React、TypeScript、shadcn/ui（Tailwind）。パッケージの管理はpnpm。ビルドの成果物はコミットせず、`make` で先にビルドする。`make verify` とCIに、型の検査、lint、テストを足す。外のCDNは使わない | 第4ラウンド Q17' |
| ADR-010の範囲 | ADR-010（1つのバイナリ）は核の `switchboard` についての決定とし、WUIは別のモジュールとして扱う | 第4ラウンドの回答で指定 |
| UIの基準の置き場所 | リポジトリ直下に `DESIGN.md` と `<PRODUCT.md>` を作る。技術の設計書は `docs/DESIGN.md` のままにする | 第4ラウンド Q18 |
| WUIの置き場所 | 同じリポジトリの `web/`。フロントエンドと、薄いGoのバックエンド（独自の `go.mod`）を置く。成果物は、静的ファイルを埋め込んだ別のバイナリ `switchboard-web`。核の `make verify` から `web/` の検査も呼ぶ | 第6ラウンド Q19 |
| WUIと核のつなぎ方 | 経路はフロントエンド、WUIのバックエンド、核の順。核に `switchboard inbox serve` を足し、受信箱のトークンを持つ常駐のプロセスとして、UnixソケットでHTTPとJSONのAPI（一覧、1件、返答）を出す。核のモジュールに、公開のクライアントのパッケージ（`inboxapi`）を作り、WUIのバックエンドが読み込む。WUIのバックエンドは静的ファイルと検査だけを受け持つ。CLIを呼ぶ案は退けた | 第6ラウンド Q20' |
| WUIの設定 | WUI専用の `~/.config/switchboard/web.yaml` に置く。核の `config.yaml` には書かない | 第6ラウンド Q22 |
| 常駐のさせ方 | 核の `service install` に `--inbox`（`<switchboard-inbox.service>`、受信箱のトークンをクレデンシャルで渡す）と `--web`（`<switchboard-web.service>`、設置のときに `PATH` から `switchboard-web` を探す。クレデンシャルは無い）を足す | 第7ラウンド Q23 |
| ソケットの場所と保護 | 既定は `/run/switchboard/inbox.sock`。両方のunitに `RuntimeDirectory=switchboard` を指定する。手で動かすときは `$XDG_RUNTIME_DIR/switchboard/inbox.sock`。ソケットは0600で作る | 第7ラウンド Q24 |
| 通知の設定 | 核の `config.yaml` の `<notify.telegram>` に `chat_id` と `token_ref` を書き、`<notify.web_url>` も書ける。エージェントのサービスに、Telegramのトークンもクレデンシャルで渡す | 第7ラウンド Q25 |
| WUIの認証 | 当面は認証しない。LANにしか出さず、使うのは1人で、扱う情報も非常に機微ではないため。認証は課題としてissueに残す | 第7ラウンド Q26（回答で指定） |
| 認証なしでの返答の守り方 | 返答のPOSTだけ、`Origin` と `Host` が `<web.listen>` のアドレスと一致することを検査し、合わなければ拒否する。外のWebページからのCSRFとDNS rebindingを防ぐ。LANの中の別の機器から返答できることは、認証のissueに残す | 第8ラウンド Q27 |
| 受信ポートの不変条件 | 「端末は受信ポートを開かない」を、WUIについて改める。ADR-036に記録する | 第2ラウンド Q2の帰結として会話中に確認 |
