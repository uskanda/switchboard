# grilling 記録: add-phase3-multihost

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 対象のOSと2台での確認 | 当面はLinuxだけを対象にする。macOSは後で扱う。2台で同時に動かす仕組みは作るが、実物の2台での確認はissueにして後回しにする | 第1ラウンド Q1 |
| 担当の割り当ての形 | 今と同じく、1つのプロジェクトを1台が担当する。設定の誤りで2台が同じプロジェクトを担当したときに備え、着手の時点で端末をまたいだ重複を防ぐ | 第1ラウンド Q2 |
| ADR-015、ADR-023、ADR-029の扱い | このフェーズには入れない。エージェントの投稿アカウントの分離、専用OSユーザーでの実行、macOSのキーチェーンは、別の変更で扱う | 第1ラウンド Q3 |
| Linuxでの常駐の方法 | systemdで常駐させる。ログインしていないとgnome-keyringは解錠されないので、トークンは暗号化したクレデンシャルで渡す | 第1ラウンド Q4 |
| 常駐のときのトークンの渡し方 | systemd 255では、ユーザーサービスで暗号化したクレデンシャルを読めない。そのため、`User=` を指定したシステムサービスにし、ホストの鍵で暗号化して `LoadCredentialEncrypted=` で渡す | 第2ラウンド Q5 |
| 端末をまたいだ重複の検知 | 着手のときに、マーカー付きの着手のコメント（`state=running`、`host`、`run`）を投稿してから取り直す。最後の `agent:ready` より後で、最も早い着手のコメントを出した端末だけが実行する | 第2ラウンド Q6 |
| 常駐の設定の配り方 | `switchboard` のサブコマンドで、unitの生成からクレデンシャルの暗号化までを行う。sudoで何をするかは、sudoを求める前に示す | 第2ラウンド Q7 |
| 後回しにする確認 | 実物の2台で同時に動かす確認だけを、issueにして後回しにする。常駐はusknasで確かめる | 第2ラウンド Q8 |
| サブコマンドの形と確認 | `service install`、`service uninstall`、`service status` の3つにする。`install` と `uninstall` は、sudoで実行するコマンドを対象のパスとともに全部表示し、`[y/N]` で確認を取る。`--dry-run` は表示だけで終わる。端末が無いときは、`--yes` が無ければ実行しない。sudoはコマンドごとに個別に呼ぶ | 第3ラウンド Q9 |
| クレデンシャルにするトークン | この端末の担当プロジェクトのエージェント用トークンだけにする。受信箱のトークンは含めない。トークンを入れ替えたら、`service install` をもう一度実行する | 第3ラウンド Q10 |
| V6（サブスクリプションで常駐させてよいか）の扱い | 調べずに進める。サブスクリプションの認証で常駐させるかは利用者の判断だと、READMEに書く | 第3ラウンド Q11 |
| 重複したときに退いた端末の後始末 | 退いた端末は、自分の着手のコメントを消し、ログと監査ログに記録する | 第3ラウンド Q12 |
| 常駐の実物での確かめ方 | OSは再起動しない。`systemctl restart` と、プロセスを止めたあとの自動の再起動で確かめ、起動時に動くかは `systemctl is-enabled` で確かめる。実際の再起動での確認は行わない | 第4ラウンド Q13 |
| ADRの追加 | 常駐の形、端末をまたいだ重複の防止、sudoを要する操作の3つをADRに足す | 第4ラウンド Q14 |

## 後回しにしたもの

- 実物の2台で同時に動かす確認（issueにする）
- macOS（launchdとキーチェーン、ADR-029）
- エージェントの投稿アカウントの分離（ADR-015）と、専用OSユーザーでの実行（ADR-023）。V10もそちらで確かめる
- V6の利用規約の確認
- Project Access Tokenでの上書きの実物での確認（#7）
