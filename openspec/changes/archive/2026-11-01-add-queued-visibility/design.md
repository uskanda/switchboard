# Design

## Context

動機はproposal.mdの「Why」にある。現状は次のとおり。

- `internal/agent/agent.go` の `launch` は、着手のコメントとラベルの付け替えより前に枠を確かめる。枠が無いと、issueを `pending` に積んで `errQueued` を返す。このとき、issueには始めるラベルか `agent:waiting` が付いたままである。
- `pending` はメモリにだけある。`drain` と毎回のポーリングが、`consider` でissueを読み直して積み直す。
- 受信箱のサービスは別のプロセスで、フォージのラベルとコメントからだけ状態を知る。今は `agent:waiting` と `agent:running` のissueだけを検索する。
- マーカーの `Transient` は、着手と進捗を、返答の判定（`hasReply`）と受信箱の待ちの理由（`latestPost`）から外す。

## Goals / Non-Goals

**Goals:**

- 順番待ちの間だけ、issueにコメントが1つある状態を保つ
- 受信箱は、そのコメントだけを手がかりに順番待ちを判定する

**Non-Goals:**

- ラベルを足すこと（grilling.md Q1）
- 順番待ちの順番を変えること

## Decisions

### マーカーに状態 `queued` を足し、一時的なものとして扱う

`marker.Queued = "queued"` を足し、`Transient` に含める。理由は `marker.Reason` に入れる。値は `max-parallel`（端末の上限）と `project-max-parallel`（プロジェクトの上限）の2つである。既存の `limit` は利用上限の待ちの理由なので使わない。上限の値は本文にだけ書く。

一時的なものとして扱うので、返答の判定と受信箱の待ちの理由は今までどおり動く。返答の待ちから順番待ちになったissueでも、最後の待ちの投稿を読める。

### エージェントは、順番待ちのコメントをメモリと状態のファイルで覚える

`a.queued` に、issueごとの順番待ちのコメントのIDを持つ。同じ内容を `queued.json` として状態のディレクトリに書く。

- `launch` が `errQueued` を返すとき、`a.queued` に無ければ、コメントを投稿してログを残す。あれば何もしない。そのため、ポーリングのたびに積み直しても、コメントとログは1回だけになる
- 着手するとき、`claim` の前に、`a.queued` にあるコメントを消す。ログには「順番待ちから始めた」と残す
- `consider` で `decide` が実行しないと判断したとき（ラベルが外れた、closeされた）、`a.queued` にあればコメントを消す。順番待ちの最中の判断は `consider` を通るため、消す処理はここ1か所で済む
- 読み直しでプロジェクトが消えたとき、`dropPending` が外したissueのコメントも消す。フォージへの書き込みは、`pmu` を外してから行う
- 起動したとき、`queued.json` にあるコメントをすべて消し、ファイルを空にする。順番待ちのままなら、次のポーリングで投稿し直す

フォージから消すときに `forge.ErrNotFound` が返れば、消えたものとして扱う。

別の案として、着手のときにissueのコメントからこの端末の `queued` のマーカーを探して消す方法を考えた。それではラベルが外れたissueや、再起動の間に順番待ちでなくなったissueのコメントが残る。

### 枠の判定は、当たった上限も返す

`hasSlot` を、空きがあるかに加えて、当たった上限の種類と値も返す形に変える。コメントとログは、その値から作る。

### 受信箱は、始めるラベルのissueも検索する

`list` は、`agent:waiting`、`agent:running` に加えて、`agent:ready`、`agent:plan`、`agent:go` も検索する。各issueのコメントを読んだあと、次の順に状態を決める。

1. `agent:running` が付いていれば実行中
2. エージェントの `queued` のコメントがあれば順番待ち
3. `agent:waiting` が付いていれば待ち
4. どれでもなければ出さない

`Item.State` に `queued` を足し、`QueuedSince` を足す。理由は `Reason` に入れる。並びは、待ち、実行中、順番待ちの順にする。CLIの表示にも「Queued」の節を足す。

`Detail` も同じ順で決める。順番待ちのときは `State` を `queued`、`Since` を順番待ちの開始時刻にする。`agent:waiting` が付いていれば `Waiting` を真にし、最後の待ちの投稿を `Post` に入れる。付いていなければ、順番待ちのコメントを `Post` に入れる。

### Web表示

`api.ts` の状態の型に `queued` を足す。一覧は、「実行中」の下に「順番待ち」の節を出す。行には「順番待ち」の印、当たった上限の説明、経過時間を出す。1件の表示は、状態が `queued` なら「順番待ち」と経過時間を出す。返答の欄は `waiting` で決まるため、変えない。会話では、`queued` のコメントを着手と同じく1行に畳む。

## Risks / Trade-offs

- ［受信箱が、始めるラベルのissueのコメントも読む］→個人の規模では、始めるラベルの付いたissueは数件で、着手まで30秒ほどしか残らない。問い合わせの増え方は小さい
- ［`queued.json` の書き込みに失敗した］→再起動の後、そのコメントは消えずに残る。一時的なマーカーなので、返答の判定は妨げない。受信箱では、`agent:waiting` のissueだけが順番待ちとして見え続ける。書き込みの失敗はログに残す
- ［順番待ちの理由が、書いた後に変わる］→コメントは編集しない（grilling.md Q6）。理由が変わっても、順番待ちであることは正しい
