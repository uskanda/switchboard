# Design

## Context

動機はproposal.mdの「Why」を参照。今のコード（main、ca36b27）で、この設計を縛る点は次のとおり。

- `pollMu` は、ポーリング（`poll`）、中継のイベントによる取り直し（`refresh`）、設定の読み直しの反映（`applyProjects`）を1つずつにする。`launch` を呼ぶ経路には、このロックの中のものと外のものがある。外から呼ぶのは、実行のgoroutineの終わりにある、待ちのあとの再実行（`consider`）とキューの消化（`drain`）である
- `launch` は、`active` に登録してから、着手のコメントの投稿（`claim`）とrunningへの付け替え（`Swap`）をする。`evaluateOnce` は、activeでラベルがrunningでないissueを見ると `maybeCancel` を呼ぶ
- `writeBack` は、最初に `outcome.json` を保存し、同じ `run` と `state` のコメントがあれば投稿しない。そのため、何度呼んでも二重に投稿しない。書き戻しをやり直す処理は、起動時の `recover` と `recoverOne` だけにある
- `labels.Swapper` の `Swap` は、`SetLabels` が成功したあとの取り直しでも失敗を返す。失敗が返っても、ラベルは変わっていることがある
- `since` は、プロジェクトの `seen` の最新から1分引いた時刻である。`evaluate` は成功したときだけ `seen` に記録する
- ループの間隔（`interval`）と取得するプロジェクト（`due`）は、中継の接続と `relay.hooks` で決まる。ティッカーの間隔を変えるのは `wake` を受けたときだけである
- 設定の読み直しで消えたプロジェクトは `projects` から外れ、その `pending` は捨てられる。`Routes` の項目は残る
- issueのロック（`State.Lock(lockName(ref))`）を使うのは、エージェントの `launch` だけである。ロックのファイルは `locks/<name>.lock` に置かれる

## Goals / Non-Goals

**Goals:**

- `launch` を呼ぶ経路を、すべて `pollMu` の中に入れる
- 書き戻しのやり直しを、起動時の回復と同じ `writeBack` の経路で行う
- 評価し直すissueの扱いを、`since` の計算の1か所にまとめる

**Non-Goals:**

- 起動時の回復で、他の端末の実行を中断として書き戻す点を直すこと（#28）
- 書き戻しの一覧をファイルに残すこと。エージェントが再起動したら、起動時の回復が引き継ぐ
- 指数バックオフ。再試行はポーリングの間隔に合わせる

## Decisions

### D1. 実行の後の処理を `pollMu` の中で行う

実行のgoroutineの終わりの処理を、`pollMu` を取ってから行う。処理は、`finish` のあとの待ちのあとの再実行と、`drain` である。これで `launch` を呼ぶ経路は、次のすべてが `pollMu` の中になる。

- `poll`、`refresh` から呼ぶ `evaluateOnce`
- `poll`、`refresh` から呼ぶ `drain`
- 実行のgoroutineの終わり（この変更で `pollMu` の中に入れる）
- 書き戻しの再試行（D2。`poll` の中で行う）

評価の時点でactiveなissueは、`launch` が `Swap` まで済ませている。`maybeCancel` は、取り直したラベルがrunningでなければ、人が外したものとして扱ってよい。

代わりの案は、`active` に「着手中」の印を持たせ、その間は `maybeCancel` を呼ばない形だった。並行性は残るが、着手中にcloseされたときの扱いを別に考える必要がある。直列にすれば、評価と着手の組み合わせを考えずに済むので、こちらを採る。

ポーリングの最中に実行が終わると、次の実行はそのポーリングの終わりを待つ。待ちは数秒である。設定の読み直しで新しいプロジェクトをcloneしている間も待つが、cloneが起きるのはプロジェクトを足したときだけである。

終了のときは、`Run` がループを抜けてから `Wait` で実行を待つ。そのときは誰も `pollMu` を持たないので、実行のgoroutineは止まらずに終わる。

### D2. 書き戻しの再試行の一覧

`Agent` に、書き戻しが終わっていない実行の一覧 <writebacks> を持たせる。キーはissueで、`mu` で守る。項目は次を持つ。

- プロジェクト（`config.Project`）。再試行のあとの再実行と、GitLabのノートの数の記録に使う
- 実行（`run`、`session`、`ack`）
- 結果（`outcome`）。中断として書き戻すものは空にする
- 起動時の回復から来たか。来たものについては、D3の判定で着手のコメントを確かめない
- 最初に失敗した時刻と、監査ログに失敗を記録したか

項目を入れるのは、次の3か所である。

- `execute` で `writeBack` が失敗したとき。結果を入れる
- `launch` で、`claim` に勝ったあとの `Swap` が失敗したとき。結果は空にする（中断）
- `recover` で、`recoverOne` が失敗したとき。`recover` はエラーを返さず、ログに残して起動を続ける。runningのissueの検索の失敗だけを、今までどおりエラーとして返す

`poll` は、`drain` の前に一覧を処理する（<settle>）。取得するプロジェクト（`ps`）に関わらず、毎回すべての項目を扱う。そのため、設定から消えたプロジェクトの項目も再試行が続く。activeなissueの項目は飛ばす。

実行のgoroutineで項目を入れたときは、ループに間隔の見直しを知らせる（D5）。ティッカーが `reconcile_interval` で回っている場合でも、次の再試行を `poll_interval` のうちに起こすためである。初めは `wake` を送る案だったが、`wake` は全プロジェクトの取得を伴うので、取得をしない知らせを別に設けた。

実行の記録（`record`）の状態に `writeback` を足す。項目を入れるときに記録をこの状態にし、`Ended` に失敗の時刻を書く。`agent status` は、この状態の記録を「write-back pending since <時刻>; retried at each poll」と表示する。エージェントが動いていなければ、「recovered when the agent starts」と表示する。起動時の回復は、`writeback` の記録の `outcome.json` を読んで書き戻すので、`recoverOne` を変えずに引き継げる。

### D3. 再試行の判定

項目ごとに、issueを `Thread` で読み直して、次の順に判定する。

1. 読み直しが失敗したら、項目を残す。ログに1行出す
2. issueがopenで、ラベルがrunningで、最新の着手のコメントがこの実行のものなら、`writeBack` で書き戻す。中断の項目には `recoverOne` と同じ中断の結果を作る。最新の着手のコメントとは、エージェントの身元が書いた `state=running` のマーカーのうち、コメントIDが最も大きいものである。起動時の回復から来た項目は、着手のコメントを確かめない
3. 2に当たらず、結果があり、その結果のコメントが未投稿なら、コメントだけを投稿する。ラベルは変えず、通知も送らない。人が引き取ったissueに「待っています」と通知すると、誤った案内になるためである。進捗のコメントは消す
4. 2に当たらない中断の項目は、何も書かない。ラベルが始めるラベルのまま（着手の付け替えが反映されなかった）なら、D4の仕組みで着手がやり直される

2か3が成功するか、3と4に当たったら、項目を外す。2が成功したら、`execute` の成功のときと同じく、記録を `finished` にして `last.json` を書く。GitLabで待ちにしたら、ノートの数を記録する。待ちにしたうえでプロジェクトがまだ担当にあれば（D6）、`consider` を呼ぶ。返答が届いていれば、次の実行が始まる（ADR-016）。

`writeBack` に、ラベルを変えずにコメントだけを投稿する形を足す。投稿済みかどうかの判定と、秘密の検査、`check_command` は共通にする。

ログには、失敗のたびに1行出す。監査ログには、最初の失敗（<writeback.failed>）と、成功（<writeback.retried>）か断念（<writeback.abandoned>）だけを記録する。

### D4. 評価し直すissueと `since`

`Agent` に、評価の終わっていないissueの一覧 <unsettled> を持たせる。キーはissueで、`mu` で守る。値は、そのissueの最新の更新時刻と、キュー待ちかどうかである。

- `evaluate` が成功したら、一覧から外して `seen` に記録する（今までどおり）
- `errQueued` なら、キュー待ちとして一覧に入れる
- `state.ErrLocked` かほかのエラーなら、キュー待ちでないものとして一覧に入れる
- `forge.ErrNotFound` なら、一覧から外して `seen` に記録する。issueが見つからないので、評価し直さない
- `drain` の `consider` が成功したら、一覧から外す。失敗したら、キュー待ちでないものに変える

`since` は、`seen` の最新と、一覧のうちそのプロジェクトの更新時刻のうち、早いほうから1分引いた時刻にする。`seen` が空なら、今までどおり時刻の指定なしで取得する。評価が終わっていないissueは、次のポーリングの `UpdatedIssues` に必ず出る。`seen` に記録されていないので、評価し直される。

設定の読み直しでプロジェクトが消えたら、そのプロジェクトの項目を `pending` と同じく捨てる。

代わりの案は、`drain` で失敗したissueを `pending` に戻す形だった。通常のポーリングで評価に失敗した場合の取りこぼしが残るので、採らない。

キュー待ちのissueは、今までどおりポーリングのたびに評価される（`Thread` と `LabelActor` を呼んで、キュー待ちに戻る）。今のコードでも、`since` が追い越すまでは同じ呼び出しをしているので、呼び出しの数は増えない。

### D5. やり直しの間隔

次のどちらかがある間、`interval` は `poll_interval` を返す。

- 書き戻しの一覧の項目
- 評価し直すissueのうち、キュー待ちでないもの

`due` は、中継につながっていて照合の時期でないときも、キュー待ちでない評価し直すissueのプロジェクトを、取得の対象に足す。

ループは、ポーリングのあとで `interval` を計算し直し、今のティッカーの間隔と違えば `Reset` する。今は `wake` を受けたときだけ間隔を変えているので、やり直すものができたときと、無くなったときにも変わるようにする。ループのポーリングの外でやり直すものができたとき（中継のイベントによる取り直し、実行の終わり）は、取得をしない知らせ（<tune>）をループに送り、ループは間隔だけを見直す。

この変更は、要件「中継による検知」（`fix-relay-unhooked-polling` が変更中）には手を入れない。やり直しの間隔は、新しい要件「やり直しの間隔」に書く。

### D6. 消えたプロジェクトでの再実行

実行のgoroutineの終わりの待ちのあとの再実行と、D3の再試行のあとの再実行の前に、プロジェクトがまだ担当にあるか（`projectList` にあるか）を確かめる。無ければ再実行しない。D1でこの処理は `pollMu` の中に入るので、`applyProjects` と同時には動かない。

### D7. ロック名

issueのロック名を、フォージの種別、所有者、リポジトリ、番号を `~` でつないだ名前にする。所有者のサブグループの `/` も `~` に置き換える。例は `gh~owner~repo~12` と `gl~group~sub~repo~3` である。GitHubとGitLabのどちらも、所有者とリポジトリの名前に `~` を使えない。リポジトリの名前は `/` を含まないので、最後の2つの区切りがリポジトリと番号を分ける。そのため、別のissueが同じ名前になることはない。

古い名前のロックのファイルは、`locks/` に残る。使われないだけで、害は無い。

### D8. テストの道具

偽フォージ（`internal/forge/fake`）に、次を足す。

- `PostComment` と `Thread` の失敗の注入。`FailNthSetLabels` と同じく、n回目の呼び出しを失敗させる
- issueの削除。削除したissueの `Thread` は `forge.ErrNotFound` を返す
- `PostComment` のあとに呼ぶ関数。#25の競合のテストで、着手のコメントの投稿の直後に別のgoroutineからポーリングを始めるのに使う

#25のテストでは、着手のコメントの直後に別のgoroutineで `Poll` を始める。`Poll` が着手の終わりまで待つこと、実行が取り消されないこと、ラベルがrunningになることを確かめる。

## Risks / Trade-offs

- ［一時的でない失敗（トークンの失効など）で、書き戻しの再試行と評価のやり直しが続く］→失敗は毎回ログに出る。止まったissueは受信箱の実行中の欄に残るので、人が気付ける。トークンを直せば、再起動しなくても続きが進む
- ［やり直すものがある間、ループの間隔が `poll_interval` に縮み、APIの呼び出しが増える］→増えるのは、やり直すものがある間だけである。照合の時期でないプロジェクトのうち、取得するのはやり直すissueのあるものだけである
- ［`since` が止まっている間、`UpdatedIssues` の結果が大きくなる］→`seen` にあるissueは評価せずに飛ばすので、増えるのは一覧の取得の分だけである
- ［実行の後の処理が `pollMu` を待つ］→待つのは長くても1回のポーリングの分である。D1を参照
- ［書き戻しの一覧はメモリにしかない］→エージェントが止まったら、起動時の回復が `agent:running` のissueを書き戻すので、失われない

## Migration Plan

- 設定の変更は無い。新しい版を置いて、エージェントを動かし直す（`make deploy`）
- 古い版に戻しても、実行の記録の `writeback` は、古い `agent status` に表示されないだけである。起動時の回復は、状態に関わらず `outcome.json` を読む
