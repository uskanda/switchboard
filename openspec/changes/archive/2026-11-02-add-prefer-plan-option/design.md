# Design

## Context

動機はproposal.mdの「Why」を参照。PR #79の前のmainで、この設計を縛る点は次のとおり。

- エージェントは、順番待ちのissueをプロジェクトの設定だけと対応付けて持っていた。順番待ちから取り出すときは、refの文字列の辞書順に並べていた
- 実行の種類（計画、承認後の実装、計画なしの実装）は、ポーリングのたびの評価で決まる。順番待ちのあいだに計画が承認されると、次の評価で種類が変わる
- 設定の読み直し（ADR-039）は、`projects` と `agent.max_parallel` だけを反映し、それ以外の変化は再起動を求めるログに出していた
- 順番待ちのコメントは、エージェントの起動時に消して出し直す

## Goals / Non-Goals

**Goals:**

- 待った時間の長いissueから順にスロットを渡す
- `agent.prefer_plan` を、`agent.max_parallel` と同じ道筋で読み直す

**Non-Goals:**

- 同じポーリングで見つかった計画と実装の起動の順を変えること（grilling.mdの後回しにしたもの）
- 順番待ちに入った時刻を、エージェントの再起動をまたいで残すこと
- 順番待ちのコメントの形式と、受信箱の順番待ちの並べ方を変えること

## Decisions

### D1 順番待ちの各issueに、種類と入った時刻を持たせる

順番待ちの値を、プロジェクトの設定から `queuedRun`（プロジェクト、計画の実行かどうか、入った時刻）に変える。
既に順番待ちにあるissueを入れ直すときは、入った時刻を残し、プロジェクトと種類だけを新しくする。順番待ちのあいだに計画が承認されても、待った時間は失われない。
入った時刻はエージェントのメモリの中だけで持つ。順番待ちのコメントは起動時に出し直すので、再起動で時刻が消えても、コメントの扱いと食い違わない（Q3）。

### D2 取り出す順を1つの比較関数で決める

`queueOrder` が順番待ちのrefを並べる。`preferPlan` がオンなら計画の実行を先にし、次に入った時刻の早い順、同じ時刻ならrefの文字列の順にする。
refの順を最後に置くのは、テストと実行の順を決まったものにするためである。

### D3 プロジェクトの上限で戻ったissueの時刻を戻す

`drain` は、起動を試みる前にissueを順番待ちから外す。`launch` が `errQueued` を返してissueが順番待ちに戻ると、新しい時刻で入り直してしまう。
そこで `drain` は外す前の時刻を控え、`errQueued` のときに `keepPlace` でその時刻を戻す。

### D4 読み直しは `agent.max_parallel` と同じ道筋に載せる

`config.Change` に `PreferPlan` を足し、`changedSections` の比較からは外す。エージェントは `Reload` で値を受け取り、次のポーリングの前の `applyProjects` で `agent.max_parallel` と一緒に反映する。

## Risks / Trade-offs

- 同じポーリングで計画と実装が見つかり、空いたスロットが1つだけのときは、実装が先に始まることがある。次に空くスロットは計画に渡るので、Q4でこの範囲を受け入れた
- D3の戻りは `hasSlot` の確認と同じロックの下で起きるため、結合テストでは起こせない。`keepPlace` を単体のテストで確かめた
- 再起動すると入った時刻が消え、待った順が崩れる。順番待ちのコメントを起動時に出し直す今の扱いと揃うので、受け入れる
