# Design

## Context

動機はproposal.mdにある。PR #45の前は、1件の詳細を求めるたびに、受信箱のサービスがフォージへ次の順で問い合わせていた。

1. エージェントのアカウントのID
2. issue
3. コメント
4. 編集した人（GraphQL）

4回の往復が続くため、WUIは数秒のあいだ空の表示のままだった。WUIは1件を読み終えるまで `detail` を空にしていた。

## Goals / Non-Goals

**Goals:**

- 1件の取得にかかる往復の待ち時間を、ほぼ1回分に縮める
- 取得を待つ間、WUIに読み込み中か前回の内容を表示する

**Non-Goals:**

- 前回の内容を、再読み込みやタブをまたいで残すこと
- 実際のフォージを相手にした速さの測定

## Decisions

- `Inbox` は、エージェントのアカウントのIDを、フォージ種別とログイン名（小文字）の組をキーとしてメモリ上で覚える。アカウントのIDは変わらないため、プロセスが動いている間は使い回す。引けなかったときは覚えず、次の要求で引き直す。設定を直したあと、再起動しなくても引けるようにするためである
- `Detail` は、エージェントのアカウントのIDとスレッドを同時に引く。どちらも他方の結果を使わない
- GitHubとGitLabのアダプタの `Thread` は、issue、コメント、編集した人の3つの問い合わせを、goroutineで同時に送る。誤りは、issue、コメント、編集した人の順に最初のものを返す
- WUIの前回の内容は、`web/ui/src/lib/issueCache.ts` のメモリ上の `Map` に置く。上限は50件で、最も前に読んだものから捨てる
  - ブラウザのストレージには書かない。issueの本文やコメントをブラウザに残さないためである
- `IssuePane` は、読み直しが届くまでの間を `reading` で表す。前回の内容が無ければ「読み込んでいます」を、あれば内容の横に「更新を取得中」を出す
  - 読み直しに失敗したとき、前回の内容があれば、誤りの知らせの末尾で、前回読んだ内容を表示していることを伝える
- 回るアイコンは `Spinner` とする。`prefers-reduced-motion` のときは回さず、意味は横の文字で伝える

## Risks / Trade-offs

- ［前回の内容が古いまま表示される］→「更新を取得中」を出し、読み直しが届いたら差し替える
- ［3つの問い合わせを同時に送ると、フォージのレート制限に早く届く］→ 問い合わせの回数は変わらないため、制限への近さは前と同じである
