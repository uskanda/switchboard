# Design

## Context

`switchboard inbox serve` は、画面がSSE（`/v1/events`）でつないでいる間だけ、フォージから一覧を取り直す（`add-web-two-pane-live`）。間隔は `<inbox.refresh_interval>` である。取り直しは、すべてのフォージを読み、GitHubの検索を1回使う。GitHubの検索の上限は1分に30回で、`MinRefreshInterval` が10秒なのもこのためである。

中継の配信口は、端末ごとのbearerトークンで認証する（ADR-035）。エージェントは `relayclient.Client` で配信口につなぎ、つないでいる間はwebhookのあるプロジェクトの照合を `reconcile_interval` に延ばす。進行中の `fix-relay-unhooked-polling` は、webhookの無いプロジェクトの間隔を延ばさないようにエージェントのループを直す。受信箱には触れないので、この変更とはぶつからない。

## Goals / Non-Goals

**Goals:**

- webhookのあるプロジェクトの変化を、数秒で受信箱の画面に出す
- 中継が切れても、今の間隔ごとの更新を保つ
- 画面で、変化がすぐ出るのか間隔ごとに出るのかがわかる

**Non-Goals:**

- 中継につないでいる間に、問い合わせの間隔を延ばすこと
- イベントの中のissueだけを取り直すこと。一覧は丸ごと取り直す

## Decisions

### トークンは `<端末名>-inbox` の別の端末として発行する

`relay token add --inbox <端末名>` は、`switchboard/relay-<端末名>-inbox` にトークンを置く。そのうえで、`relay.hosts` に足す `<端末名>-inbox` の項目を表示する。中継から見れば、受信箱のサービスは別の端末である。中継の側は変えずに済み、ADR-035の範囲に収まる。名前を利用者に付けさせる形（grilling q1のB）は、表示が `agent.relay` のままで書き間違えやすいので採らない。

設定は `<inbox.relay>` に置き、型は `<agent.relay>` と同じ `AgentRelay` を使い回す。`service install --inbox` は、`InboxCredentials` にこのトークンを足して渡す。

### 中継には、サービスが動いている間ずっとつなぐ

画面の接続は、タブを裏へ回すたびに切れ、表へ戻すとつなぎ直す。画面に合わせて中継の接続を開け閉めすると、接続とそのログが何度も出入りする。ずっとつないでおき、画面が無いときのイベントでは一覧のキャッシュ（`cached` と `last`）を捨てる。次に画面を開いたときは、控えを使わずに取り直す。接続はローカルから外向きなので、受信ポートの不変条件には触れない。

### 間隔ごとの問い合わせは延ばさない

受信箱は、GitHubを `search_scope` で1回検索するなど、フォージ単位で問い合わせる。プロジェクトごとに間隔を分けられないので、延ばすとwebhookの無いプロジェクトの変化が遅れる。これは `fix-relay-unhooked-polling` が直しているエージェントの問題と同じである。問い合わせは画面を開いている間だけなので、延ばさなくても負担は小さい。イベントは、間隔を待たずに取り直すきっかけとしてだけ使う。

### イベントは2秒まとめ、前回から10秒あける

GitLabでは、ラベルの付け替えとコメントが続けてwebhookになる。`RelayEvent` は、画面がつないでいれば、タイマーを1本だけ持つ。待つ時間は `RelayDebounce`（2秒）と、前回の取得（`last.FetchedAt`）から `config.MinRefreshInterval`（10秒）までの残りの長い方である。待っている間のイベントは足さない。タイマーが切れたら、取り直しをループへ頼む（`readAgain`）。その時点で画面が無ければ、キャッシュを捨てる。どちらの値も設定の項目とはせず、定数として持つ。テストでは、`Server` の非公開の項目で短くする。

### 中継の状態は一覧に入れて送る

`inboxapi.Inbox` に `relay`（`connected`、`disconnected`、設定が無ければ空）と `refresh_interval_seconds` を足す。`switchboard-web` は `inboxapi` の型をそのまま中継するので、型が増えるだけで渡し方は変わらない。新しいSSEのイベントを足す形（grilling q6のB）は、クライアント、Webの中継、ブラウザの3か所を変えることになり採らない。

`RelayState` は状態が変わったら、最後の一覧に新しい状態を入れて、フォージを読まずに送り直す。`same` は `relay` も比べる。`publish` は、送る直前に今の状態を入れ直す。取り直しの途中で状態が変わっても、古い状態を送らないためである。GET `/v1/inbox` は、キャッシュを返すときも今の状態を入れる。

### ヘッダの文言

ブラウザと受信箱のサービスがつながっている（`live`）ときだけ、文言を分ける。`connected` なら「自動更新中（即時）」、`disconnected` なら「自動更新中（N秒ごと）」、空なら「自動更新中」とする。点の印は変えない。1つの点でブラウザとのつながりと中継の両方を示すと、何が切れているのかがわかりにくくなる。

## Risks / Trade-offs

- 中継が配るイベントは、受信箱が扱わないプロジェクトの分も含む → 取り直しは最短でも10秒おきなので、GitHubの検索の上限に近づかない
- 画面が無いときのイベントで、取り直しをせずにキャッシュだけ捨てる → 次に画面を開いたときに1回だけ待つ。古い一覧を見せるよりよい
