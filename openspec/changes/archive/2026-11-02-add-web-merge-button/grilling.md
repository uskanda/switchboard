# grilling 記録: add-web-merge-button

issue `gh:uskanda/switchboard` #69の計画である。受信箱のWeb表示（WUI）で、完了（close待ち）のissueのPR/MRを、draftを解除してマージできるようにする。grillingは、issueのコメントで計画を先に立てるモードとして行った。エージェントが第1ラウンドの質問Q1〜Q7を出し、マスターが回答し、続く計画を `/ok` で承認した。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| マージに使うトークンと、権限を広げるADR | 受信箱のトークンの権限を広げる。ADR-043で、人がWUIから押すマージを人間のマージとし、README、設定例、doctorの説明を直す | issue #69 第1ラウンド Q1 |
| マージの方式 | 方式を指定しない。GitHubはAPIの既定のマージコミット、GitLabはプロジェクトの設定に従う | issue #69 第1ラウンド Q2 |
| ボタンの種類と、それぞれの動き | 「マージ」のボタンだけを置く。issueのcloseは、PR/MRの本文の `Closes #N` に任せる。推奨はマージとcloseのみの2つだったが、マスターがCを選んだ | issue #69 第1ラウンド Q3 |
| マージ後のリモートブランチ削除 | 消さない。GitHubの「Automatically delete head branches」などリポジトリの設定に任せる | issue #69 第1ラウンド Q4 |
| マージ前の安全確認 | 完了の時点のhead SHAを `sha` としてフォージに渡し、headが動いていればマージを断る。CIとマージできるかの判定はフォージに任せ、断られたら理由を誤りのトーストに出す | issue #69 第1ラウンド Q5 |
| ボタンの置き場所と確認 | 詳細のペインと、一覧の完了の行の両方に置く。どちらも確認のダイアログを出す。推奨は詳細のペインだけだったが、マスターがBを選んだ | issue #69 第1ラウンド Q6 |
| GitLabの対応範囲 | GitHubとGitLabの両方を作る。GitLabのdraftの解除は、タイトルの先頭の印を外して行う | issue #69 第1ラウンド Q7 |
| 計画の全体 | 回答を前提にした計画（フォージの層、受信箱の核、HTTPの二層、WUI、ADR-043、検証項目V38〜V40）を承認した | issue #69 計画の承認（`/ok`） |

## 後回しにしたもの

- 受信箱からissueを直接closeするボタン。Q3でCを選び、作らないことにした。ADR-043は、このボタンを使う場面が少なく、LANの中の誰でもマージしないままissueを閉じられるようになる、と理由を記録している
- マージの方式の設定（`<merge_method>`）。squashが要るときに足す（Q2）
- CIが通っていないときにボタンを無効にすること。ブランチの保護に任せる（Q5）
- baseが既定のブランチでないときに、マージの後でissueを閉じること。issueは受信箱に残り、手でcloseする
- 実機での確かめ（ROADMAPのV38〜V40）。マージの後にusknasのsandboxで行う
