# grilling 記録: keep-done-until-close

issue `gh:uskanda/switchboard` #53の計画である。`agent:done` の時点では受信箱から消さず、issueのcloseで消す。作ったPR/MRに問題があるときやコンフリクトしたときに、doneの後もやりとりを続けるためである。grillingは、issueのコメントで計画を先に立てるモードとして行った。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| doneのissueへのコメントで再開するか | 再開する。openのまま `agent:done` のissueに、最後の投稿より後で信頼済みのコメントが付けば、waitingと同じ規則で前の実行を引き継ぎ、runningに移す。受信箱の返答も、waitingとdoneの両方で受け付ける | 第1ラウンド Q1 |
| 一覧でのdoneの出し方 | 新しい状態 `done` とし、CLIとWUIで「順番待ち」の下に「完了（close待ち）」の節を出す。各行には、端末、完了からの経過時間、PR/MRのリンクを出す。完了した時刻の古い順に並べる | 第1ラウンド Q2 |
| doneの行の番号 | 待ちの行に続く通し番号を振る | 第1ラウンド Q3 |
| WUIのヘッダの件数 | 完了の件数を、順番待ちと同じく1件以上のときだけ出す | 第1ラウンド Q4 |
| 再開した実行が再びdoneになったときのPR/MR | フォージに「ブランチの開いたPR/MRを探す」操作を足す。開いたものがあれば作らずにそのURLを使い、doneの投稿は「PRを更新しました」とする。無ければ作る | 第2ラウンド Q5 |
| コンフリクトの解消をpushまで通す方法 | pushはforceなしのまま変えない。システムプロンプトに、baseとの衝突は `git merge origin/<base>` で解消し、rebaseと履歴の書き換えをしないと書き足す | 第2ラウンド Q6 |
| 計画を先に立てるモードのdoneの再開 | 承認された計画の実装（approvedRun）のまま再開する。classifyは今のままでこの動きになる | 第2ラウンド Q7 |

## 後回しにしたもの

- 人間がPRのブランチに直接pushしていて、switchboardのpushが拒まれる場合の自動の解消。今までどおり、waiting（error）として受信箱に出す
