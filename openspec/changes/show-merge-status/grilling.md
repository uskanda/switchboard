# grilling 記録: show-merge-status

issue `gh:uskanda/switchboard` #84の計画である。マージの確認ダイアログに、CIの結果とマージできるか（衝突の有無）を出す。grillingは、issueのコメントで計画を先に立てるモードとして行った。第1ラウンドの質問はコメント6583907864の後の投稿、回答はコメント6585903799、計画はコメント6585945344、承認はコメント6586186345（`/ok`、変更なし）である。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 受信箱のサービスにCIを読ませるか、GitHubの受信箱のトークンの権限を広げるか | A。新しいADRでADR-043の分担を改め、GitHubの受信箱のトークンに Actions: Read と Commit statuses: Read を足す。権限が無いときは、ダイアログに「CIを読む権限がありません」と出し、マージはこれまでどおりできる | 第1ラウンド Q1 |
| APIの形 | A。新しい口 `GET /v1/merge-status`（webでは `GET /api/merge-status`）を足し、確認ダイアログを開いたときに1件だけ読む。一覧の要素は変えない | 第1ラウンド Q2 |
| CIの失敗や衝突があるときにマージのボタンを止めるか | A。情報として出すだけにし、「マージする」は押せるままにする。最後の判定はフォージに任せる | 第1ラウンド Q3 |
| CIの表示の細かさ | A。要約の1行と、失敗中・実行中のチェックの名前をフォージへのリンクにして並べる。成功は数だけにする。マージできるかは「衝突なし／衝突あり／フォージが計算中」の3つ。headが画面のshaから動いていればそのことも出す | 第1ラウンド Q4 |
| 実装の計画 | コメント6585945344の計画のとおり。forgeの `ChangeRequestState` に `Computing` を足し、受信箱に `MergeStatus` を足し、API、web、UI、権限の文書、doctorを直す | 計画の承認（コメント6586186345） |
