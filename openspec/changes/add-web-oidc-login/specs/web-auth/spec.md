# Spec Delta

## Purpose

受信箱のWeb表示に、GitLabのOpenID Connectでログインできるようにする。ログインできる人を確かめ、セッションを保ち、ログインしていない人にはWeb表示の中身を見せない。

## ADDED Requirements

### Requirement: ログインの始まり
認証を設定したとき、Web表示は、ログインしていない人に、「GitLabでログイン」のボタンだけの画面を出さなければならない（MUST）。
ボタンを押すと、Web表示は受信箱のサービスに認可のURLを求め、ブラウザをそのURLへ移さなければならない（MUST）。
認可のURLは、次のものを持つ。

- `<inbox.auth>` のclient id
- スコープ `openid profile api`
- 推測できない `state`
- PKCEの `code_challenge`

戻り先は `http://<listen>/auth/callback` とする。

#### Scenario: ログインしていない人が開く
- **WHEN** 認証を設定した受信箱で、cookieの無いブラウザが `/` を開く
- **THEN** 一覧は出ず、「GitLabでログイン」のボタンだけが出る

### Requirement: GitLabからの戻り
Web表示は、`/auth/callback` で受け取った `code` と `state` を、受信箱のサービスに渡さなければならない（MUST）。
受信箱のサービスは、`state` が自分の発行したもので10分以内のときだけ、`code` をトークンと交換しなければならない（MUST）。交換にはclient secretとPKCEの `code_verifier` を使う。
受信箱のサービスは、トークンでGitLabのユーザー情報を読み、ユーザー名とグループを得なければならない（MUST）。
ログインできる人なら、受信箱のサービスはセッションを作り、推測できないセッションIDだけをWeb表示に返す。Web表示は、それを `HttpOnly` と `SameSite=Lax` のcookieにして `/` へ移す。
トークンは、受信箱のサービスの外へ出してはならない（MUST NOT）。

#### Scenario: 知らないstate
- **WHEN** 受信箱のサービスが発行していない `state` で `/auth/callback` が開かれる
- **THEN** トークンとの交換は行われず、ログインの画面に誤りが出る

#### Scenario: ログインできた
- **WHEN** `<member_groups>` のグループに属する `alice` がGitLabで許可して戻る
- **THEN** セッションのcookieが付き、一覧の画面が出る

### Requirement: ログインできる人
受信箱のサービスは、`<member_groups>` と `<admin_groups>` のどれかに属する人と、`<owner>` の人だけをログインさせなければならない（MUST）。
グループの判定は、GitLabのユーザー情報のグループのフルパスで行い、設定のグループの下位のグループに属する人も含める。
それ以外の人は、セッションを作らず、トークンを失効させなければならない（MUST）。Web表示は、ログインの画面に、この受信箱を使う権限が無いことと、ログインしたGitLabのユーザー名を出す。

#### Scenario: どのグループにも属さない人
- **WHEN** `<member_groups>` が `[team]` で、`team` にも下位のグループにも属さない `mallory` が戻る
- **THEN** セッションは作られず、ログインの画面に、`mallory` に権限の無いことが出る

#### Scenario: 下位のグループの人
- **WHEN** `<member_groups>` が `[team]` で、`team/app` に属する `bob` が戻る
- **THEN** `bob` はログインできる

### Requirement: ログインを求める範囲
認証を設定したとき、Web表示は、`/auth/` 以下と画面の静的ファイルを除くすべての要求に、有効なセッションを求めなければならない（MUST）。
セッションの無い `/api/` の要求には、401と、ログインが要ることを示す誤りの符号を返さなければならない（MUST）。SSEも同じとする。
受信箱のサービスも、`/v1/auth/` 以下を除くすべての要求で、セッションIDを確かめなければならない（MUST）。
画面は、401を受け取ったら、ログインの画面を出す。

#### Scenario: セッションの無いAPIの要求
- **WHEN** 認証を設定した受信箱で、cookieを付けずに `/api/inbox` を求める
- **THEN** 401が返り、一覧は返らない

### Requirement: セッションの期限
セッションは、受信箱のサービスのメモリーにだけ置かなければならない（MUST）。受信箱のサービスを再起動すると、すべてのセッションが消える。
セッションは、最後の要求から24時間たったときと、ログインから7日たったときに、消さなければならない（MUST）。
受信箱のサービスは、アクセストークンの期限が近づいたら、更新用のトークンで更新しなければならない（MUST）。更新のたびにグループの所属を確かめ直し、ログインできる人でなくなっていたらセッションを消す。更新に失敗したときも、セッションを消す。

#### Scenario: グループから外れた
- **WHEN** ログイン中の `bob` が `team` から外され、そのあと受信箱のサービスがトークンを更新する
- **THEN** `bob` のセッションは消え、次の要求は401になる

#### Scenario: 長く使わなかった
- **WHEN** 最後の要求から24時間たってから、同じcookieで一覧を開く
- **THEN** ログインの画面が出る

### Requirement: ログインした人の表示とログアウト
認証を設定したとき、Web表示のヘッダは、ログインした人のGitLabのユーザー名と、ログアウトのボタンを出さなければならない（MUST）。
ログアウトすると、受信箱のサービスはセッションを消し、GitLabでトークンを失効させなければならない（MUST）。Web表示は、cookieを消してログインの画面を出す。
ログアウトのPOSTには、返答と同じ `Origin` と `Host` の検査をかける。

#### Scenario: ログアウト
- **WHEN** ログイン中の `alice` がヘッダのログアウトを押す
- **THEN** ログインの画面が出て、古いcookieでの `/api/inbox` は401になる

### Requirement: Androidのアプリでのログイン
Androidのアプリは、GitLabの `base_url` の下のページを、既定のブラウザでなくWebViewの中で開かなければならない（MUST）。
WebViewのcookieは、アプリを閉じても残さなければならない（MUST）。

#### Scenario: アプリでログインする
- **WHEN** 認証を設定した受信箱をアプリで開き、「GitLabでログイン」を押す
- **THEN** GitLabのログインの画面がアプリの中に出て、許可すると受信箱の一覧に戻る

### Requirement: 認証を設定しない構成
`<inbox.auth>` が無いとき、Web表示と受信箱のサービスは、ログインを求めてはならない（MUST NOT）。今までどおり、`Origin` と `Host` の検査だけを行う。

#### Scenario: 1人の構成
- **WHEN** `<inbox.auth>` の無い設定で、Web表示を開く
- **THEN** ログインの画面は出ず、一覧が出る
