# grilling 記録: add-plan-first-mode

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 計画モードを決める単位 | プロジェクトの設定で既定を決め、issueのラベルで個別に切り替える | 第1ラウンド Q1 |
| 計画の段階で作るもの | issueのコメントだけ。質問のラウンドを往復し、質問が尽きたら計画をコメントして承認を待つ。コードにもファイルにも触れない。OpenSpecの成果物や `grilling.md` は、承認のあとの実装の実行で、issueのやり取りから作る（ハーネスに任せる） | 第1ラウンド Q2 |
| 承認の伝え方 | 信頼済みの人のコメントの先頭行が決まった語（既定は `/ok`）で始まるかを、switchboardが機械的に判定する。`/ok` のあとの上書きも実装のプロンプトに入る。語は設定で変えられる | 第1ラウンド Q3 |
| 計画の段階で実装させない仕組み | 計画の実行では、`Edit`、`Write`、`NotebookEdit`、`git add`、`git commit`、`make` を拒否し、`Read`、`Grep`、`Glob`、`git log`/`diff`/`status` だけを許す。実行のあと、HEADが変わらず、worktreeに差分が無いことを確かめる。差分があれば捨てて元に戻し、出力はそのまま投稿し、変更を捨てたことをコメントに書く | 第2ラウンド Q4 |
| 計画の実行の終わり方 | 計画の実行には別のスキーマを渡す。`status` は `questions`（題、本文、推奨の答えを持つ質問の配列）か `plan`（計画の本文）。switchboardがコメントの書式を整える。質問の番号はラウンドをまたいで通し番号にする | 第2ラウンド Q5 |
| `/ok` の意味 | 直前のエージェントの投稿が計画なら、承認して実装に入る。質問なら、推奨どおりの返答として計画の実行を続ける。上書きはどちらでも書ける | 第2ラウンド Q6 |
| 質問が無いとき | 質問のラウンドを飛ばして、すぐに計画を出してよい | 第2ラウンド Q7 |
| 計画への `/ok` 以外の返答 | 計画の実行をもう一度回し、計画を出し直す | 第2ラウンド Q7 |
| 計画の段階の状態の表し方 | 状態ラベルは今の4つのまま。計画の段階の待ちは `agent:waiting` とし、マーカーの `reason` を `plan-questions` か `plan` にする。今の段階は、モードと、最新の計画のあとの信頼済みの `/ok` の有無から、コメントで毎回判定する。`/ok` で実装に入ったあとの待ちは、普通の待ちとして扱う | 第2ラウンド Q8 |
| 受信箱とWeb表示 | 待ちの理由として「質問（計画）」と「計画の承認待ち」を出すだけ。承認は返答欄に `/ok` と書いて送る | 第2ラウンド Q10 |
| 始めるラベル | 付けるラベルは常に1つで済むようにする。`agent:ready` はプロジェクトの `plan_first` に従い、`agent:plan` は計画から、`agent:go` はすぐ実装に入る。着手したら、始めるラベルを外して `agent:running` に付け替える。モードは着手のコメントのマーカー（`mode=plan` / `mode=direct`）に記録し、以降の実行はそこから読む。始めるラベルは、状態ラベルの正規化では ready の仲間として数える | 第2ラウンド Q8への指摘、第3ラウンド Q11 |
| 設定とラベルの名前 | プロジェクトの設定は `<projects[].plan_first>`（既定は `false`）。ラベルの名前は `<labels.plan>` と `<labels.go>` で変えられ、`switchboard labels sync` で作る。承認の語は `<plan.approve_word>`（既定は `/ok`）。始めるラベルが2つ以上付いていたら、設定の誤りとして `waiting(reason=error)` にする | 第2ラウンド Q9、第3ラウンド Q11 |
| 計画の実行に渡す指示 | switchboardが持つ汎用の指示（コードを変えない。決まっていない判断を洗い出し、今答えられるものをすべて1ラウンドで推奨付きで聞く。事実は自分で調べる。決めることが無くなったら計画を出す）に加えて、利用者の追加の指示を渡せる。追加の指示はWeb表示で編集できる | 第3ラウンド Q12 |
| 承認のあとの実装の実行 | 承認された計画のコメントと `/ok` のコメント（上書きを含む）を名指しし、決まったことを蒸し返さず、計画に無い判断が新しく出たときだけ質問するよう指示する。ハーネスの成果物を作るかは、リポジトリのCLAUDE.mdとユーザー層のスキルに任せる | 第3ラウンド Q13 |
| 計画の実行の上限 | `timeout` と `max_turns` は、実装の実行と同じ値を使う | 第3ラウンド Q14 |
| 追加の指示の置き場所 | 端末のローカルのファイル（`~/.config/switchboard/instructions/` の下）。Web表示は `inbox serve` の新しいAPIに頼み、`inbox serve` が書く。エージェントは計画の実行のたびに読む。`config.yaml` とは別のファイルにする。端末ごとの違いはREADMEに書き、同期は利用者に任せる | 第4ラウンド Q15 |
| 指示の単位 | 全体に1つと、プロジェクトごとの両方。全体、プロジェクトの順につなげて渡す | 第4ラウンド Q16 |
| 指示を渡す実行 | 計画の実行だけ。ファイル名を `<plan.md>` にして、実装用を後から足せるようにする | 第4ラウンド Q17 |
| 編集の安全策 | 保存のPOSTは、返答と同じ検査（JSON、`Origin` と `Host`）を通す。大きさの上限は32 KiB。秘密の検査に引っかかれば保存を拒む。保存のたびに `audit.jsonl` に日時、プロジェクト、内容のSHA-256を記録する。以前の版は残さない | 第4ラウンド Q18 |
| 編集の入口 | Web表示のヘッダから「設定」の画面へ行き、全体とプロジェクトごとの指示を編集する。画面にはどの端末のファイルかを出す。CLIにも `switchboard instructions edit [<プロジェクト>]` を足し、`$EDITOR` で編集できるようにする | 第4ラウンド Q19 |
| 追加の指示の渡し方 | 計画の実行のsystem promptで、組み込みの指示のあとに「利用者の追加の指示」の節を作る。ぶつかるときは組み込みを優先すると明記する。ファイルが無いか空なら節を作らない | 第4ラウンド Q20 |
| 計画の実行での権限の拒否 | 拒否があっても、待ちの理由は `plan-questions` / `plan` のままにする。拒否された操作は、コメントの末尾の `<details>` に一覧で出す | 第5ラウンド Q21 |
| 計画のコメントの書き方 | 計画のコメントの末尾に、承認なら `/ok`、直すならそのまま返答、という1行を書く。質問のコメントには、推奨どおりなら `/ok`、変えるなら `/ok q5はB` のように、という1行を書く。どちらもコメントの言語（`comments.language`）で書く | 第5ラウンド Q22 |
| 進める順序 | #22（WebUIのブラッシュアップ）は、grillingなしで書かれたPRなので取り込まず、この変更では考えに入れない。#23（`add-run-progress-comment`）を先にmainへ入れ、この変更の実装はそのあとに始める。設定の画面は、今のmainのWeb表示の上に作る | 第5ラウンド Q23 |
| 成果物を置くブランチ | scratchpadのworktreeで、mainから切った `change/add-plan-first-mode` に書く。元のチェックアウトには触れない | 第5ラウンド Q24 |

## 後回しにしたもの

- 実装の実行に渡す追加の指示（`<implement.md>`）（第4ラウンドQ17）
- 追加の指示を端末をまたいで同期すること（第4ラウンドQ15）
- 追加の指示の以前の版を残すこと（第4ラウンドQ18）
