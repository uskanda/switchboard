# grilling 記録: wait-on-red-base

背景：2026-11-15の12:08〜12:16に、人が受信箱のWeb表示で `gh:uskanda/smarternews` のマージを約15件押した。衝突の無い9件はすぐマージされ、mainに033番のマイグレーションが4つ入って、mainのCIが赤になった（12:08の#271から）。衝突した6件はADR-048の自動マージの依頼になった。衝突を直す実行で赤いmainを取り込み、そのあとのCIが同じテストで落ちた。どのissueも `agent.max_fix_attempts`（2）を使い切って `waiting(reason=ci)` になり、依頼は取り消された。開いている10件のPRが同じ失敗で止まった。

このgrillingでは、エージェントの側（変更A、この変更）と、受信箱のマージの直列化（変更B、`serialize-inbox-merges`）の両方を決めた。Bの成果物は別の変更で作る。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 変更の分け方 | 2つに分ける。A（baseが赤のときの直す実行、エージェント）をこの変更にし、B（受信箱からのマージの直列化、受信箱のサービス）は別の変更 `serialize-inbox-merges` にする。Bの決定もこの記録に残す | 第1ラウンド Q1 |
| 「baseが赤」の判定 | baseのブランチの先頭のコミットのCIに失敗があり、かつPRで失敗したチェックの名前がすべてbaseの先頭でも失敗しているとき。baseのCIが終わっていなければ判定を保留し、次の問い合わせに回す | 第1ラウンド Q2 |
| baseが赤の間のPRの扱い | 直す実行を始めず、回数にも数えない。issueは `agent:done` のまま見張りを続け、baseが緑に戻ったらbaseを取り込んで見張り直す。`waiting` にはしない | 第1ラウンド Q3 |
| baseが赤の間のマージ | Aではマージのダイアログ（ADR-050）にbaseのCIの状態を出すだけにする。押したマージを依頼として持ち、緑に戻ってからマージするのはBで行う | 第1ラウンド Q4 |
| 直列化（B）の方式 | 受信箱のサービスに、プロジェクトごとのマージの順番待ちを持たせる。1件マージしたら、次のPR/MRはbaseを取り込み、そのコミットのCIが緑になってからマージする | 第1ラウンド Q5 |
| baseが緑に戻ったときの取り込み方 | エージェントがworktreeで `git merge origin/<base>` を機械的に実行し、衝突しなければpushする。Claudeは起動しない。pushしたら、`fix=base` のマーカー付きのdoneの投稿を出し直す。衝突したら、衝突を直す実行（ADR-044、回数に数える）に回す | 第2ラウンド Q6 |
| baseを見る頻度と待つ期間 | `poll_interval` ごとに、プロジェクトとbaseの組ごとに1回だけbaseの先頭のCIを読む。待つ期間に上限は設けず、PR/MRがopenでissueが `agent:done` の間は待つ | 第2ラウンド Q7 |
| 待っていることの見せ方 | 待ち始めたときに、issueへ短いコメントを1回だけ書く。マーカーは付けない。監査ログにも記録する。マージのダイアログにbaseのCIの状態を足す。受信箱の一覧のプロジェクト単位の帯はBの側で検討する | 第2ラウンド Q8 |
| すでに `waiting(reason=ci)` のissue | 移行しない。人がmainを直したあと、始めるラベルか返信で数え直す（ADR-041の既存の手順） | 第2ラウンド Q9 |
| 次のPR/MRにbaseを取り込む主体（B） | 受信箱のサービスが、受信箱のトークンでフォージの機能を呼ぶ（GitHubのupdate-branch、GitLabのrebase）。そのコミットの見張りは受信箱のサービスが持つ。取り込みで衝突したら、ADR-048の衝突の経路に戻す | 第2ラウンド Q10 |
| 取り込んだあとのCIが失敗したとき（B） | 依頼を打ち切り、Web表示で知らせる。そのPR/MRを順番から外し、次の依頼へ進む。直すのは人がissueに返信して行う | 第2ラウンド Q11 |
| 直列にする範囲（B） | Web表示で押したマージをすべて、プロジェクトとbaseの組ごとの順番待ちに入れ、押した順に処理する。headがbaseの先頭を含み、CIが緑なら、すぐマージする | 第2ラウンド Q12 |
| baseが赤の間の衝突を直す実行 | baseが緑に戻るまで始めない。戻ったら衝突を直す実行を始める | 第3ラウンド Q13 |
| 順番待ちの置き場所と見せ方（B） | ADR-048の `inbox/automerge.json` の依頼を広げ、理由（`conflict`／`queue`／`base_red`）を持たせる。マージのPOSTは202で順番を返し、詳細のペインに状態と取り消しを出す | 第3ラウンド Q14 |
| 先頭が詰まったとき（B） | 先頭で待つ。取り込んだコミットのCIが6時間終わらなければ、依頼を打ち切って次へ進む | 第3ラウンド Q15 |
| 「CIが緑」の定義（B） | ci-watchの失敗の判定と同じ。全部終わり、`failure` と `timed_out` が1つも無いこと。CIが1つも現れないリポジトリでは10分待ってからマージする | 第3ラウンド Q16 |
| 待ち始めのコメントのマーカー | Q8の「マーカーは付けない」を改める。状態を変えない一時的なマーカー `state=note reason=base` を付ける（画像の添付の `state=attachment` と同じ扱い）。エージェントと信頼するユーザーが同じアカウントのとき（ADR-056）、マーカーの無いコメントは人の返信と見分けられないため | 会話中に確認（Q8の補足） |
