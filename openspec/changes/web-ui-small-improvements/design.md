# Design

## Context

動機はproposal.mdのWhyを参照。7項目のうち、APIに手を入れるのは新規issueの`plan_first`だけで、残りはWeb UIの中で閉じる。決めたことはgrilling.mdに記録してある。

## Goals / Non-Goals

**Goals:**

- 時間の文と進捗の文を、表示する箇所ごとに組み立てず、`lib/api.ts`の関数1つずつにまとめる
- 未保存の指示の扱いを、返答の下書き（`lib/drafts.ts`）と同じ振る舞いにする

**Non-Goals:**

- エージェントがフォージに書く進捗コメントの書式は変えない
- ルーターをデータルーターへ書き換えない。アプリの中で画面を移るときの確認ダイアログは出さない
- 一覧の表の時間の列は変えない。列の見出しが何の時間かを示している

## Decisions

### 時間の文は`timeText(state, since)`にまとめる

状態（running、waiting、queued、done）と時刻を受け、今ある`age`と`elapsed`の結果に「経過」「から待ち」「から順番待ち」「に完了」を付ける。1分未満は、`age`の「1分未満」に「前から待ち」を付けると「1分未満前から待ち」となり読みにくい。そこで「始めて1分未満」「待ちになって1分未満」「順番待ちになって1分未満」「完了して1分未満」と書き分ける。「たった今」系の言い方は、状態が始まった時刻と取り違えやすいので使わない。

### 進捗の文は最初の区切りで切る

`progressText`は、最初の「｜」か「|」より後ろを返す。後ろが空か`?`のとき、区切りが無いとき、進捗が無いときは、どれも`作業しています`にそろえる。区切りが無い行は、目的の文を書く前のエージェントが時刻とツールだけを書いた行とみなす。

### 右のペインの案内は`oldestWaiting`で選ぶ

待ちの項目のうち、`waiting_since`が最も古いものを選ぶ。時刻の無い項目は無限に新しいものとして扱い、最後に回す。カードは一覧のカードと同じ部品の並び（参照、タイトル、理由のバッジ、時間の文）にし、色は理由のバッジだけにする。

### 設定の画面の見出しの大きさ

DESIGN.mdのタイプの段は`headline-md`が最も大きく、節の見出しも`headline-md`だった。段を足すと`tokens.css`の書き出しまで変わるので、段は足さない。画面の見出し「設定」を`headline-md`にし、節の見出しを`body-md`の太字に下げて見分ける。DESIGN.mdも`headline-md`を「画面の見出し」と定めているので、それに合う。

### 未保存の指示は`lib/instructionDrafts.ts`に置く

キーは`kind`と`target`の組。`Field`は、最後に保存した文を状態に持ち、欄の文と違う間を未保存とする。文が変わるたびに下書きを書き、保存済みと同じになれば消す。`beforeunload`は、未保存の`Field`ごとに登録し、未保存でなくなるか画面を離れると外す。`lib/drafts.ts`の拡張にしなかったのは、返答の下書きの型（文と選んだ答え）とキー（issueの参照）が違うためである。

### `plan_first`は項目に足すだけにする

`inboxapi.IssueTarget`に`PlanFirst bool`（`json:"plan_first"`）を足す。`switchboard-web`は型ごと中継するので変えない。Web UIの型では省略可能とし、無ければ補足を出さない。古い受信箱のサービスと組み合わせても、ダイアログは今までどおり使える。

## Risks / Trade-offs

- ［`beforeunload`の確認の文言はブラウザが決める］→ 確認を出すことだけを約束し、文言は約束しない
- ［下書きはメモリだけにあるので、再読み込みで消える］→ 再読み込みの前に`beforeunload`で確かめる。返答の下書きと同じ扱いである
- ［問題の無いプロジェクトの1行からクローンの場所が見えなくなる］→ title属性に持たせ、マウスを乗せれば見える。問題のあるプロジェクトはカードのまま場所を出す
