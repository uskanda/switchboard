# Spec Delta

## MODIFIED Requirements

### Requirement: 同時実行の制限
エージェントは、同じissueについて同時に2つ以上の実行をしてはならない（MUST NOT）。
エージェントは、端末で同時に動かす実行の数を `<agent.max_parallel>` 以下に保たなければならない（MUST）。
`<projects[].max_parallel>` のあるプロジェクトでは、エージェントは、同時に動かす実行の数をその値以下に保たなければならない（MUST）。
スロットが空いたとき、エージェントは、スロットを待つ直す実行を、順番待ちのissueより先に始めなければならない（MUST）。直す実行には、baseとの衝突を直す実行とCIの失敗を直す実行の両方が入る。
`<agent.prefer_plan>` がtrueの間も、スロットが空いたとき、エージェントは、スロットを待つ直す実行を、計画の実行になるissueより先に始めなければならない（MUST）。
スロットを待つ直す実行が複数あるとき、エージェントは、衝突を直す実行をCIの失敗を直す実行より先に始めなければならない（MUST）。同じ種類のあいだでは、スロットを待ち始めた時刻の早い順、時刻が同じならrefの文字列の順にする。
プロジェクトの上限に当たった直す実行は、ほかのプロジェクトの実行が始まるのを妨げてはならない（MUST NOT）。
直す実行のためにスロットを空けようとして、エージェントは、動いている実行を止めてはならない（MUST NOT）。

#### Scenario: 上限に達している
- **WHEN** `<agent.max_parallel>` が1の端末で1つの実行が動いている間に、別のissueに `agent:ready` が付く
- **THEN** 2つ目の実行は、1つ目が終わってから始まる

#### Scenario: プロジェクトの上限に達している
- **WHEN** 全体の上限が3、プロジェクトAの上限が1の端末で、Aの実行が1つ動いている。その間に、Aの別のissueに `agent:ready` が付く
- **THEN** 2つ目のAの実行は、1つ目が終わってから始まる

#### Scenario: プロジェクトの上限を書いていない
- **WHEN** 全体の上限が2の端末で、`<projects[].max_parallel>` の無いプロジェクトAの実行が1つ動いている。その間に、Aの別のissueに `agent:ready` が付く
- **THEN** 2つ目のAの実行はすぐに始まる

#### Scenario: 直す実行が順番待ちより先に始まる
- **WHEN** `<agent.prefer_plan>` がfalseで、`<agent.max_parallel>` が1の端末で1つの実行が動いている。その間に、実装の `#10` が順番待ちに入り、doneの `#12` のPRがbaseと衝突する。そこで動いている実行が終わる
- **THEN** `#10` より先に `#12` の衝突を直す実行が始まり、`#12` に順番待ちのコメントは付かない

#### Scenario: prefer_planがオンでも直す実行が先に始まる
- **WHEN** `<agent.prefer_plan>` がtrueで、`<agent.max_parallel>` が1の端末で1つの実行が動いている。その間に、計画の `#9` が順番待ちに入り、doneの `#12` のPRのCIが失敗する。そこで動いている実行が終わる
- **THEN** `#9` より先に `#12` のCIの失敗を直す実行が始まる

#### Scenario: 衝突がCIの失敗より先に始まる
- **WHEN** `<agent.max_parallel>` が1の端末で1つの実行が動いている間に、doneの `#13` のPRのCIが失敗し、そのあとdoneの `#12` のPRがbaseと衝突する。そこで動いている実行が終わる
- **THEN** `#12` の衝突を直す実行が先に始まる

#### Scenario: プロジェクトの上限に当たった直す実行
- **WHEN** 全体の上限が2、プロジェクトAの上限が1の端末で、Aの実行とプロジェクトBの実行が1つずつ動いている。Aのdoneのissueが衝突を直す実行のスロットを待ち、Bのissueが順番待ちにある。そこでBの実行が終わる
- **THEN** Bの順番待ちのissueの実行が始まり、Aの直す実行はスロットを待ったまま残る
