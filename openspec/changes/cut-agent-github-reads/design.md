# Design

## Context

動機はproposal.mdのWhyにある。ここでは、測った数字と今のコードの経路を書く。

### 測った数字

偽のフォージに、メソッドごとの呼び出しを数える層をかぶせて測った。`max_parallel: 1` で1件が実行中、80件が順番待ちの状態である。GitHubのcoreの回数は、`Thread` を2回（issueとコメント）、ほかを1回として数えた。`Thread` は別にGraphQLを1回使う。

| 場面 | 呼び出し | core |
|---|---|---|
| 80件を順番待ちにした最初のポーリング | `Thread` 84、`LabelActor` 81、`PostComment` 81 ほか | 332 |
| 変化の無いポーリング1回 | `Thread` 80、`LabelActor` 80、`UpdatedIssues` 1 | 241 |
| 変化の無い中継の取り直し1回 | 同上 | 241 |
| 実行が終わり、順番待ちから次を始める | `Thread` 8、`SetLabels` 2、`PostComment` 2 ほか | 22 |

本番の設定では、中継の `hooks` に載っているのはGitLabの2件だけである。`gh:uskanda/smarternews` は `poll_interval: 30s` でポーリングされる。80件を順に読むポーリングは1回に100〜130秒ほどかかるので、ポーリングは間を空けずに続く。1時間に約29回 × 241回で約7000回となり、V63の数字と合う。順番待ちのコメントの投稿と削除、引き継ぎ、`since` の変化によるETagの外れは、合わせても1時間に数100回である。

### 今のコードの経路

- `pollProject` は、一覧のissueの更新の時刻が `seen` より新しいか `unsettled` にあれば、`evaluate` を呼ぶ。キュー待ちで終わったissueは `seen` に入らず、`queued: true` として `unsettled` に残る。そのため、ポーリングと `refresh` のたびに、`evaluate` → `consider` → `decide`（`Thread` と `LabelActor`）→ `launch` → `errQueued` を通る。
- `since` は `unsettled` の時刻より前に保たれるので、順番待ちのissueは毎回の一覧に出る。一覧の要求は1回で、ETagが合えば枠を使わない。
- GitLabの `pollReplies` は、待ちとdoneのissueのノートの数を `notes` と比べる。`notes` は評価が成功したときだけ書かれるので、返答でキュー待ちになったissueも毎回評価し直される。
- エージェントは `forge.RateLimitError` を見ていない。枠が尽きたあとも、ポーリングのたびに読む。

## Goals / Non-Goals

**Goals:**

- 変化の無い順番待ちのissueについて、ポーリングと中継の取り直しでフォージに要求を送らない。80件でも、変化の無いポーリングは一覧の1回だけにする。
- API制限の間は、エージェントがそのフォージのクライアントで読みに行かない。

**Non-Goals:**

- `Thread` と `LabelActor` の条件付きリクエスト（grillingのQ2）。
- 起動したときの順番待ちのコメントの消し方（grillingのQ5）。
- 中継の `hooks` の設定。

## Decisions

### D1: 順番待ちのissueは、一覧の更新の時刻が動いたときだけ評価する

`pollProject` は、`unsettled` にあって `queued` が真のissueを、一覧の `UpdatedAt` が `unsettled` の `at` より後のときだけ評価する。そうでなければ読まずに次へ進む。`queued` が偽のissue（エラーやロック中で終わったもの）は、今までどおり毎回評価する。

キュー待ちのissueを始めるのは、今までどおり `drain` である。`drain` は `consider` で読み直してから始めるので、待っている間にラベルが外れていても、始める前に分かる。

ラベルを外す、closeする、コメントを付けるといった人の操作は、issueの更新の時刻を動かす（コメントはV62で確認）。だから、次のポーリングで評価され、順番待ちから外れる。

`unsettled` の `at` には、`launch` が `pl.issue.UpdatedAt`（`Thread` で読んだ時刻）を、`evaluate` が一覧の `UpdatedAt` を入れる。大きいほうが残る。順番待ちのコメントの投稿は更新の時刻を動かすので、新しく順番待ちになったissueは、次のポーリングで1回だけ評価される。grillingのQ4で受け入れた。その評価では `queued` に記録済みなので、コメントは投稿し直さない。

GitLabの `pollReplies` にも同じ規則を当てる。`evaluate` がキュー待ちで終わったときも、そのときのノートの数を `notes` に書く。返答が増えなければ、そのissueを読み直さない。

他の案は次のとおり。

- 受信箱と同じように読む間隔を段階的に延ばす（ADR-071）。読んだ結果を使わないので、延ばしても無駄が残る。
- `Thread` にETagを付けて安くする。`LabelActor` とGraphQLが残り、1件あたりの要求の数は減らない。

### D2: API制限の状態は、フォージのクライアントごとにメモリに持つ

エージェントに、フォージのクライアント（`forge.Forge` の値）からリセットの時刻への表を持たせる。プロジェクトごとの `Route` が別のトークンを持てるので、フォージの種別ではなくクライアントで分ける。同じトークンの別のクライアントは、それぞれ1回断られたあとで止まる。

`errors.As` でエラーに `*forge.RateLimitError` を見つけたら、そのクライアントのリセットの時刻を記録する。表に無かったときだけ、ログに「API制限に入った、何時まで」を1回残す。次の箇所では、クライアントがリセットの時刻より前なら要求を送らずに飛ばす。

- `pollProject`：そのプロジェクトを飛ばす。`unsettled` と `seen` は変えない。
- `pollProject` の評価のループと `pollReplies`：途中で制限を受けたら、残りのissueを評価しない。評価しなかったissueは `unsettled` にも入れない。`since` が動かないので、次の一覧にまた出る。
- `drain`：そのクライアントのissueは順番待ちのまま残し、ほかのプロジェクトのissueに進む。
- `checkWatches` と `scanWatches`：そのクライアントの監視を飛ばす。
- `startFixes`：そのクライアントの修正の実行を始めない。

リセットの時刻を過ぎたら、最初にクライアントを使う箇所で表から消し、ログに「API制限が明けた」を1回残す。

書き戻しの再試行（`retryWriteBacks`）と、実行中の進捗と書き戻しは止めない。制限の間は失敗し、今の再試行の仕組みで後に回る。grillingのQ3のとおりである。

他の案は次のとおり。

- フォージのクライアントの中で、リセットまで要求を断る。書き戻しまで止まり、エージェントのログに残す場所も分かれる。受信箱はADR-071で呼び出す側に持たせたので、それに合わせる。

### D3: 呼び出しを数える回帰テストを残す

測定に使った、`forge.Forge` を包んでメソッドごとに数える型を、`internal/agent` のテストに残す。80件の順番待ちで、変化の無いポーリングと `refresh` が `Thread` と `LabelActor` を1回も呼ばないことを確かめる。API制限は、偽のフォージに `RateLimitError` を返させて確かめる。

## Risks / Trade-offs

- リスク：ラベルの付け外しでフォージが更新の時刻を動かさないなら、順番待ちのissueからラベルを外したことにポーリングで気づかない。対策：`drain` が始める前に読み直すので、ラベルの無いissueは実行されない。順番待ちのコメントは、順番が来たときに消える。キュー待ちでないissueのラベルの変化を見つけるのも、今は同じ前提による。
- リスク：順番待ちのissueは `since` を止めるので、一覧は毎回その分を返す。対策：一覧の要求は1回で、変化が無ければ304で枠を使わない。100件を超えると2ページ目の要求が増える。
- リスク：API制限の表をクライアントの値で引くので、再読み込みで `Route` を作り直すと制限を忘れる。対策：新しいクライアントが1回断られて、また記録する。要求は1回増えるだけである。
- リスク：制限の間に人が付けた開始ラベルには、リセットまで反応しない。対策：受信箱も同じ時間読めない。リセットの時刻はログに出る。

## Migration Plan

状態はメモリにだけ持つ。設定、状態のファイル、マーカーは変わらない。新しいバイナリで起動し直すと新しい振る舞いになり、戻すときは前のバイナリで起動し直す。直したあと、V63と同じ手順で `gh api rate_limit` を5分ごとに読み、coreの使用数を測ってV64に追記する。
