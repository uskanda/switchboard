## MODIFIED Requirements

### Requirement: 設定の画面
WUIは、ヘッダから開ける設定の画面を持たなければならない（MUST）。
設定の画面は、全体と各プロジェクトの、計画用と実装用の指示の欄を並べ、欄ごとに保存できなければならない（MUST）。
設定の画面は、指示のファイルがどの端末のものかを表示しなければならない（MUST）。
保存の誤り（大きさの上限、秘密らしいもの、受信箱のサービスに届かない）は、どの欄の誤りかが分かる形で画面に示す。
設定の画面は、全体とプロジェクトの許可の節を持たなければならない（MUST）。節の中身は「設定の画面の許可の節」に従う。
設定の画面は、`config.yaml` の `allow_tools_extra` を編集する手段を持ってはならない（MUST NOT）。

#### Scenario: プロジェクトの指示を保存する
- **WHEN** 設定の画面で `gh:uskanda/switchboard` の計画用の欄に指示を書いて保存する
- **THEN** `<inboxapi>` を通して保存され、画面には端末 `ubuntu-a` の指示として保存されたことが示される

#### Scenario: 実装用の指示を保存する
- **WHEN** 設定の画面で `gh:uskanda/switchboard` の実装用の欄に指示を書いて保存する
- **THEN** 実装用の指示として保存され、同じプロジェクトの計画用の欄の内容は変わらない

#### Scenario: トークンを貼り付けた
- **WHEN** 設定の画面で、トークンを含む指示を保存しようとする
- **THEN** 保存されず、その欄に、秘密らしいものを含むと示される

### Requirement: ほかの失敗の理由では再実行のボタンを出さない
理由が `verify`、`push`、`ci` の待ちの間、1件の画面は、「再実行する」のボタンを置いてはならない（MUST NOT）。
理由が `permission` の待ちの間、1件の画面は、許可の操作とは別の「再実行する」のボタンを置いてはならない（MUST NOT）。再実行は「許可して再実行」で行う。

#### Scenario: CIの待ちを開く
- **WHEN** 理由が `ci` の待ちのissueを1件の画面で開く
- **THEN** 画面に「再実行する」のボタンは表示されない

#### Scenario: 出力検査の待ちを開く
- **WHEN** 理由が `verify` の待ちのissueを1件の画面で開く
- **THEN** 画面に「再実行する」のボタンは表示されない

## ADDED Requirements

### Requirement: permissionの待ちの許可の操作
理由が `permission` の待ちの間、1件の画面は、拒否された操作の一覧を出さなければならない（MUST）。コマンドは文字列として出す。
候補のある操作には、候補の規則を選べる欄と、範囲を選ぶ欄を置かなければならない（MUST）。範囲は、このissue、このプロジェクト、全プロジェクトの3つとする。範囲の既定はこのissueとする。候補の規則は保存の前に編集できる。
候補の無い操作には、規則では許可できないことを出し、選べないようにしなければならない（MUST）。
1件の画面は、「許可して再実行」を主のボタン、「許可だけ」を副のボタンとして置かなければならない（MUST）。どちらも、選んだ規則が1つも無い間は押せない。
「許可して再実行」を押したとき、1件の画面は、許可を保存してから、「再実行する」と同じ決まった文を返答のPOSTで1回投稿しなければならない（MUST）。保存に失敗したときは投稿しない。保存のあとに投稿だけが失敗したときは、許可は保存済みであることと、投稿の失敗を出す。
`<inbox.auth>` のある構成で管理者でない人には、一覧だけを出し、選ぶ欄とボタンを出してはならない（MUST NOT）。
文言は、日本語と英語の両方を用意しなければならない（MUST）。

#### Scenario: 許可して再実行
- **WHEN** `git mv a.sql b.sql` が拒否された待ちのissueで、候補 `Bash(git mv *)` を選び、範囲をこのプロジェクトにして「許可して再実行」を押す
- **THEN** プロジェクトの許可に規則が足され、issueに再実行を頼む文が投稿され、「送りました」が表示される

#### Scenario: つないだコマンドだけの拒否
- **WHEN** 拒否された操作が `for f in a b; do git log -- $f; done` だけの待ちのissueを開く
- **THEN** 規則では許可できないことが出て、「許可して再実行」は押せない。返答の欄は今までどおり使える

#### Scenario: 断られた規則
- **WHEN** 候補を `Bash(git *)` に書き換えて「許可だけ」を押す
- **THEN** 保存されず、断った理由がその規則の近くに出る

### Requirement: 設定の画面の許可の節
設定の画面の許可の節は、全体と各プロジェクトの許可の規則を一覧にし、規則ごとに外すボタンを置かなければならない（MUST）。
節は、規則を書いて足す欄を、全体と各プロジェクトに置かなければならない（MUST）。
節は、許可のファイルがどの端末のものかと、その端末のエージェントにだけ渡ることを表示しなければならない（MUST）。
ログインが有効で、ログインした人が管理者でないとき、WUIは、許可の節を出してはならず、許可を読んではならない（MUST NOT）。

#### Scenario: プロジェクトに規則を足す
- **WHEN** 設定の画面で `gh:uskanda/smarternews` の欄に `Bash(git blame *)` を書いて足す
- **THEN** 一覧に `Bash(git blame *)` が加わり、端末 `ubuntu-a` の許可として保存されたことが示される

### Requirement: 1件の画面のissueの許可
1件の画面は、そのissueの許可の規則があるとき、その一覧と、規則ごとの外すボタンを出さなければならない（MUST）。
`<inbox.auth>` のある構成で管理者でない人には、issueの許可を出してはならない（MUST NOT）。

#### Scenario: issueの許可を外す
- **WHEN** issue 217の画面で、issueの許可の `Bash(git ls-tree *)` を外す
- **THEN** 一覧からその規則が消える

### Requirement: 許可のPOSTの検査
許可の追加と削除のPOSTについて、`<switchboard-web>` は、本文がJSONであることを確かめなければならない（MUST）。
同じPOSTについて、`<switchboard-web>` は、`Origin` と `Host` が `<listen>` のアドレスと一致することを確かめなければならない（MUST）。一致しないか、`Origin` が無いときは、保存せずに403を返す。

#### Scenario: 外のWebページから送られる
- **WHEN** 別のオリジンのWebページが、WUIの許可の追加のURLへPOSTを送る
- **THEN** 403が返り、許可のファイルは変わらない
