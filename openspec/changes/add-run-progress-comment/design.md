# Design

## Context

動機はproposal.mdに、判断はgrilling.mdにある。設計の前提になる今の形は、次のとおりである。

- `claudecode.Run` は、`claude -p` の出力を `runs/<run>/stream.jsonl` に書き、終わってから読む。実行の途中では誰も読んでいない
- エージェントは、着手のときにマーカー（`state=running`）付きの着手のコメントを投稿し、ADR-033の重複防止に使う。結果は `writeBack` で、同じ `run` の結果のコメントが無ければ投稿する
- フォージのクライアントは、コメントの投稿と削除はできるが、書き換えはできない
- 受信箱は待ちのissueだけを集める。`latestPost` は、エージェントの投稿のうち `state=running` 以外の最新のものを、待ちの理由の出どころとして使う
- GitLabでは、待ちのissueの `user_notes_count` を記録して、返答を検知する（V22）

## Goals / Non-Goals

**Goals:**

- 実行中のissueについて、1分以内の進み具合が、フォージとWeb表示の両方で分かる
- 進み具合を出すことで、エージェントの判定（重複防止、返答の検知、信頼）が変わらない

**Non-Goals:**

- 止まっていると判断する目安の表示
- Web表示の自動更新

## Decisions

### 1. フォージにコメントの書き換えを足す

`forge.Forge` に `EditComment(ctx, ref, id, body)` を足す。GitHubでは `PATCH /repos/{o}/{r}/issues/comments/{id}` を使う。GitLabでは `PUT /projects/:id/issues/:iid/notes/:note_id` を使う。偽物は、本文と更新の時刻を書き換える。

### 2. 実行の途中で `stream.jsonl` を読む

`claudecode` に `Progress` を足す。`stream.jsonl` を前回読んだ位置から読み、`tool_use` の名前ごとの回数と、最新のassistantのテキストを持つ。ツールの入力と出力は持たない。書きかけの最後の行は、次に読むときまで残す。

エージェントは、`claude -p` を起動したら、実行ごとにゴルーチンを1つ起こす。ゴルーチンは、1分のtickerで `Progress` を読んで行を作る。

```
13:41 7分 Edit 5・Bash 12 ｜ DESIGN.mdのバナーの記述を、実装に合わせて直している
```

目的の1行は、最新のassistantのテキストの1行目を120文字で切る。目的の1行はassistantの文をそのまま使うため、ファイルの名前を含むことがある。進捗のコメントに書かないのは、ツールの入力と出力である。ツールの回数と目的の1行が直前の行と同じなら、行を足さず、書き換えもしない。

### 3. 進捗のコメント

- 最初の行ができたときに投稿する。それまでは投稿しない。1分より早く終わる実行には、進捗のコメントが付かない
- 本文は、見出し、行の並び、マーカー（`state=progress`、同じ `run` と `host`）である。言語は `comments.language` に従う
- 行を作るときに、目的の1行を120文字で切る前の行を `workspace.HasSecret` で調べ、秘密が見つかった行を、その旨の行に置き換える。そのうえで、本文全体を `runs/<run>/progress.md` に書いて `comments.check_command` を通す。検査の失敗は、結果のコメントと同じく記録して投稿は続ける
- 投稿と書き換えの失敗は、監査ログ（`progress.failed`）に残し、実行は止めない
- 書き換えが `ErrNotFound` で失敗したら、誰かがコメントを消したとみなし、同じ本文を投稿し直す

### 4. 削除

`writeBack` が結果のコメントを投稿したあと、そのissueのエージェントの投稿のうち、`state=progress` で、今動いている実行のものでないものを消す。回復の `writeBack` でも同じ処理を通るので、落ちて残った進捗のコメントもここで消える。

GitLabでは、進捗のコメントを消すと `user_notes_count` が減る。エージェントは、消したあとでissueを取り直し、待ちのノートの数を記録する。消す前の数を記録すると、次のポーリングで数が変わったように見えて、返答の無い再評価が起きるためである。

### 5. 判定への影響

- 重複防止（ADR-033）は着手のコメントだけを見るので、変わらない
- `latestPost` は、`state=running` と `state=progress` の両方を飛ばす
- 信頼の判定では、進捗のコメントはエージェントの投稿として扱う。今の判定でも、エージェントの身元の投稿は指示に使わない
- GitHubでコメントを書き換えると、issueの `updated_at` は変わりうる。そのときエージェントは、実行中のissueを1分ごとに評価し直す。実行中のissueは実行の管理で飛ばされるので、問い合わせが1回増えるだけである

### 6. 受信箱

- `inbox.Item` に `State`（`waiting` か `running`）と `Progress`（最新の進捗の1行）を足す。`N`（行番号）は待ちの行にだけ付け、行番号の記録も待ちの行だけにする
- 実行中の行の端末と着手の時刻は、最新の着手のコメント（`state=running`）のマーカーから取る。経過時間は着手の時刻から計る。最新の進捗の1行は、進捗のコメントの最後の行から取る
- GitHubは、1回の検索で待ちと実行中を取る（`label:"agent:waiting","agent:running"`）。この書き方でラベルのORになるかは、実物で確かめる（V28）。ならなければ、検索を2回に分ける
- GitLabは、プロジェクトごとに2回問い合わせる（`labels` はANDのため）
- `Detail` は、実行中のissueでは、`Post` に進捗のコメントの本文を入れる。進捗のコメントがまだ無ければ、着手のコメントの本文を入れる
- CLIの一覧は、待ちの表の下に「実行中」の見出しと表を出す。`--json` の要素は `state` と `progress` を持つ

### 7. `inboxapi` とWeb表示

- `inboxapi.Item` に `state` と `progress` を足す。`Detail` には `state` があるので、それを使う
- Web表示の一覧は、待ちの欄の下に実行中の欄を出す。実行中の行は、待ちの行と同じ組み方で、理由のバッジの代わりに「実行中」の表示を出し、質問の代わりに最新の進捗の1行を出す。色は付けない（`DESIGN.md` の「色は待ちの理由と誤りだけ」に従う）
- 1件の画面は、状態が `running` なら、進捗のコメントの全文を出し、返答の欄の代わりに「実行中のため返答できません」を出す

## Risks / Trade-offs

- ［進捗のコメントは公開リポジトリでも誰でも読める］→ツールの入力と出力は書かない。目的の1行はassistantの文なので、ファイルの名前が出ることは受け入れる（grilling.mdの第4ラウンド）。目的の1行は、切る前に秘密の検査を通し、本文は `check_command` を通す
- ［GitLabでノートを消すと、返答の検知のノートの数がずれる］→消したあとで数を記録する。GitLabの偽物で確かめる
- ［GitHubで書き換えのたびに実行中のissueが評価され直す］→実行中のissueは飛ばされ、問い合わせが1回増えるだけである
- ［1分ごとの書き換えで、Search APIとは別のREST APIの回数が増える］→1つの実行につき1分に1回で、5,000回/時の上限に比べて十分少ない

## Migration Plan

- 古い版のエージェントが残した着手のコメントには、進捗のコメントが無い。受信箱は、その行の進捗を `?` と出す
- 戻すときは、前の版を置き直す。残った進捗のコメントは、手で消す
