# Design

## Context

1件の画面（`web/ui/src/components/IssuePane.tsx`）は、理由が `error` の待ちにだけ「再実行する」を出す。押すと、決まった文 `RETRY_TEXT` を返答のPOSTで送る。エージェントは、`waiting(reason=conflict)` の待ちに信頼済みのコメントが付くと実行を再開し、衝突を直す回数も数え直す。このため、衝突の待ちで決まった文を送れば、衝突を直す実行が始まる。サーバーやエージェントは変えなくてよい。

## Goals / Non-Goals

**Goals:**

- 衝突の待ちでも、`error` と同じ形（主と副のボタン、押せない条件、送っている間の表示）で「再実行する」を使えるようにする

**Non-Goals:**

- サーバー、受信箱のサービス（`inboxapi`）、エージェントの変更
- `ci`、`verify`、`permission`、`push` の待ちに「再実行する」を出すこと

## Decisions

### 理由ごとに送る文を選ぶ

決まった文の定数 `CONFLICT_RETRY_TEXT`（`baseとの衝突を解消して、もう一度pushしてください。`）を足す。理由から送る文を選ぶ小さな関数 `retryTextOf(reason)` を置く。`error` なら `RETRY_TEXT`、`conflict` なら `CONFLICT_RETRY_TEXT` を返す。

`error` と同じ文（`RETRY_TEXT`）を送る案もあった。しかし再開した実行はスレッドを読んで作業を決めるので、「再実行」だけでは最初の作業のやり直しとも読める。衝突の解消を文で頼めば、エージェントにもフォージでスレッドを読む人にも意図が伝わる（grilling.mdのQ1）。システムプロンプトには、baseと衝突したら `git merge origin/<base>` で解消するという規則が既にある。この文はその規則と食い違わない。

### ボタンを出す条件

`retrying` を「理由が `error` か `conflict` で、計画の問いの形でない」に広げる。ボタンの並びと押せない条件は `error` の分岐をそのまま使う。

### `ci` には出さない

`ci` の待ちは、CIの失敗の中身を確かめるか直し方を伝えるのが先なので、今までどおり出さない。衝突は、baseが落ち着いた後なら同じ直し方をもう一度試すだけで解けることが多いので、別の扱いにする（grilling.mdのQ3）。仕様の「ほかの失敗の理由では再実行のボタンを出さない」の対象（`verify`、`permission`、`push`、`ci`）は変えず、`conflict` も加えない。

### 案内の文

`PlanHint` の `conflict` の文を、grilling.mdのQ2で決めた文に差し替える。`error` の案内と同じく2つのボタンの使い分けを示し、回数を数え直すことは今の案内にある情報なので残す。

## Risks / Trade-offs

- 衝突の原因がエージェントでは解けないものだと、押すたびに上限まで直す実行が繰り返される。→ 案内で「返答を送る」による直し方の指示も示す。押すかどうかは人が決める
