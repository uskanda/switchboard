# Spec Delta

## ADDED Requirements

### Requirement: 一覧でのissueの読み方
一覧を作るとき、受信箱のサービスは、issueごとにコメントだけを読まなければならない（MUST）。issueの本文と、本文やコメントを編集した人は、一覧のためには読まない。
GitHubのissueのコメントを読み直すとき、受信箱のサービスは、前回の応答のETagを付けて求めなければならない（MUST）。304が返ったときは、前回のコメントを使う。

#### Scenario: GitHubの87件を読む
- **WHEN** GitHubに開始ラベルか状態ラベルの付いた開いたissueが87件あり、一覧を初めて作る
- **THEN** issueごとのGitHubへの要求は、コメントの読み取りだけで、本文と編集した人の読み取りは無い

#### Scenario: 変化の無いコメントを読み直す
- **WHEN** 前回の読み取りのあとコメントが変わっていないGitHubのissueを、一覧のために読み直す
- **THEN** GitHubは304を返し、一覧の行は前回のコメントから作られる

### Requirement: 一覧での読む頻度
`<inbox.read_mode>` が `adaptive` の間、受信箱のサービスは、一覧の取り直しのたびに検索し、issueのコメントは次の規則で読まなければならない（MUST）。
- 検索の結果で、更新の時刻、人のコメントの数、ラベルのどれかが前回の検索と違うissueは、その取り直しで読む
- 前回の検索に無かったissueは、その取り直しで読む
- 実行中のissueは、取り直しのたびに読む
- 最後に変化を見てから10分以内のissueは、取り直しのたびに読む
- それ以外のissueは、前回読んでから、そのissueの読む間隔がたった取り直しで読む。読む間隔は、10分を過ぎて最初は `<inbox.refresh_interval>` の2倍である。変化の無い読み取りごとに倍へ延ばし、上限は `<inbox.idle_interval>` とする

変化を見たとき、受信箱のサービスは、そのissueの読む間隔を `<inbox.refresh_interval>` に戻し、10分をそこから数え直さなければならない（MUST）。
読まなかったissueの行は、最後に読んだコメントから作らなければならない（MUST）。

#### Scenario: 動きの無いissue
- **WHEN** `<inbox.refresh_interval>` が30秒、`<inbox.idle_interval>` が30分で、検索の結果が1時間変わらない `agent:ready` のissueがある
- **THEN** 最後の変化から10分のあとは、1分、2分、4分、8分、16分の間隔で読み、そのあとは30分ごとに読む

#### Scenario: 動きの無いissueに返答が付く
- **WHEN** 30分ごとに読んでいるGitHubのissueに、人がコメントを付ける
- **THEN** 次の取り直しの検索でコメントの数の変化を見て、そのissueのコメントを読む。そのissueは、そこから10分は取り直しのたびに読まれる

#### Scenario: 実行中のissue
- **WHEN** 検索の結果が20分変わらない、`agent:running` のissueがある
- **THEN** そのissueのコメントは、取り直しのたびに読まれる

#### Scenario: 常に読むモード
- **WHEN** `<inbox.read_mode>` を `always` にした設定で、1時間、検索の結果の変わらないissueを一覧に出す
- **THEN** そのissueのコメントは、取り直しのたびに読まれる

#### Scenario: 受信箱のサービスを起動し直す
- **WHEN** 30分ごとに読んでいたissueがある状態で、受信箱のサービスを起動し直す
- **THEN** 起動のあと最初の取り直しで、そのissueのコメントを読む

### Requirement: 読めなかったissueの行
一覧の取り直しでissueのコメントを読めなかったとき、受信箱のサービスは、そのissueの最後に読めた行を一覧に入れなければならない（MUST）。
フォージの検索が失敗したとき、受信箱のサービスは、そのフォージの最後に読めた一覧の行をすべて一覧に入れなければならない（MUST）。
どちらのときも、一覧の `errors` には、そのフォージを読めなかったことを入れなければならない（MUST）。
受信箱のサービスは、最後に読めた行をメモリにだけ持たなければならない（MUST）。検索が成功して結果に無かったissueの行は捨てる。

#### Scenario: 1件だけ読めない
- **WHEN** GitHubの待ちのissueが3件あり、取り直しでそのうち1件のコメントの読み取りが失敗する
- **THEN** 一覧には3件の行があり、読めなかった1件は前回の内容で出る。`errors` にはGitHubが入る

#### Scenario: 検索が失敗する
- **WHEN** GitHubの行が5件ある一覧を返したあと、次の取り直しでGitHubの検索が失敗する
- **THEN** 一覧には前回のGitHubの5件の行があり、`errors` にはGitHubが入る

#### Scenario: 起動の直後に読めない
- **WHEN** 受信箱のサービスを起動した直後の取り直しで、GitHubの検索が失敗する
- **THEN** 一覧にGitHubの行は無く、`errors` にはGitHubが入る

### Requirement: API制限を受けたフォージ
フォージがAPI制限の応答を返したとき、受信箱のサービスは、その応答が示すリセットの時刻まで、一覧の取り直しでそのフォージに要求を送ってはならない（MUST NOT）。その間の取り直しでは、そのフォージの最後に読めた一覧の行を一覧に入れる。
API制限で待っている間も、受信箱のサービスは、返答、マージ、issueの作成、1件の詳細の要求では、そのフォージに要求を送らなければならない（MUST）。

#### Scenario: 制限を受ける
- **WHEN** 一覧の取り直しで、GitHubが07:49 UTCにリセットされるAPI制限の403を返す
- **THEN** 07:49 UTCまでの取り直しではGitHubに要求を送らず、一覧は前回のGitHubの行を持つ

#### Scenario: 制限中に返答する
- **WHEN** GitHubのAPI制限で一覧の取り直しを待っている間に、GitHubのissueへ返答を送る
- **THEN** 受信箱のサービスはGitHubに返答を投稿しに行く

### Requirement: 一覧の誤りの再開の時刻
API制限で一覧の取り直しを待っているフォージについて、一覧の `errors` の要素は、待ちが終わる時刻を `retry_at` に持たなければならない（MUST）。API制限でない誤りの要素は `retry_at` を持たない。

#### Scenario: 制限中の一覧
- **WHEN** GitHubが07:49 UTCまでのAPI制限を返したあとに、一覧を求める
- **THEN** `errors` のGitHubの要素の `retry_at` は07:49 UTCである

## MODIFIED Requirements

### Requirement: 変化の知らせ
APIは、一覧の変化をSSEで知らせる口を持たなければならない（MUST）。
口につないだとき、APIは、そのときの一覧を最初の知らせとして送らなければならない（MUST）。
口につながっているクライアントがある間、APIは、`<inbox.refresh_interval>` ごとにフォージから一覧を取り直さなければならない（MUST）。API制限で待っているフォージには、待ちが終わるまで要求を送らない。issueごとのコメントを読むかどうかは、「一覧での読む頻度」に従う。
取り直した一覧が前の一覧と違うとき、APIは、新しい一覧を、つながっているすべてのクライアントに送らなければならない（MUST）。
口につながっているクライアントが無い間、APIは、フォージへの間隔ごとの問い合わせをしてはならない（MUST NOT）。
返答を投稿したとき、APIは、間隔を待たずに一覧を取り直して知らせなければならない（MUST）。
APIは、知らせの一覧を、GETの一覧のキャッシュにも使わなければならない（MUST）。

#### Scenario: 待ちが増える
- **WHEN** クライアントが口につながっている間に、別のissueが待ちになる
- **THEN** 次の間隔の取り直しで、そのissueを含む一覧がクライアントに届く

#### Scenario: 誰もつながっていない
- **WHEN** 口につながっているクライアントが無いまま、間隔の3倍の時間がたつ
- **THEN** APIはフォージに問い合わせない

#### Scenario: 一覧が変わらない
- **WHEN** 取り直した一覧が前の一覧と同じである
- **THEN** クライアントには何も届かない

### Requirement: 届かなかったフォージがある一覧のキャッシュ
一覧を取ったときに届かなかったフォージがあれば、APIは、その一覧を返さなければならない（MUST）。その一覧には、「読めなかったissueの行」に従って、最後に読めた行が入る。
APIは、その一覧をGETの一覧のキャッシュにしてはならない（MUST NOT）。

#### Scenario: 届かなかった次の要求
- **WHEN** GitHubに届かなかった一覧を返したあと、60秒以内にもう一度一覧を求める
- **THEN** APIはフォージに問い合わせ直し、GitHubに届けば、誤りを含まない一覧が返る

#### Scenario: API制限中の次の要求
- **WHEN** GitHubのAPI制限で待っている間に返した一覧のあと、60秒以内にもう一度一覧を求める
- **THEN** APIはGitHubに要求を送らず、前回のGitHubの行と、`retry_at` を持つGitHubの誤りを含む一覧が返る
