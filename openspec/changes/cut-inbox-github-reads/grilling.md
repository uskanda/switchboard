# grilling 記録: cut-inbox-github-reads

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 一覧で1件ごとに読む量 | 一覧ではコメントだけを読む。GitHubはETagの条件付きリクエストにし、4件ずつ並べて読む。検索の `updated_at` が同じissueを読まない案は、この時点では検証項目として残した（第3ラウンドで読む頻度の仕組みに取り込んだ）。 | 第1ラウンド Q1 |
| GitLabの扱い（読む量） | GitLabの一覧もコメントだけを読む。条件付きリクエストはGitHubだけにする。 | 第1ラウンド Q2 |
| 読めなかったときの一覧 | 読めなかったissueは、最後に読めた行を出す。検索ごと失敗したら、そのフォージの最後に読めた行をすべて出す。帯は今までどおり出す。欠けた一覧を完全な一覧としてキャッシュしない。 | 第1ラウンド Q3 |
| API制限を受けたあと | リセットの時刻まで、一覧の取り直しではそのフォージを読まない。返答、マージ、1件の詳細などの人の操作は、今までどおり試す。「間隔を延ばしてはならない」の要件に、制限中の例外を足す。 | 第1ラウンド Q4 |
| エージェント側の読み取り | この変更では直さない。直したあとに枠の減り方を測ってから、別の変更で扱う。 | 第1ラウンド Q5 |
| 古い行の見せ方 | 行に印を付けず、上の帯で示す。一覧の要素は変えない。 | 第2ラウンド Q6 |
| 制限中の再開の時刻の出し方 | 一覧の `errors` の要素に `retry_at` を足す。Web表示は端末の時刻で「API制限中、何時に読み直す」と出す。Androidのアプリは変えない。 | 第2ラウンド Q7 |
| 最後に読めた行の保ち方 | 受信箱のサービスのメモリにだけ持ち、期限は設けない。検索が成功して出てこなくなったissueの行は捨てる。CLIの `switchboard inbox` は今までどおり。 | 第2ラウンド Q8 |
| 読む頻度の下げ方 | 段階的に延ばす。最後に変化を見てから10分以内のissueと、実行中のissueは、`refresh_interval` ごとに読む。それを過ぎたら、変化が無いたびに読む間隔を倍にし、`<idle_interval>` で止める。倍にする元は `refresh_interval`。検索の結果に変化が見えたら、すぐ読み、間隔と10分の数え直しを戻す。延ばした間隔はメモリにだけ持ち、再起動したら全件を一度読む。 | 第3ラウンド Q9（利用者の指定で、案Bに案Aの条件を取り込んだ）、会話中に確認 |
| モードの設定 | `<inbox.read_mode>` に `adaptive` か `always` を書く。既定は `adaptive`。`always` は全件を間隔ごとに読む（ETagは使う）。延ばす上限は `<inbox.idle_interval>` で、既定は30分。10分の境は固定。 | 第3ラウンド Q10 |
| GitLabの扱い（読む頻度） | GitLabも同じ仕組みにする。`updated_at`、人のコメントの数、ラベルのどれかが変わったら読む。 | 第3ラウンド Q11 |
| 中継のイベント | 今のまま、イベントは検索をやり直すきっかけとする。読むかどうかは検索の結果の変化で決める。 | 第3ラウンド Q12 |
| 決定の記録と変更の名前 | ADR-071を足す。変更の名前は `cut-inbox-github-reads`。 | 会話中に確認 |

## 後回しにしたもの

- エージェントの読み取りがGitHubの枠をどれだけ使うかの測定と、その削減（第1ラウンドのQ5）。エージェントと受信箱が同じGitHubアカウントのトークンを使っているかは未確認。
- 古い行に印を付けること（第2ラウンドのQ6）。
- Androidのアプリで再開の時刻を出すこと（第2ラウンドのQ7）。
