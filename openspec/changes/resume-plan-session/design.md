# Design

## Context

実物での確認の結果（claude 2.1.316、haiku）は次のとおり。

- `--resume <A> --fork-session --session-id <B>` は、指定した `B` のIDで分岐する。initとresultの `session_id` は `B` になる。
- 再開した実行では、`--tools` と `--json-schema` は新しい値が使われる。`--append-system-prompt-file` は使われず、最初の実行のシステムプロンプトのままになる。
- キャッシュの有効期間は1時間（`ephemeral_1h`）だった。ツールとシステムプロンプトが同じなら、再開した実行は前回の履歴をキャッシュから読んだ。ツールを変えると、キャッシュは読まれなかった。
- 無いセッションを再開すると、claudeは終了コード1で終わり、費用は0だった。
  - resultは `error_during_execution` で、`num_turns` は0だった。
  - `errors` は `No conversation found with session ID: <A>` だった。

エージェントは、実行ごとの `runs/<実行>/` に、`system.md`、`prompt.md`、`settings.json`、`stream.jsonl` を書く。issueごとの記録（`record`）は最後の実行だけを持ち、次の実行で上書きされる。待ちの投稿のマーカーは、端末、実行のID、セッションID、理由、時刻を持つ。

## Goals / Non-Goals

**Goals:**

- 同じ端末で続く計画のラウンドで、前回のセッションから分岐して起動する。
- 前回と今回で規則やコードの状態が違うときは、引き継がない。
- 引き継ぎの失敗で、実行を誤りにしない。

**Non-Goals:**

- 承認のあとの実行と、失敗を直す実行の引き継ぎ。
- 続けて引き継ぐ回数の上限。

## Decisions

### 引き継ぐ元をマーカーから見つける

前回の実行は、issueの最新のエージェントの待ちの投稿のマーカーから見つける。マーカーの端末がこの端末で、理由が `plan-questions` か `plan` のときだけ候補にする。マーカーの時刻は投稿の時刻なので、前回の実行の終わりとして使う。マーカーの実行のIDから、端末の `runs/<実行>/` を読む。

フォージのマーカーを使う理由は、ローカルの `record` が次の実行で上書きされるためである。マーカーは端末をまたいでも同じものが見え、別の端末の投稿を確実に除ける。

### 起動の条件を実行ごとに残す

エージェントは、実行ごとの `runs/<実行>/` に `<launch.json>` を書く。中身は、セッションID、始まりのworktreeのHEAD、渡したツール、モデル、effort、追記する指示のSHA-256とする。次の計画の実行は、今回の値と前回の `<launch.json>` を比べる。前回の `<launch.json>` が無いか読めないときは、引き継がない。

追記する指示を比べるのは、再開では新しい指示が使われないためである。計画用の指示（`plan.md`）、承認の語、言語のどれかを変えると、指示の中身が変わり、引き継がなくなる。ツールとモデルとeffortを比べるのは、ツールを変えるとキャッシュが読まれず、モデルを変えた再開の振る舞いはまだ確かめていないためである。

### claudecodeの引数

`claudecode.Request` に、引き継ぐ元のセッションIDを足す。空でなければ、`Args` は `--session-id` に加えて `--resume <元>` と `--fork-session` を付ける。`claudecode` は、resultが誤りで、ターン数が0で、`errors` に `No conversation found` を含むかを見分ける関数を持つ。CLIの文言に依存する部分を、アダプタに閉じ込めるためである。

### 引き継ぎの失敗と起動し直し

引き継ぎに失敗したとき、エージェントは新しいセッションIDを決め、同じ実行のIDと同じ `runs/<実行>/` で、引き継がずに起動し直す。`stream.jsonl` は上書きされる。進捗のコメントと結果のマーカーには、起動し直したあとのセッションIDを使う。起動し直す前に、`resumed_from` を空にした `run.started` を、同じ実行のIDでもう1行書く。

### プロンプトの先頭の行

`prompt.Input` に、前の段の続きであることを示す項目を足す。立っているとき、`Build` はプロンプトの先頭に「この実行は前の計画のラウンドの続きである。issueの今の内容は次のとおり」という英語の行を書く。続く内容は引き継がない実行と同じである。利用上限からの再開の `Resumed` とは別の項目にする。

### 用語

この変更では、前回のセッションから分岐して起動することを「セッションの引き継ぎ」と書く。仕様の「再開」は、返答や利用上限のあとに実行を始め直すことを指しており、それと区別するためである。CLIのフラグの名前に合わせて、設定の名前は `<agent.resume_within>` とする。

## Risks / Trade-offs

- リスク：前回の履歴に、前回のプロンプトの非信頼のデータが残る。対策：前回のデータもnonce付きの区切りの中にあり、前回の実行と同じ扱いである。今回のプロンプトでは、信頼の判定をやり直す。
- リスク：引き継いだ実行は、前回の履歴のトークンを入力に持つ。1時間を過ぎるとキャッシュが切れ、新しく始めるより高くなることがある。対策：既定の間隔をキャッシュの有効期間に合わせ、`<agent.resume_within>` で変えられるようにする。
- リスク：ラウンドを重ねると履歴が長くなる。対策：CLIの自動の要約に任せ、実ログで長さを見てから上限を考える。
- リスク：transcriptの置き場所と形式はCLIの内部の仕様である（C22）。対策：エージェントはtranscriptを読まない。無いときは、引き継ぎの失敗として起動し直す。

## Migration Plan

更新したバイナリで再起動したあとの計画の実行から適用される。前の版の実行には `<launch.json>` が無いので、更新の直後の最初の計画の実行は引き継がない。戻すときは、`<agent.resume_within>` を0にするか、前のバイナリに戻す。
