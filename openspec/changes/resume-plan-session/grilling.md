# grilling 記録: resume-plan-session

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| セッションを引き継ぐ実行の種類 | 計画の実行から次の計画の実行だけ。再開ではシステムプロンプトを差し替えられないため | 第1ラウンド Q1 |
| 引き継いでよい間隔 | 設定の `<agent.resume_within>` で決める。既定は1時間で、0なら引き継がない | 第1ラウンド Q2 |
| 引き継いでよい条件 | 前回の実行のマーカーがこの端末のもので、計画の実行である。端末に残る前回の `system.md` が今回と同じで、渡すツール、モデル、effortも同じ | 第1ラウンド Q3 |
| 引き継いだ実行のプロンプト | 今と同じプロンプトの全体を渡し、先頭に前の段の続きであることを書く | 第1ラウンド Q4 |
| 引き継ぎに失敗したとき | `No conversation found`（ターン数0の誤り）なら、同じ実行の中で新しいセッションとして起動し直す。コメントは書かない。始まったあとの失敗は、今までどおり実行の誤りにする | 第1ラウンド Q5 |
| 効果の測り方 | 監査ログの `run.started` に、引き継いだ元のセッション（`resumed_from`）を足す | 第1ラウンド Q6 |
| 前回の実行の終わり方 | 質問か計画を投稿して終わった実行だけを引き継ぐ。誤り、時間切れ、ターン数の上限、利用上限で終わった実行は引き継がない | 第2ラウンド Q7 |
| worktreeのHEADが動いたとき | 前回の実行の始まりのHEADを記録し、今回と同じときだけ引き継ぐ | 第2ラウンド Q8 |
| 続けて引き継ぐ回数 | 上限を設けない。間隔の条件とCLIの自動の要約に任せる | 第2ラウンド Q9 |

## 後回しにしたもの

- 承認のあとの実行と、失敗を直す実行の引き継ぎ。システムプロンプトを差し替えられる方法が見つかったら考える。
- 続けて引き継ぐ回数の上限。実ログの数字を見てから決める。
