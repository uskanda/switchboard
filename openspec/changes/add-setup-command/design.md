# Design

## Context

動機はproposal.mdのWhyにある。設計を決める今の状態は次のとおり。

- 実行は `internal/agent/run.go` の `work` が進める。最初に、worktreeの準備（`workspace.Space` の `Prepare`）とClaude Codeの設定の検査をする。そのあとで、スクリーンショットの置き場の準備、プロンプトの組み立て、`claude -p` の起動へ進む。
- 検証コマンドは、`finish` が `Agent` の `shell` で実行する。`shell` は `sh -c` でコマンドを動かし、`timeout` の期限と、プロセスグループごとの停止を持つ。環境変数は `claudecode.Env` が作り、フォージのトークンを含まない。
- 実行のsandboxは `claude -p` のBashにだけかかる（ADR-057）。エージェント自身が動かすコマンドにはかからない。
- 計画の実行のあとの検査は、追跡しているファイルの差分と、無視の対象でない追跡されていないファイルを捨てる。無視の対象のファイル（`node_modules` など）は残す。
- worktreeはissueごとに作られ、実行をまたいで残る。前の実行がcommitしていない差分を残していることがある。

## Goals / Non-Goals

**Goals:**

- 依存の取得が要るプロジェクトで、実行の中のテストを動かせるようにする。
- ADR-057のsandboxの設定（ネットワークを許さない、外で動くのは `git` と検証コマンドだけ）を変えない。

**Non-Goals:**

- `claude -p` が同じ実行の中で依存を足して取得すること（grilling.mdの後回し）。
- ロックファイルの変化の検出や、依存のキャッシュの管理。準備のコマンドとパッケージマネージャーに任せる。
- 回避できた拒否で待ちの理由が `permission` になる問題。

## Decisions

### 準備は `work` の中で、設定の検査のあとに行う

準備のコマンドは、`Prepare` と `CheckClaudeConfig` のあと、プロンプトを組み立てる前に実行する。`CheckClaudeConfig` が失敗する実行では、依存を取得する意味が無いためである。実行には `shell` をそのまま使う。作業ディレクトリはworktree、環境変数は検証コマンドと同じ `claudecode.Env(a.Env, "subscription")` とする。

着手のコメントとラベルの付け替えは、今までどおり `work` の前に済んでいる。準備に時間がかかっても、issueは `agent:running` に見える。

代わりの案は、`Prepare` の中に入れる案である。`workspace` はgitの操作だけを持つパッケージなので、利用者のコマンドの実行は `agent` に置く。

### 失敗は `o.fail` で書き戻す

準備のコマンドが0以外で終わったとき、`o.fail` に新しい文言を渡す。文言は、コマンド、終了の理由、`tail` で切った出力の末尾からなる。`o.fail` は `waiting(reason=error)` を作るので、利用者は設定やネットワークを直してから、返答で実行をやり直せる。

期限を超えたときは、`shell` の文脈が期限切れになる。このときは、期限を超えたことを文言に書く。実行の取り消し（親の文脈の取り消し）のときは、今の `Prepare` の失敗と同じく `nil` を返し、コメントを書かない。この2つは、親の文脈の `Err` が空かどうかで区別する。

文言は `messages.go` に日本語と英語で足す。検証コマンドの失敗の文言（`verifyFailed`）と同じ形にする。

### 準備の前後でgitの状態を比べる

準備のコマンドが0で終わったあと、worktreeのgitの状態が準備の前と同じかを確かめる。比べるのは次の2つである。

- `git status --porcelain --untracked-files=all` の出力
- `git diff HEAD` の出力のハッシュ

1つ目だけでは、前の実行が残した差分のあるファイルを準備のコマンドがさらに書き換えた場合を検出できない。そのため2つ目も比べる。どちらかが変わっていたら、準備の失敗として `o.fail` に渡す。文言には、準備のあとの `status` にあって準備の前の `status` に無い行のパスを書く。パスが1つも無いとき（内容だけが変わったとき）は、追跡しているファイルの内容が変わったことだけを書く。

この確認は `workspace.Space` のメソッドにする。gitの呼び出しを `workspace` にまとめるためである。

変更は捨てない。利用者が `git status` で原因を見られるようにするためである。次の実行でも同じ失敗になるので、利用者は準備のコマンドか `.gitignore` を直す。

### 記録

- 監査ログの `<setup.ran>` は、準備のコマンドが終わるたびに1行書く。欄は `issue`、`run`、`command`、`ms`、`ok` とする。gitの状態が変わって失敗にした場合は `ok` を偽にし、`reason` に `changed` を入れる。0以外の終了は `exit`、期限切れは `timeout` を入れる。取り消しのときは書かない。
- 出力の全体は、実行のディレクトリ（`runDir`）の `<setup.log>` に、権限 `0600` で書く。実行のディレクトリは、今の保持の期間で消える。

### 追記する指示

`internal/prompt` に、準備のコマンドの節を足す関数を作る。sandboxの節（`WithSandbox`）の直後に足す。節は英語で、次の内容を書く。

- 依存は、実行の前にエージェントが準備のコマンド（文字列を示す）で用意した。
- sandboxの中からは依存を取得できないので、入れ直しを試みない。
- 依存が足りないときは、足りないものを報告して待ちで終える。

準備のコマンドが無いプロジェクトでは節を足さない。計画の実行の引き継ぎ（ADR-058）は、追記する指示のSHA-256が同じことを条件にする。準備のコマンドを足したあとの最初の計画の実行は、指示が変わるので引き継がない。これは今の規則どおりの動きである。

### sandboxの設定は変えない

`settings` と `baseAllow` に準備のコマンドを渡さない。`excludedCommands` と許可の規則は今のままである。

### 設定

`config.Project` に `SetupCommand`（`yaml:"setup_command"`）を足す。検査は足さない。空の文字列は、項目が無いのと同じに扱う。`projects` の読み直しは、プロジェクトの値を丸ごと入れ替えるので、新しい項目もそのまま反映される。

### ADR

ADR-070として、次を `docs/DECISIONS.md` に足す。

- 決定：依存の取得は、プロジェクトの準備のコマンドを、エージェントが `claude -p` の起動の前にsandboxの外で実行して行う。
- 決定：準備のコマンドの環境は検証コマンドと同じにし、`claude -p` には実行させない。
- 理由：ADR-057のsandboxを変えずに、依存の要るプロジェクトでテストを動かすため。準備のコマンドが実行するのは、基点のブランチとエージェントのcommitの内容であり、検証コマンドが今実行しているものと同じである。

## Risks / Trade-offs

- リスク：準備のコマンドは、ブランチの `package.json` のスクリプトなどを、sandboxの外でネットワークに出られる状態で実行する。対策：ブランチの中身は、基点のブランチとエージェント自身のcommitである。検証コマンドは今も同じものを同じ環境で実行している。フォージのトークンは渡さない。`docs/SECURITY.md` に、準備のコマンドがsandboxの外で動くことを書く。
- リスク：前の実行でClaudeが `package.json` を書き換えてcommitすると、次の実行の準備で、そのスクリプトがsandboxの外で動く。対策：検証コマンドにも同じ性質がある。`docs/SECURITY.md` に、依存の定義を変えるPRを人が確かめることを書く。
- リスク：実行のたびに準備のコマンドが走り、実行の開始が遅れる。対策：`docs/GUIDE.md` で、ロックファイルを書き換えず、依存が最新のときにすぐ終わるコマンドを勧める。例は `pnpm install --frozen-lockfile` と `go mod download` である。
- リスク：準備のコマンドの出力が無視の対象でないプロジェクトでは、すべての実行が失敗する。対策：失敗のコメントにパスを書く。`docs/GUIDE.md` に、出力を `.gitignore` に入れることを書く。
- リスク：`max_parallel` が2以上のプロジェクトで、複数のworktreeの準備が同時に走り、パッケージマネージャーの共有のストアを同時に書く。対策：pnpmとGoのモジュールのキャッシュは、同時の書き込みに対応している。ほかのパッケージマネージャーで問題が出たら、そのときに扱う。

## Migration Plan

更新したバイナリで再起動しても、`setup_command` を書かないプロジェクトの動きは変わらない。使うプロジェクトは、`config.yaml` に `setup_command` を足す。エージェントは `projects` の読み直しで反映する。戻すときは、項目を消す。前のバイナリは `setup_command` を未知のキーとして拒むので、バイナリを戻すときは先に項目を消す。
