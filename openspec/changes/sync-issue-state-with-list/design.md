# Design

## Context

動機はproposal.mdのWhyを参照。一覧と1件の状態は、どちらもフォージのラベルとエージェントのコメントから決まる。食い違いは読んだ時刻の差から生まれる。一覧は既定で30秒ごとに読み直し、GitHubでは検索APIを使うので遅れることがある。1件は開いたときにissueを直接読む。決めたことはgrilling.mdに記録してある。

## Goals / Non-Goals

**Goals:**

- 正しい状態の出どころを、サービスの一覧ひとつのままにする
- 一覧が追いつくまでの短いあいだ、1件の側が新しいと利用者に示す

**Non-Goals:**

- ブラウザで一覧の行に1件の状態を重ねない。行のほかの項目が古いまま残り、半端な表示になる
- APIの形を変えない

## Decisions

### サービスは1件を読んだあとに一覧と比べる

`Server.issue`で詳細を読んだあと、`subMu`の下で`s.last`（最後に配った一覧）から同じrefの行を探す。詳細の状態は`listState`で4つと「載らない」に分ける。`State`が`running`なら実行中、`queued`なら順番待ち、`Done`なら完了、`Waiting`なら待ち、どれでもなければ載らない。UIの`IssuePane`と同じ順で分ける。食い違えば`readAgain()`を呼ぶ。

`readAgain()`は通知を1つの枠にまとめ、`fetch`は1回ずつ順に走る。何度呼ばれてもフォージへの問い合わせは急に増えない。一覧が変わらなければ`publish`は何も送らないので、ブラウザの1件の読み直しが繰り返されることもない。`s.last`が無いときは、読み直しのループも動いていないので何もしない。

### UIは純粋な関数で比べる

`lib/api.ts`に`itemState(item)`と`detailState(detail)`、それを比べる`stateDiffers(item, detail)`を置く。一覧の側は`isRunning`、`isQueued`、`isDone`で分け、残りを待ちとする。1件の側は`IssuePane`の`running`、`queued`、`finished`と同じ判定で、どれでもなければ待ちとする。`IssuePane`はこの結果と`fresh`、`reading`、`item`の有無で知らせを出す。

一覧に行が無いissueには、今の「待ちでも実行中でもなくなりました」の文がすでにあるので、知らせは出さない。一覧が追いつくと行の`watchKey`が変わり、1件も読み直される。そのあいだは「更新を取得中」が出て、読み終われば比較が一致して知らせは出ない。

## Risks / Trade-offs

- GitHubの検索の遅れが残っているあいだは、読み直しても一覧が古いままのことがある → 次の定期の読み直しまで、1件の側の知らせで補う
