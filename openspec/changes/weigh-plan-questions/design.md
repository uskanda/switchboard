# Design

## Context

#190で、計画の実行の宣言の質問は、題、本文、選択肢の文、推奨のラベル、理由、任意の図を持つようになった。宣言の形は `internal/agent/planrun.go` にある。`planQuestions` は、宣言の順に番号を振って各質問を書き、質問の間を `---` で区切る。質問のコメントの見出しは `### 計画についての質問` で、マーカーの `q=` は最後の問いの番号を持つ。

Web表示では、`parsePlanQuestions` が最新の質問のコメントを問いに分け、`PlanQuestions` が問いを1枚ずつカードに描く。答えの状態は `IssuePane` が持ち、`QuestionChips` は送る文の上に問いごとのチップを並べる。チップを押すと、カードの位置までスクロールし、カードの題にフォーカスを移す。

計画の実行への指示（`internal/prompt/prompt.go` の `planSystem`）は、本文に「判断に要る事実」を書かせ、`summary` を「1〜2文」に制限している。動機はproposal.mdの「Why」を参照する。

## Goals / Non-Goals

**Goals:**

- 確認だけの問いの印を宣言で受け、フォージのコメントの上でも、Web表示の上でも、判断が要る問いと分けて見せる
- 見出しの無い前の形のコメントは、今までどおり読める
- 範囲の問いを先に聞くことと、問いの書き方は、プロンプトの指示だけで行う

**Non-Goals:**

- 本文の長さや書き方、範囲の問いの有無を、switchboardが検査すること（grilling第1ラウンドQ3、Q4）
- 1ラウンドの問いの数の上限（第3ラウンドQ12）と、効果を測る新しい記録（第3ラウンドQ13）
- CLIの `switchboard inbox` と `switchboard reply` の表示の変更。コメントの文をそのまま出すので、見出しもそのまま出る

## Decisions

### 宣言のスキーマ

質問の項目に、必須の `weight`（`"enum":["decision","check"]`）を足す。`PlanQuestion` に `Weight` を足し、`questionProblem` でも、値が2つのどちらでもない質問を誤りにする。Claude Codeがスキーマを守らなかったときにも、`waiting(reason=error)` になる。ほかの案として、省略できる `check: true` と、配列を2つに分ける形があった。省略できる形は印が付かないまま今と同じ表示になりやすく、配列を分ける形は宣言の順を失うので採らない（第2ラウンドQ5）。

### コメントの並べ方と見出し

`planQuestions` は、宣言の質問を、重みが `decision` のものと `check` のものに分ける。それぞれの中では宣言の順を保ち、`decision` を先に並べてから番号を振る。マーカーの `q=` は、今までどおり最後の問いの番号になる。

`check` の質問があるときは、`decision` の質問の後へ、区切りの `---` と見出しの行を置く。見出しは `#### 推奨でよいか確認してほしい問い`（英語は `#### Please check the recommended answers`）である。その後に `check` の質問を `---` で区切って書く。コメントの見出しが `###` なので、確認だけの問いの見出しは1段下の `####` とする。文言は `messages.go` に日本語と英語で足す。

確認だけの問いしかない宣言も、そのまま投稿する。最初の問いの前に見出しが来る。問いがすべて確認だけのときに計画を出させるのは、プロンプトの指示である（第2ラウンドQ9）。指示に従わなかった宣言を誤りにすると、実行のやり直しに時間と費用がかかる。書き方の決まりを検査しない第1ラウンドQ4と同じ考え方で、誤りにはしない。

### 計画の実行への指示

`planSystem` の「What to do」に、次の2つを足す。

- 範囲の問い：答えがほかの問いの選択肢を変える問い（範囲や方向を決める問い）があれば、そのラウンドではその問いだけを聞く。残りの問いは、その答えを待つ
- 重み：推奨の答えがissue、コード、既存の決まりから導けて、ほかの選択肢を選ぶ理由が見当たらない問いは `check`、それ以外は `decision` とする。聞く問いがすべて `check` なら問いを出さず、計画を出す。その答えは、計画の拠って立つ決定に書く

「How to end the run」の質問の項目を、次のように直す。

- `body`：問いを1文で書き、判断に要る事実を3つまでの短い箇条書きで続ける。調べた根拠（読んだファイルや文書）は書かない
- `weight`：上の基準で `decision` か `check`
- `summary`：調べたものと、問いの事実の根拠を書く。「1〜2文」の制限は外す
- コードの名前（関数、ファイル、項目）は、初めて出たところで括弧の中で説明する

「Diagrams」には、範囲や方向を決める問いでは、何が含まれて何が外れるかを図で示すとよい、という1行を足す（第4ラウンドQ14）。`planSkip`（計画の段階を省いてよい実行）には、確認だけの事項は省く理由にならず、それだけが残るときは `implement` でなく `plan` で終えるよう足す。

仕様の「計画の実行の指示」は、#190の後も「選択肢にラベルを付けて書く」という指示を求めたままで、プロンプトと食い違っていた。#190の変更では、この要件を直していなかった。この変更の差分で、ラベルはswitchboardが振るという内容に直す。

### Web表示での読み取り

`parsePlanQuestions` は、コメントを問いへ分ける前に、行全体が `#### 推奨でよいか確認してほしい問い` か `#### Please check the recommended answers` の行を探す。コメントの言語はエージェントの設定で決まり、画面の言語とは別なので、両方の文言を読む。見つかったときは、その行より後で始まる問いの `Question` に `check: true` を付ける。見出しの行と、その直前の区切りの `---` は、手前の問いの部分から除く。見出しが無いコメントでは、どの問いにも `check` は付かない。

### Web表示での描き方

`PlanQuestions` は、`check` の無い問いを今のカードで描く。カードの題の前の位置（`Q5 1/4`）の問いの数には、確認だけの問いも数える。

確認だけの問いは、カードの後の節に描く。節の見出しは `h3` で、`推奨でよいか確認してほしい問い（3件）` とし、チップから移れるように `tabIndex={-1}` を付ける。行は `<details>` と `<summary>` で作る。`<summary>` には、`Q7 題 — B：選択肢の文` と、推奨どおりでないときの状態の語を出す。開閉、キーボードでの操作、開いているかどうかの伝達は、要素が受け持つ。開いた中には、今のカードの中身（本文、図、選択肢、推奨の理由、補足の欄）を、題の行と位置を除いて描く。

`<details>` を閉じても中身は描いたまま残るので、閉じても選んだ答えは消えない。行には、選んでいる選択肢を出す。開いた直後は推奨の選択肢で、第3ラウンドQ10の形になる。選び直したあとも、送る答えと行の表示が食い違わない。

ほかの案として、開閉の状態を `IssuePane` で持つ形があった。チップから開くために状態を持ち上げる必要があるが、`<details>` の要素の `open` を直接立てれば足りる。このため、状態は持ち上げない。

### チップ

`QuestionChips` は、判断が要る問いのチップを今までどおり並べる。確認だけの問いのうち、状態が推奨どおりで補足の無い問いは、1つのチップ `推奨どおり 3件` にまとめる。それ以外の確認だけの問いは、問いごとのチップにする。まとめたチップは、問いごとのチップの後に置く。まとめたチップの件数が0のときは出さない。

確認だけの問いのチップを押すと、その行の `<details>` を開き、行をスクロールして `<summary>` にフォーカスを移す。まとめたチップを押すと、節の見出しへ移る。

### PRODUCT.mdとADR

原則3に、確認だけの問いの例外を足す。「確認だけの問いは、題と選んでいる答えを1行で出し、全文は行を開いて読める形でよい」とする。この例外を、ADR-067として `docs/DECISIONS.md` に書く。

## Risks / Trade-offs

- エージェントが、判断の要る問いを `check` にする → 所有者は、推奨どおりの答えを、開かずに送ってしまうことがある。行に題と答えの文を出し、開かなくても何が決まるかを読めるようにする。運用の後、推奨と違う答えになった確認だけの問いの割合を、コメントから数え直す
- 範囲の問いを先に聞くと、ラウンドが1回増える → 増えるのは、答えがほかの問いの選択肢を変えるときだけである。指示はその条件で書く
- 仕様の差分が、まだarchiveしていない変更の要件を書き換える → この差分の「問いのカード」と「問いの状態のチップ」は、`plan-question-cards` で決まった内容を含む。「計画の実行の終了の宣言」と「質問のコメント」は、`structured-plan-questions` で決まった内容を含む。archiveは、`plan-question-cards`、`structured-plan-questions`、`weigh-plan-questions` の順に行う
- このPRは別のPRの上に積む → このブランチは `structured-plan-questions`（#195）から切る。#195がmainへマージされたら、このPRのbaseをmainへ付け替えてからマージする
