# Design

## Context

動機はproposal.mdのWhyを参照。受信箱の一覧の質問の冒頭（`inbox.Excerpt`）と待ちの通知は、どちらも`agent.Question`でコメントから段落を1つ拾う。`agent.Question`は、質問のラベルが無ければ、見出しの次の最初の段落を返す。ただし、`**`で始まり`**`で終わる段落（「**What was done**」のような小見出し）は飛ばす。Web UIの一覧（`InboxList.tsx`の`plainText`）は、その文から`**`と`` ` ``を除いて出す。決めたことはgrilling.mdに記録してある。

## Goals / Non-Goals

**Goals:**

- 計画の題を、コメント、受信箱の一覧、待ちの通知で同じ仕組みで出す
- 受信箱とWeb UIのコードは変えない

**Non-Goals:**

- この変更の前に書かれたコメントから題を推し量ること。古いコメントは今までの抜粋のまま出す
- 通知の本文から`**`を除くこと。ほかの待ちの抜粋と同じ扱いのままにする

## Decisions

### 題の段落は`**計画：** 〈題〉`にする

段落は`**`で始まるが`**`では終わらないので、`agent.Question`の小見出しの飛ばしに当たらず、そのまま拾われる。題は`strings.Fields`で1行にまとめる。ラベルはコメントの言語の`texts`に`planLabel`として持たせる（日本語は`計画：`、英語は`Plan:`）。

### 題が無い宣言は異常として扱う

スキーマの`required`に`title`を足すので、StructuredOutputは題を欠かない。それでも`planDeclaration`で空白だけの題を確かめ、「the structured output has no title」として`waiting(reason=error)`にする。ほかの欄（計画の本文、質問の題など）と同じ扱いである。

### 質問の待ちの通知で最初の問いを抜き出す処理をやめる

これまで、`plan-questions`の通知は、要約ではなく最初の問いを引くために、本文を最初の`❓`から切っていた。題の段落は要約より前、つまり`❓`より前にあるので、この処理が残ると題が通知に載らない。計画の承認で決めた「通知も題を出す」に合わせ、この処理を外す。新しいコメントは必ず題を持つので、通知が要約を引くことはない。

## Risks / Trade-offs

- 計画の実行が、issueの題をそのまま繰り返す題を返すことがある → 計画の実行への指示で、issueの題を繰り返さないよう書く
- 長い題は一覧で72字、通知で300字に切られる → 指示で目安を40字以内とする
