# Spec Delta

## ADDED Requirements

### Requirement: アプリの登録
APIは、FCMのトークンを受けて、通知の宛先に登録しなければならない（MUST）。登録は状態のディレクトリのファイルに残し、再起動しても消えない。
同じトークンを登録し直したとき、APIは、宛先を増やさずに登録の時刻だけを新しくしなければならない（MUST）。
宛先が10を超えるとき、APIは、登録の時刻の最も古い宛先を消さなければならない（MUST）。
空のトークンと4096バイトを超えるトークンを、APIは拒まなければならない（MUST）。

#### Scenario: 登録し直す
- **WHEN** 登録済みのトークンを、もう一度登録する
- **THEN** 宛先の数は変わらない

#### Scenario: 11台目
- **WHEN** 宛先が10ある状態で、別のトークンを登録する
- **THEN** 最も古い宛先が消え、新しいトークンが入る

### Requirement: 計画の承認
APIは、issueの参照と、通知に載せた待ちの開始時刻を受けて、そのissueに承認の語（`<plan.approve_word>`）を受信箱のトークンで投稿しなければならない（MUST）。
APIは、投稿の前に、issueを取り直して次の全部を確かめなければならない（MUST）。

- issueがopenで、`agent:waiting` が付いている
- エージェントの最新の待ちの投稿の理由が `plan` である
- その投稿の待ちの開始時刻が、受けた時刻と一致する

どれかに当たらないとき、APIは投稿してはならず、`stale` の誤りを返さなければならない（MUST NOT）。
APIは、承認の語のほかの文を、この口で投稿してはならない（MUST NOT）。

#### Scenario: 承認する
- **WHEN** 理由 `plan` で待つ `o/r#12` を、通知の開始時刻とともに承認する
- **THEN** issueに `/ok` のコメントが付く

#### Scenario: 計画が出し直されていた
- **WHEN** 新しい計画が投稿されたあとで、古い開始時刻で承認する
- **THEN** コメントは付かず、`stale` が返る

#### Scenario: 質問の待ち
- **WHEN** 理由 `question` で待つissueを承認する
- **THEN** コメントは付かず、`stale` が返る

## MODIFIED Requirements

### Requirement: 変化の知らせ
APIは、一覧の変化をSSEで知らせる口を持たなければならない（MUST）。
口につないだとき、APIは、そのときの一覧を最初の知らせとして送らなければならない（MUST）。
口につながっているクライアントがある間、APIは、`<inbox.refresh_interval>` ごとにフォージから一覧を取り直さなければならない（MUST）。
`<inbox.notify.fcm>` があるとき、APIは、クライアントの有無にかかわらず、`<inbox.refresh_interval>` ごとに一覧を取り直さなければならない（MUST）。
取り直した一覧が前の一覧と違うとき、APIは、新しい一覧を、つながっているすべてのクライアントに送らなければならない（MUST）。
`<inbox.notify.fcm>` が無く、口につながっているクライアントが無い間、APIは、フォージへの間隔ごとの問い合わせをしてはならない（MUST NOT）。
返答を投稿したとき、APIは、間隔を待たずに一覧を取り直して知らせなければならない（MUST）。
APIは、知らせの一覧を、GETの一覧のキャッシュにも使わなければならない（MUST）。

#### Scenario: 待ちが増える
- **WHEN** クライアントが口につながっている間に、別のissueが待ちになる
- **THEN** 次の間隔の取り直しで、そのissueを含む一覧がクライアントに届く

#### Scenario: 誰もつながっていない
- **WHEN** `<inbox.notify.fcm>` が無く、口につながっているクライアントが無いまま、間隔の3倍の時間がたつ
- **THEN** APIはフォージに問い合わせない

#### Scenario: 通知のために取り直す
- **WHEN** `<inbox.notify.fcm>` があり、口につながっているクライアントが無いまま、間隔の3倍の時間がたつ
- **THEN** APIはフォージから一覧を3回取り直す

#### Scenario: 一覧が変わらない
- **WHEN** 取り直した一覧が前の一覧と同じである
- **THEN** クライアントには何も届かない

### Requirement: 中継のイベントによる取り直し
`<inbox.relay>` があるとき、`switchboard inbox serve` は、動いている間ずっと中継の配信口につながなければならない（MUST）。つないだときと切れたときは、ログに残す。
画面が `/v1/events` でつないでいる間に中継のイベントが届いたとき、受信箱のサービスは、`<inbox.refresh_interval>` を待たずに一覧を取り直さなければならない（MUST）。
`<inbox.notify.fcm>` があるときは、画面がつないでいなくても、中継のイベントで同じく一覧を取り直さなければならない（MUST）。最初のイベントから2秒の間に届いたイベントは、1回の取り直しにまとめる。前回の取得から10秒たつまでは取り直さない。
`<inbox.notify.fcm>` が無く画面もつないでいないとき、中継のイベントが届いたら、受信箱のサービスはフォージを読まずに一覧のキャッシュを捨てなければならない（MUST）。
中継につないでいる間も、受信箱のサービスは、`<inbox.refresh_interval>` ごとの取り直しを延ばしてはならない（MUST NOT）。

#### Scenario: イベントが続けて届く
- **WHEN** 画面を開いている間、中継からイベントが1秒のうちに3つ届く
- **THEN** 一覧の取り直しは1回だけで、変化は間隔を待たずに画面へ出る

#### Scenario: 画面が無いときにイベントが届く
- **WHEN** `<inbox.notify.fcm>` が無く、画面を閉じている間に中継からイベントが届き、そのあとで画面を開く
- **THEN** 画面を開いたときに、キャッシュを使わずにフォージから一覧を取り直す

#### Scenario: 通知のためにイベントで取り直す
- **WHEN** `<inbox.notify.fcm>` があり、画面を閉じている間に、issueが待ちになった中継のイベントが届く
- **THEN** 間隔を待たずに一覧を取り直し、アプリに通知が届く
