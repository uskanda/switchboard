# Spec Delta

## Purpose

受信箱のサービスが、一覧の変化を見て、登録したアプリへFCMでプッシュ通知を送る。エージェントが送るTelegramの通知とは別の経路で、両方を併用できる。

## ADDED Requirements

### Requirement: 送る条件
`<inbox.notify.fcm>` があるとき、受信箱のサービスは、一覧を取り直すたびに、前に送った記録と比べて通知を送らなければならない（MUST）。
送るのは、次のどれかに当たるissueだけとする。

- 待ちか完了の状態で、記録に無い
- 記録と状態が違う（待ちと完了の間で変わった）
- 待ちの状態で、記録と待ちの理由か待ちの開始時刻が違う

実行中と順番待ちのissueについて、受信箱のサービスは通知を送ってはならない（MUST NOT）。

#### Scenario: 新しく待ちになる
- **WHEN** 一覧を取り直すと、`o/r#12` が理由 `question` の待ちとして初めて現れる
- **THEN** 登録したアプリに1通届く

#### Scenario: 変わらない
- **WHEN** 待ちの `o/r#12` が、次の取り直しでも同じ理由と開始時刻で一覧にある
- **THEN** 通知は送られない

#### Scenario: 計画が出し直される
- **WHEN** 理由 `plan` の待ちの `o/r#12` に、新しい計画が投稿されて待ちの開始時刻が変わる
- **THEN** 新しい開始時刻の通知が1通届く

### Requirement: 起動して最初の一覧
受信箱のサービスが起動して最初の一覧を取ったとき、受信箱のサービスは、記録に無いissueを記録だけし、通知を送ってはならない（MUST NOT）。

#### Scenario: 再起動する
- **WHEN** 待ちのissueが3つある状態で、受信箱のサービスを再起動する
- **THEN** 通知は1通も送られない

### Requirement: 送った記録
受信箱のサービスは、通知を送った記録（issueの参照、状態、待ちの理由、待ちの開始時刻）を、状態のディレクトリのファイルに残さなければならない（MUST）。
一覧から消えたissueの記録は、受信箱のサービスが消さなければならない（MUST）。

#### Scenario: 閉じたissue
- **WHEN** 完了の `o/r#12` が閉じられ、一覧から消える
- **THEN** `o/r#12` の記録が消え、同じissueが開き直されて待ちになれば、また通知が届く

### Requirement: 載せる内容
通知は、issueの参照、状態（待ちか完了）、待ちの理由、issueのタイトル、待ちの開始時刻を載せなければならない（MUST）。完了の通知は、PR/MRの番号とコミットも載せる。
通知は、質問、計画、進捗、コメントの本文を載せてはならない（MUST NOT）。

#### Scenario: 質問の待ち
- **WHEN** 質問を残して待ちになった `o/r#12` の通知を送る
- **THEN** 通知には参照、理由 `question`、タイトルが載り、質問の文は載らない

### Requirement: 通知のボタン
待ちの理由が `plan` の通知は、「承認」のボタンを持たなければならない（MUST）。
PR/MRの番号とコミットのある完了の通知は、「マージ」のボタンを持たなければならない（MUST）。
ほかの通知は、ボタンを持ってはならない（MUST NOT）。

#### Scenario: 計画の質問
- **WHEN** 理由 `plan-questions` の待ちの通知を送る
- **THEN** 通知にボタンは無い

#### Scenario: 古い完了
- **WHEN** マーカーにPR/MRの番号の無い完了の通知を送る
- **THEN** 通知に「マージ」のボタンは無い

### Requirement: 送れなかったとき
通知が失敗したとき、受信箱のサービスは、一覧、詳細、返答の処理を止めてはならない（MUST NOT）。
そのとき、受信箱のサービスは、監査ログに `<push.failed>` を、issue、理由とともに残さなければならない（MUST）。
FCMがトークンを無効と答えたとき、受信箱のサービスは、そのトークンを登録から消さなければならない（MUST）。
1回の送信は、10秒で打ち切る。

#### Scenario: 無効なトークン
- **WHEN** アプリを消した端末のトークンへ送り、FCMが `UNREGISTERED` と答える
- **THEN** そのトークンが登録から消え、ほかのトークンへの送信は続く

### Requirement: 資格情報の扱い
受信箱のサービスは、FCMのサービスアカウントの鍵を `secret.Resolver` で読まなければならない（MUST）。鍵の名前は `<inbox.notify.fcm>` の `credentials_ref` に書く。
受信箱のサービスは、鍵、アクセストークン、FCMのトークンを、ログ、監査ログ、誤りの文に出してはならない（MUST NOT）。

#### Scenario: 鍵を読めない
- **WHEN** `credentials_ref` の秘密が無い状態で受信箱のサービスを起動する
- **THEN** 起動は失敗し、誤りには `credentials_ref` の名前が示され、鍵の内容は出ない

### Requirement: Telegramとの併用
受信箱のサービスのFCMの通知は、エージェントのTelegramの通知と独立して動かなければならない（MUST）。
`<inbox.notify.fcm>` が無いとき、受信箱のサービスは通知を送らず、今までどおり動かなければならない（MUST）。

#### Scenario: 両方を設定する
- **WHEN** エージェントに `<notify.telegram>`、受信箱のサービスに `<inbox.notify.fcm>` を設定し、issueが待ちになる
- **THEN** Telegramとアプリの両方に1通ずつ届く
