# Design

## Context

動機と範囲はproposal.mdに、判断はgrilling.mdにある。設計の前提になる今の形は、次のとおりである。

- `switchboard-web` は、`/api/inbox`、`/api/issue`、`/api/reply` を `inboxapi` の `Client` へ渡す。`http.Server` の `WriteTimeout` は60秒である
- `switchboard inbox serve` は、一覧を60秒キャッシュし、返答のあとに捨てる。詳細はキャッシュしない
- 画面は、`/` が一覧、`/issue/:ref` が1件で、それぞれ開いたときに1回だけ取る
- CSPは `default-src 'self'` で、同じオリジンへの接続だけを許す

## Goals / Non-Goals

**Goals:**

- 一覧と1件を、1つの画面で見比べながら返答できる
- 画面を開いたままで、待ちの増減と、選んだissueの変化が画面に出る
- 画面の数が増えても、フォージへの問い合わせは増えない

**Non-Goals:**

- 中継のイベントによる、数秒以内の更新
- 認証（#15）

## Decisions

- 流れは `GET /api/events` の1本にする。開いた直後に一覧を送り、その後は変わったときだけ送る。イベントは2種類で、`inbox` は `inboxapi.Inbox`、`failure` は `inboxapi.Error` を運ぶ。変わったかどうかは、`fetched_at` を除いた項目と届かなかったフォージのJSONで比べる。`fetched_at` は、キャッシュを作り直すたびに変わるためである
- 求め直しは、開いている流れごとに5秒の間隔で行う。受信箱のサービスがキャッシュを持つので、フォージへの問い合わせは30秒に1回で済む。流れの間で状態を共有するより、作りが単純になる
- 返答に成功したら、すべての流れを起こして、すぐに求め直させる。受信箱のサービスは返答でキャッシュを捨てるので、新しい一覧が届く
- 変わらない間も、25秒ごとにコメント行を送る。途中の機器やブラウザに、流れを閉じさせないためである
- 流れのハンドラーは、`http.ResponseController` で書き込みの期限を外す。サーバーの `WriteTimeout` は他の要求のために残す。`BaseContext` にシグナルのコンテキストを渡し、停止のときに流れを終える
- 画面は `EventSource` で流れを開く。切れたら、ブラウザが自分でつなぎ直す。ヘッダには、つなぎ始め、自動更新中、つなぎ直しの3つの状態のどれかを出す
- 詳細は、一覧の項目の `waiting_since`、`reason`、`question` を並べた値が変わったとき、または一覧から消えたときに取り直す。詳細の中身（最後の質問）は、この3つが変わらない限り変わらない。最初の一覧が届いたことは変化とみなさない。開いた直後に取った詳細を、もう一度取らないためである
- 返答の欄に書きかけの文は、詳細を取り直しても残す。issueが待ちでなくなれば、欄を消して、待ちでないことを出す

## Risks / Trade-offs

- 画面に変化が出るまで、最大で35秒ほどかかる（キャッシュの30秒と、求め直しの5秒）。数秒にするには、中継のイベントでキャッシュを捨てる別の変更が要る
- GitHubで待ちが多いと、キャッシュを作り直すたびに、待ちのissueごとにGraphQLを1回呼ぶ。待ちが10件なら、1時間に1,200ポイントで、5,000の上限に収まる。画面が開いていなくても、CLIの `switchboard inbox` と同じ回数しか呼ばない
