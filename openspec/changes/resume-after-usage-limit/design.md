# Design

## Context

動機はproposal.mdのWhyにある。今の作りでは、次のことが前提になる。

- Claude Codeは上限に当たると、まず `rate_limit_event`（`status=rejected`、`resetsAt` はUNIX秒）を出す。続くresultは `is_error=true`・`api_error_status=429`・`api_error=usage_limit_reached` を持つ。`subtype` は `success` のままである。V12として記録する
- 順番待ちは、`pending`（端末の中の待ち行列）、`queued`（投稿した順番待ちのコメント）、`queued.json`（再起動で消すコメント）で動く。`drain` が、枠の空いた順に `consider` から `launch` へ進める
- 始めるラベルで始めるには、ラベルを最後に付けた人が信頼済みでなければならない。エージェントのアカウントは信頼済みに入っていない
- 実行の周期（計画のモードか、承認済みか）は、エージェントの着手のマーカーの `mode` から読む（`classify`）

## Goals / Non-Goals

**Goals:**

- 上限とクオータで止まった実行を、人の返信なしに再開する
- 上限を検出する部分を、Claude Codeのアダプタに閉じ込める

**Non-Goals:**

- 実行の途中での停止（クオータの途中超過、`allowed_warning`）
- 直す実行の順番待ちへの戻し
- 他の端末への停止の伝達

## Decisions

### D1 サービスに依存しない型を `internal/usage` に置く

`usage.LimitHit{Kind, ResetsAt, Message}` を新しいパッケージに置く。`claudecode.Result` は `Limit *usage.LimitHit` と `CostUSD` を持つ。`internal/agent` は `usage` の型だけを見て判断し、Claude Codeの出力の形を知らない。`Kind` は `usage`（使用量の上限）と `rate`（それ以外の429）の2つである。

`Parse` は、resultが `is_error` のときだけ `Limit` を埋める。rejectedの `rate_limit_event` が先にあれば、その `resetsAt` を解除時刻にする。無くても、`api_error_status=429` なら上限とみなし、解除時刻は無しにする。成功したresultでは、rejectedのイベントがあっても上限にしない。

案：`claudecode` に型を置き、`agent` が直接読む。別の実行器を足すときに `agent` が `claudecode` の型に縛られるので採らない。

### D2 上限の結果は、順番待ちのコメントとして書き戻す

`outcome` の状態に `queued` を足す。書き戻しは今の `writeBack` を使う。コメントのマーカーは `state=queued reason=limit run=<実行> until=<再開の時刻>` とし、ラベルは `agent:ready` に戻す。通知は送らない。`outcome.json` を先に保存するので、書き戻しの途中で止まっても、次の起動で同じコメントを二重に投稿しない。

### D3 再開の印はフォージのマーカーで持つ（`<limit_resume.json>` を作らない）

計画では、端末の `<limit_resume.json>` に再開の印を書くとしていた。実装では、上のコメントのマーカーの `run=` を印として使う。理由は2つある。

- エージェント自身が `agent:ready` を付け直すので、ラベルの付与者はエージェントのアカウントになる。始めるラベルの信頼の判定を通すには、フォージ上で「エージェントが上限で戻した」と分かる印が要る
- 再起動しても、別の端末が実行しても（計画のD3）、同じ印を読める

`decide` は、始めるラベルの付与者がエージェントで、エージェントの最新の投稿（進捗と、`run=` の無い順番待ちを除く）が `run=` 付きの順番待ちのコメントのとき、それを上限からの再開とする。再開では新しい周期を始めない。`classify` を返答の再開と同じ道で通し、前の周期のモード（計画、承認済み、直接）を保つ。着手のマーカーにも `mode` を書かない。プロンプトの一文は、再開で、計画の実行でないときだけ足す。

再開の印のコメントは `queued.json` に `resume: true` として記録する。起動時の掃除では消さない。消すと、再開の印も消えるからである。実行を始めるときと、issueが順番待ちから外れたときに消す。

### D4 端末の停止は `pause.json` と、枠の判定に入れる

`pause.json` は `{reason, until}` を持つ。上限では、解除時刻（無いか過去なら、今から `agent.limit_wait` 後）を書く。すでに止まっているときは、遅い方の時刻を残す。`hasSlot` は最初に停止を見て、止まっていれば `limit` か `quota` を返す。そのため、順番待ちの仕組み（`pending`、コメント1つ、外れたら消す）がそのまま使える。直す実行は今と同じく順番待ちにせず、次のポーリングで試し直す。

時刻は `Agent` の `Now`（テストで進められる）で比べる。過ぎていれば `pause.json` を消す。停止を書いたときは、`time.AfterFunc` で再開の時刻に `drain` を走らせる。ポーリングも毎回 `drain` するので、タイマーは遅れを縮めるためだけにある。

### D5 クオータは `cost.json` と始める前の確認

`claude.auth: api_key` のときだけ、実行が終わるたびに `CostUSD` を `cost.json` へ足す。中身は `{day, day_usd, month, month_usd}` で、日と月は端末のローカル時刻で数える。日や月が変わっていれば、足す前に0へ戻す。`hasSlot` での停止の確認の後に、日と月の合計を `quota` と比べる。超えていれば、次の日の0時（月なら翌月1日の0時）を `until` とし、理由 `quota` で `pause.json` へ書く。以後はD4と同じ道を通る。

### D6 直す実行の上限（計画のD1）

直す実行が上限に当たったときは、D4の停止を書き、`waiting(reason=error)` で終える。本文に上限と解除予定の時刻を書く。マーカーに `until=` を付ける。`fixes()` は、`until=` の付いた待ちで終わった直す実行の着手を数えない。

### D7 受信箱

`inbox.Item` と `inboxapi.Item` に `queued_until` を足す。順番待ちのマーカーの `until` から取る。CLIの順番待ちの節の上限の列は、`limit (until 11-03 18:30)` のように出す。Webの順番待ちの行は「利用上限に達しています（11/3 18:30まで）」「APIのクオータに達しています（11/4 0:00まで）」とする。

### D8 偽フォージのラベルの付与者

偽フォージの `SetLabels` は、新しく足したラベルの付与者を、投稿に使うユーザー（既定ではエージェント）にする。実際のフォージは、トークンの持ち主を付与者として記録するからである。これまでエージェントは始めるラベルを付けなかった。そのため、既存のテストは変わらない。

## Risks / Trade-offs

- 危険：解除予定の時刻がずれていて、再開してすぐ上限に当たる。対策：上限の結果として順番待ちへもう一度戻るだけで、作業は失わない
- 危険：別の端末が、止まった端末のissueを先に始める。対策：計画のD3のとおり受け入れる
- 危険：`run=` の付いた順番待ちのコメントが、消し損ねで残る。対策：次に実行を始めるときに消す。残っても受信箱で順番待ちに見えるだけで、実行を誤って始めることはない（始めるラベルと、エージェントの投稿の両方が要る）
- 危険：クオータは始める前だけ確かめるので、1回分は超えうる。対策：計画どおり受け入れる（Q6）

## Migration Plan

設定を足さなければ、`agent.limit_wait` は30分、クオータは無効になる。`pause.json` と `cost.json` は無ければ作る。戻すときは前の版に戻すだけでよい。残った `run=` 付きの順番待ちのコメントは手で消す。
