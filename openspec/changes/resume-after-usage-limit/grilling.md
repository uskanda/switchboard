# grilling 記録: resume-after-usage-limit

issue `gh:uskanda/switchboard` #103の計画である。AIサービスの使用量上限に当たった実行を、自動で再開できるようにする。テストはClaude Codeで行うが、作りはサービスに依存させない。API利用ではクオータを設ける。grillingは、issueのコメントで計画を先に立てるモードとして行った。質問はコメント6586797351、回答は6593449436、計画は6593638170、承認は6594276875である。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 「任意のサービス」に対応する範囲 | 実行の結果に、サービスに依存しない上限の型（上限に当たったこと、解除予定の時刻、上限の種類）を設ける。検出はアダプタの責務とし、今回はClaude Codeのアダプタだけが埋める。解除時刻が分からないときは、設定した待ち時間（既定30分）の後に再開する | 第1ラウンド Q1（A） |
| 上限で止まったissueの状態と再開の仕方 | 順番待ちに戻す（`agent:ready` と `state=queued reason=limit` のマーカー）。解除予定の時刻をコメントで知らせ、過ぎたら自動で始めてそのコメントを消す。受信箱では順番待ちの節に、解除予定の時刻と一緒に出る | 第1ラウンド Q2（A） |
| 再開する実行の中身 | 新しいセッションで始め、プロンプトに「前の実行は利用上限で途中で止まった。worktreeの差分から続けよ」と足す。計画の実行には足さない | 第1ラウンド Q3（C） |
| 上限に当たったときに止める範囲 | その端末で新しい実行を始めるのを解除時刻まで止める。動いている実行は止めない。止めた状態はファイルに書き、再起動しても引き継ぐ | 第1ラウンド Q4（A） |
| APIのクオータの単位と範囲 | 費用（USD）で数える。端末ごとに `quota.daily_usd` と `quota.monthly_usd` を設け、resultの `total_cost_usd` を積み上げる。超えたら日または月の切り替わり（端末のローカル時刻）まで新しい実行を始めない。順番待ちの理由は `quota` | 第1ラウンド Q5（A） |
| 実行中にクオータを超える場合 | 途中では止めない。始める前だけ確かめ、超過を許して次の実行から止める | 第1ラウンド Q6（A） |
| サブスクリプションでも先回りして止めるか | 止めない。`allowed_warning` は使わず、実際にrejectedになってから止める | 第1ラウンド Q7（A） |
| 直す実行（CIの失敗・pushの拒否）が上限に当たったとき | 端末を止めることだけ同じにする。その実行は `waiting(reason=error)` で終え、本文に利用上限で止まったことと解除予定の時刻を書く。`max_fix_attempts` の回数には数えない | 計画のD1（承認で確定） |
| 待ち時間とクオータの設定の場所 | 待ち時間は `agent.limit_wait`（既定30m）。クオータは最上位の `quota:` 節（`daily_usd`、`monthly_usd`、未設定なら無効）。`claude.auth: subscription` のときは `quota` を使わず、設定の検査で警告を出す | 計画のD2（承認で確定） |
| 別の端末との関係 | 別の端末は、この端末の止まった状態を知らない。順番待ちに戻ったissueを別の端末が実行してもよい | 計画のD3（承認で確定） |

## 後回しにしたもの

- 実行の途中でクオータを超えたときに止めること（Claude Codeの予算のフラグか、stream-jsonの積算）。必要になったら別のissueにする
- `allowed_warning` を使った先回りの停止
- プロジェクトごとのクオータ
- 直す実行を順番待ちに戻す仕組み
- 正規表現の検出ルールと、Claude Code以外の実行器
