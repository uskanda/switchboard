## MODIFIED Requirements

### Requirement: 順番待ちのコメント
issueを順番待ちにしたとき、エージェントは、そのissueにマーカー `state=queued` 付きのコメントを投稿しなければならない（MUST）。
順番待ちのコメントには、順番待ちの理由だけを書かなければならない（MUST）。理由は、端末の上限とその値、プロジェクトの上限とその値、利用上限と再開の時刻、クオータと再開の時刻のどれかである。
順番待ちのコメントに、エージェントは、ほかのプロジェクトのissueやリポジトリの名前を書いてはならない（MUST NOT）。
同じissueが順番待ちのままである間、エージェントは、順番待ちのコメントを2つ以上投稿してはならない（MUST NOT）。投稿した後に編集もしない。
順番待ちのマーカーは、返答の判定と待ちの理由の読み取りでは、進捗のマーカーと同じく読み飛ばす。

#### Scenario: 端末の上限で順番待ちになる
- **WHEN** `<agent.max_parallel>` が1の端末で1つの実行が動いている間に、別のissueに `agent:ready` が付く
- **THEN** そのissueに、端末の上限1に達しているため順番待ちにしたというコメントが1つ付き、ラベルは `agent:ready` のまま変わらない

#### Scenario: 順番待ちのままポーリングが続く
- **WHEN** 順番待ちのissueがあるまま、ポーリングが3回続く
- **THEN** そのissueの順番待ちのコメントは1つのままである

#### Scenario: 止まった端末で順番待ちになる
- **WHEN** 利用上限で18:30まで止まった端末で、別のissueに `agent:ready` が付く
- **THEN** そのissueに、マーカー `reason=limit` と再開の時刻を持つ順番待ちのコメントが1つ付く

### Requirement: 順番待ちのコメントの削除
順番待ちのissueに着手するとき、エージェントは、着手のコメントを投稿する前に、そのissueの順番待ちのコメントを消さなければならない（MUST）。
順番待ちのissueが実行されずに順番待ちから外れたとき、エージェントは、そのissueの順番待ちのコメントを消さなければならない（MUST）。外れるのは、始めるラベルが外れたとき、closeされたとき、プロジェクトが設定から消えたときである。
起動したとき、エージェントは、同じ端末の前のプロセスが書いた順番待ちのコメントを消さなければならない（MUST）。順番待ちのままのissueには、次のポーリングで順番待ちのコメントを投稿し直す。
ただし、上限で止まった実行の順番待ちのコメントは、起動したときに消してはならない（MUST NOT）。そのコメントが、再開の印になるからである。

#### Scenario: 順番が来る
- **WHEN** 順番待ちのissueの前の実行が終わり、そのissueの実行が始まる
- **THEN** 順番待ちのコメントは消え、着手のコメントが付く

#### Scenario: 順番待ちの間にラベルを外す
- **WHEN** 順番待ちのissueから、マスターが `agent:ready` を外す
- **THEN** 次のポーリングで順番待ちのコメントが消え、そのissueの実行は始まらない

#### Scenario: 順番待ちのままエージェントを再起動する
- **WHEN** 順番待ちのissueがあるまま、エージェントを再起動する
- **THEN** 前のプロセスが書いた順番待ちのコメントは消え、まだ枠が空いていなければ、新しい順番待ちのコメントが1つ付く

#### Scenario: 上限で止まったまま再起動する
- **WHEN** 実行が上限で止まり、順番待ちに戻ったissueがあるまま、エージェントを再起動する
- **THEN** そのissueの順番待ちのコメントは1つのまま残り、再開の時刻を過ぎると実行が始まってコメントが消える

## ADDED Requirements

### Requirement: 上限で止まった実行の順番待ちへの戻し
実行が利用上限で終わったとき、エージェントは、そのissueを `agent:ready` に戻さなければならない（MUST）。
実行が利用上限で終わったとき、エージェントは、結果のコメントの代わりに、マーカー `state=queued reason=limit` と再開の時刻を持つ順番待ちのコメントを投稿しなければならない（MUST）。
利用上限は、実行器のアダプタが実行の結果から検出する。Claude Codeでは、rejectedの `rate_limit_event` か、エラーのresultの `api_error_status=429` である。
エージェントは、利用上限で終わった実行を通知してはならない（MUST NOT）。

#### Scenario: 実行が上限に当たる
- **WHEN** 実行中のclaudeが、解除時刻18:30のrejectedの `rate_limit_event` を出し、エラーのresultで終わる
- **THEN** issueは `agent:ready` になり、18:30まで止めて過ぎたら再開するという順番待ちのコメントが1つ付く。待ちのコメントは付かず、通知も送られない

### Requirement: 上限からの再開
上限で止まった実行の順番待ちのコメントがあるissueは、再開の時刻を過ぎたとき、エージェントが自動で実行を始めなければならない（MUST）。
エージェント自身が付けた始めるラベルでも、エージェントの最新の投稿が上限で止まった実行の順番待ちのコメントなら、エージェントはその実行を始めなければならない（MUST）。
上限からの再開は、新しい周期を始めてはならない（MUST NOT）。止まった実行と同じ周期のモードで動く。

#### Scenario: 時刻を過ぎて再開する
- **WHEN** 上限で止まったissueがあり、再開の時刻を過ぎる
- **THEN** 実行が始まり、順番待ちのコメントは消える

#### Scenario: 承認済みの計画の実装が上限で止まる
- **WHEN** 計画を先に立てるモードで、承認された計画の実装が上限で止まり、時刻を過ぎる
- **THEN** 再開した実行は、承認された計画の実装として動き、計画の質問をやり直さない

### Requirement: 再開した実行のプロンプト
上限からの再開で始まる実行のプロンプトに、エージェントは、前の実行が利用上限で途中で止まったことと、worktreeの変更から続けることを書かなければならない（MUST）。
計画の実行のプロンプトには、この一文を足してはならない（MUST NOT）。

#### Scenario: 実装の再開
- **WHEN** 実装の実行が上限で止まり、再開する
- **THEN** 再開した実行のプロンプトに、前の実行が利用上限で止まったという一文が入る

#### Scenario: 計画の実行の再開
- **WHEN** 計画の実行が上限で止まり、再開する
- **THEN** 再開した計画の実行のプロンプトには、その一文が入らない

### Requirement: 上限に当たった端末の停止
実行が利用上限で終わったとき、エージェントは、その端末で新しい実行を始めるのを、再開の時刻まで止めなければならない（MUST）。
再開の時刻は、アダプタが返した解除時刻とする。解除時刻が分からないときか過去のときは、今から `<agent.limit_wait>` 後とする。
止まっている間に始まるはずだったissueは、エージェントが順番待ちにしなければならない（MUST）。
止まっている間、エージェントは、動いている実行を止めてはならない（MUST NOT）。
止まった状態は、エージェントを再起動しても引き継がなければならない（MUST）。

#### Scenario: 止まっている間に別のissueが来る
- **WHEN** `<agent.max_parallel>` が2の端末で、1つの実行が上限に当たる。そのとき、もう1つの実行が動いている。続いて別のissueに `agent:ready` が付く
- **THEN** 動いている実行は最後まで続き、新しいissueは `reason=limit` の順番待ちになる

#### Scenario: 解除時刻が分からない
- **WHEN** `<agent.limit_wait>` が30mの端末で、解除時刻の無い429で実行が終わる
- **THEN** その30分後に、順番待ちのissueの実行が始まる

#### Scenario: 止まったまま再起動する
- **WHEN** 端末が上限で止まっている間に、エージェントを再起動する
- **THEN** 再開の時刻まで、新しい実行は始まらない

### Requirement: APIのクオータ
`<claude.auth>` が `api_key` の間、実行が終わったとき、エージェントは、その実行の費用を端末の日と月の合計に足さなければならない（MUST）。日と月は端末のローカル時刻で数える。
`<claude.auth>` が `api_key` の間、実行を始める前に、日の合計が `<quota.daily_usd>` 以上か、月の合計が `<quota.monthly_usd>` 以上のとき、エージェントはその実行を始めてはならない（MUST NOT）。そのissueは `reason=quota` の順番待ちにし、次の日（月の超過なら次の月）の0時に始める。
実行の途中では、エージェントはクオータで実行を止めてはならない（MUST NOT）。
`<claude.auth>` が `subscription` の間、エージェントは費用を数えてはならない（MUST NOT）。

#### Scenario: 日のクオータを超える
- **WHEN** `<quota.daily_usd>` が1の端末で、費用1.2ドルの実行が終わった後に、別のissueに `agent:ready` が付く
- **THEN** そのissueは `reason=quota` の順番待ちになり、日付が変わると実行が始まる

#### Scenario: サブスクリプションでは数えない
- **WHEN** `<claude.auth>` が `subscription` で `<quota.daily_usd>` が1の端末で、費用1.2ドルの実行が終わる
- **THEN** 次のissueは順番待ちにならずに始まる
