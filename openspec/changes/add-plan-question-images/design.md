# Design

## Context

計画の実行は `PlanSchema` の宣言で終わる（`internal/agent/planrun.go`）。各質問は `title`、`body`、`options`（文字列の配列）、`recommended`、`reason`、`weight` と、任意の `diagram` を持つ。図は `diagramOf` が検査し、`questionText` が `mermaid` のコードブロックとして書く。計画の実行の権限は `planSettings` が固定で作り、`allow_tools_extra` を渡さない。実行のあとは、HEADと差分を確かめ、変わっていれば戻して捨てる。

画像の添付は、ADR-051の `forge.Attacher` がある。GitLabの `upload` は `POST /projects/:id/uploads` を呼ぶ。`AttachComment` は、返る `markdown` を本文の最後の行の前に並べる。返る記法は、プロジェクトからの相対の `/uploads/<secret>/<name>` である。実装の実行の前に、`<Space.PrepareScreenshots>` が `.switchboard/screenshots/` を `.git/info/exclude` へ足す。

受信箱の `/v1/project-icon` は、フォージのアバターを受信箱のトークンで取る。取った画像は `forge.GetImage` で検査してキャッシュする（`internal/inboxserve/icons.go`）。Web表示はissueの画像をリンクとして出し、CSPは `img-src` を `'self'` に限る。動機はproposal.mdの「Why」を参照する。

## Goals / Non-Goals

**Goals:**

- 撮影、回収、アップロード、描画のどこで失敗しても、質問は画像なしで投稿される
- LLMがブラウザの中で動かすJSは、ループバックの外へ出られない
- 計画の実行の試作は、実行のあとに必ず捨てられる

**Non-Goals:**

- GitHubでの画像（`gh --attach` は画像を末尾に付けるので、各問いの位置へ移す仕組みが要る）
- 実装の実行での `<switchboard shot>` の案内
- 画像の比較や差分の自動生成

## Decisions

### 宣言のスキーマ

質問に `image`（文字列）と `option_images`（キーが `^[A-F]$` のオブジェクト、値はファイル名）を足す。選択肢を `{text, image}` の配列に変えると、#190で決めた `options` の形と、それを読むコードとテストを広く変えることになる。ラベルをキーにすれば、`recommended` と同じ書き方で選択肢を指せる。範囲の外のラベルのキーは、画像の検査で捨てる（質問は誤りにしない）。

`image` と `diagram` の両方があるときは、図を捨てる。画像を選んだ方が、手間をかけた結果だからである。

### 画像の回収

計画の実行の前に、`.switchboard/plan-images/` を `.git/info/exclude` に足して中を消す。スクリーンショットの準備と同じ関数を、置き場所を引数にして使う。実行が終わったら、HEADと差分の検査の前に、中のファイルを実行のディレクトリの `plan-images/` へ移す。検査は移したファイルに対して行う。形式は先頭のバイトで判定し、拡張子は信じない。`forge.ImageType` の上限は256KiBなので、上限を引数で受け取る形に広げる。アバターは256KiB、質問の画像は5MBで呼ぶ。

除外した置き場所は `git status` に出ないので、今の「計画の実行のあとの検査」の判定は変わらない。

### コメントの組み立てとアップロード

`forge` に、1つのファイルを上げて記法を返す `Uploader` のインターフェースを足し、GitLabのクライアントだけが満たす。今の `upload` をそのまま公開する形にする。`planQuestions` を組み立てる前に、エージェントは各画像を上げて記法を得る。記法を得られた画像だけを置く。問いの画像は図の位置、選択肢の画像はその選択肢の行の次の行とする。選択肢の行の間に画像の行が入ると、今のWeb表示が選択肢の組を1つと読めるかを、`parsePlanQuestions` のテストで確かめる。読めなければ、Web表示の読み取りを画像の行を飛ばすよう直す。

コメントの投稿に失敗したときは、上げた画像がプロジェクトに残る。GitLabのアップロードは、どこからも参照されなくても害は無いので、消さない。

### `<switchboard shot>`

CDPのライブラリとして `chromedp` を使う。Go側だけで完結し、ブラウザを別にダウンロードしない。ほかの案は次のとおりで、採らない。

- `go-rod`：機能は同等だが、既定でブラウザをダウンロードしようとする
- Playwrightを呼ぶ包み：Nodeとplaywrightのパッケージがホストに要る

外への読み込みは、ブラウザのプロキシを存在しない `127.0.0.1:9` にし、`localhost`、`127.0.0.1`、`[::1]` だけを直接つなぐことで止める。Chromiumは `127.0.0.0/8` を暗黙にプロキシから外すので、`<-loopback>` でその扱いを消す（V58）。CDPの `Fetch` で要求を捕まえる案は、WebSocketを捕まえられないので採らない。撮る前のJSは、ページの読み込みと待つ要素のあとに、CDPの `<Runtime.evaluate>` で動かす。

注記は、画像を後から編集せず、撮る直前にページへ重ねる要素で描く。セレクタの要素の位置から枠と矢印と文字を置き、重ねた要素ごと撮る。画像を編集するライブラリが要らず、文字はページのフォントで描かれるので、日本語も崩れない。注記はJSONのファイルか、繰り返せる引数で受ける。

エージェントは、自分の実行ファイルの絶対パスを `os.Executable` で得て、指示に書き、その `shot` だけを許す規則を足す。

### sandboxの中での撮影

指示では、開発サーバーの起動から停止までを、1回のBashの呼び出しで行うよう伝える。間に、起動の待ちと撮影を挟む。sandboxは呼び出しごとにネットワークの名前空間を分けるが、1回の呼び出しの中ではループバックが通じるはずである。Chromiumは、bwrapの中では自前のsandboxを作れない見込みが高いので、`<switchboard shot>` は `--no-sandbox` で起動する。外への読み込みは前の項のとおり止め、開けるのはループバックのページだけである。

この前提を検証項目V58としてROADMAP.mdに足し、実装の最初に確かめる。通らなければ、grillingの第2ラウンドQ9のとおり、sandboxの外で動かすコマンドの一覧の設定を足す。その場合は仕様の差分を足してから実装する。

### 計画の実行の許可

`planSettings` をプロジェクトとブラウザの有無を受け取る形にする。`allow_tools_extra` は、ファイルを書く実行と同じ `extraAllow` で足し、`--tools` にもツール名を足す。`<projects[].plan_prototype>` が有効なときは、拒否の一覧から `Edit` と `Write` を外し、許可とツールに足す。画像の項を渡すときは、試作が無効でも、worktreeの画像の置き場所だけへの `Write` を許し、`Write` のツールを渡す。`Write` のツールは `Edit` の規則で判定されるので、規則は `Edit(//<絶対パス>/**)` と書く。`Write(...)` の規則では、どこへの書き込みも許されない。`Edit` のツールは渡さない。撮る前のJSは、このファイルに書かせる。コマンドの行やheredocにJSを書くと、`dontAsk` のモードでは拒否されることがあるためである（V58）。完全なChromeは、単一のインスタンスのためにunixソケットを作り、計画の実行のsandboxでは起動できない。そのため、ブラウザは `chrome-headless-shell` を先に探す。`NotebookEdit`、`git add`、`git commit`、`git push`、`make` の拒否は保つ。試作で作ったファイルは、今の検査と戻しで捨てる。このとき「変更を捨てた」の行は書かない。

### 画像の指示

`prompt.PlanSystem` に、画像の項を入れるかどうかと試作の可否を渡す。画像は、アプリのスクリーンショットに限らない。Mermaidでは描きにくい説明は、実行がHTMLを画像の置き場所に書き、`python3 -m http.server` でループバックに配って `<switchboard shot>` で撮る。撮り方と検査はスクリーンショットと同じなので、switchboardの側に新しい仕組みは要らない。項を入れるのは、GitLabのプロジェクトで、ブラウザが見つかるときだけとする。ブラウザは実行の開始ごとに探す。項の中身は仕様の「画像の指示」のとおりで、Mermaidの「Diagrams」の項の後ろに置く。

### 受信箱の画像の口

`/v1/issue-image?issue=<ref>&src=<記法のURL>` を足す。`src` は、相対の `/uploads/<secret>/<name>` と、そのプロジェクトのWebのURLの下の絶対URLだけを受ける。取るときは、GitLabのAPI `GET /projects/:id/uploads/:secret/:filename` を受信箱のトークンで呼ぶ。Webの経路のURLは、非公開のプロジェクトで個人のトークンが通るとは限らないためである。`<secret>` と `<name>` の形を検査し、パスの区切りや `..` を含むものは404にする。

アップロードは `<secret>` で一意で、中身は変わらない。そのため、アイコンと同じ置き場所に長い期限でキャッシュする。`switchboard-web` は `/api/issue-image` で、受け取った値をそのまま受信箱のAPIへ渡す。

### Web表示

`parsePlanQuestions` は、最新の質問で、本文と選択肢の組の間の画像の行を問いの画像に、選択肢の行の直後の画像の行を選択肢の画像にする。`<QuestionImage>` の部品は、`/api/issue-image` のURLを `<img>` に入れ、カードの幅に縮める。押すと、Mermaidの図と同じダイアログで元の大きさに開く。読み込みに失敗したら、今の `ImageLink` を出す。CSPは変えない。

### ADRと文書

ADR-068を足し、次の2つを改める。

- ADR-051の「撮影専用の設定の項目は作らない」：撮影の仕組みは、設定の項目ではなくサブコマンドとして足す。設定の項目はブラウザのパスと試作の許可だけである
- 計画の実行は読むだけ、という前提：利用者が選んだプロジェクトだけで、捨てる前提の書き込みを許す

SECURITY.mdとSECURITY.ja.mdに、計画の実行がブラウザでLLMのJSを動かす脅威を足す。GUIDE.mdとGUIDE.ja.mdに、`<agent.browser>`、`<projects[].plan_prototype>`、`plan.md` に撮り方を書く例を足す。

## Risks / Trade-offs

- Chromiumを `--no-sandbox` で動かす → 開けるのはループバックのページだけで、外への要求はCDPで止める。ページはそのプロジェクトのアプリで、JSはLLMのものである。ブラウザの脆弱性で抜けられても、外側にはClaude Codeのsandboxが残る
- issueの本文に誘導されたLLMが、撮影でローカルの別のサービスを開く → 開けるのはループバックだけだが、ループバックの他のサービスは開ける。撮った画像は、そのプロジェクトのissueに上がる。プロジェクトの指示で使うポートを書いてもらい、SECURITY.mdに残余のリスクとして書く
- 試作の書き換えが捨てられずに実装の実行へ残る → 今の検査と戻しを使い、試作を許したプロジェクトで、書き換えが捨てられることをテストで確かめる
- 撮影のぶん、計画の実行が長くなり、トークンも増える → 画像は任意で、指示で①②を先に試させる
- V58が通らない → sandboxの外で動かすコマンドの一覧を足す（仕様の差分を足してから実装する）
- GitLabのアップロードのAPIが、受信箱のトークンの権限で通らない → 受信箱のトークンには `read_api` が要る。GUIDEに書き、取れないときはリンクに戻る

## Migration Plan

核の `switchboard` と `switchboard-web` を同じ版にそろえて入れ替える。設定の新しい2項目は任意で、無ければ今までどおり動く（GitLabでも、ブラウザが見つからなければMermaidだけ）。古いWeb表示では、画像はリンクとして出る。戻すときは前の版に入れ替える。
