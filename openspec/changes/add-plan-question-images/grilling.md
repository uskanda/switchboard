# grilling 記録: add-plan-question-images

計画の実行の質問に、Mermaidの図に加えて、LLMが作った画像を付けられるようにする計画である。`structured-plan-questions`（ADR-066）のMermaidの図は流れ図が中心で、画面がどう変わるかを直感的に伝えにくい。利用者の前提は、図の主な用途が「GUIやWeb画面が実際にどう変わるか」を見せることで、多くの場合はスクリーンショットを使うべき、というものである。sandboxの制約は、必要なら緩める提案をしてよいとされた。

面談の前に確かめた事実は次のとおりである。

- 画像の添付はADR-051の `Attacher` にある。GitLabはuploads APIで、返る `markdown` を本文の任意の位置に置ける。GitHubは `gh issue comment --attach` で、画像は末尾に付き、V47は未確認である
- 計画の実行のツールは `Bash`、`Read`、`Glob`、`Grep`、`WebSearch` で、`Edit`、`Write`、`make`、`gh` は拒否している。`allow_tools_extra` は計画の実行に渡らない
- 計画の実行と実装の実行は、issueごとに同じworktreeを使う
- sandboxの外で動くのは `git` と `verify_command` だけである。sandboxのBashは呼び出しごとにネットワークの名前空間が分かれるので、別の呼び出しで起動したサーバーにブラウザから届かない
- Web表示は、issueの画像を「画像：名前」のリンクとして出す。CSPは `default-src 'self'` である。`forge.ImageType` はSVGを拒否する
- 手元のホストには、PlaywrightのChromiumが `~/.cache/ms-playwright` にある。PythonにPILとmatplotlibは無い。Goの依存にブラウザを操作するライブラリは無い

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 画像の作り方 | 実行の中でBashを使い、PNGなどのファイルを `.switchboard/` の下に書く。宣言では問いと選択肢ごとにファイル名を指す。集め方はスクリーンショット（ADR-051）と同じにする | 第1ラウンド Q1 |
| Mermaidとの関係 | Mermaidは残す。1つの問いに付ける図は、Mermaidか画像のどちらか1つにする。GitLabでは、LLMが問いごとに合う方を選ぶ。画面の変化はスクリーンショット、流れや状態の移り変わりはMermaidを目安にする | 第1ラウンド Q2、会話中に確認 |
| GitHubの扱い | 今回はGitLabだけで画像を許す。GitHubのプロジェクトはMermaidだけの今のままにする | 第1ラウンド Q3 |
| Web表示での見せ方 | switchboard-webが受信箱のトークンでGitLabから画像を取り、最新の質問の問いのカードの中に描く。`img-src 'self'` のまま描ける | 第1ラウンド Q4 |
| 画像を付けられなかったとき | その問いは画像なしで投稿し、監査ログに `<plan.image_dropped>` を残す。コメントには、図を付けられなかった旨を1行書く | 第1ラウンド Q5 |
| 何を撮るか | 低コストな方法を優先する。今の画面のスクリーンショットと、その書き換えで表せるならそれで済ませる。worktreeを一時的に書き換えて試作するのは、必要なときだけにする | 第2ラウンド Q6 |
| 画像を付ける単位 | 問いに1枚（今の画面）と、選択肢ごとに1枚（その案を選んだあとの画面）を付けられる。どれも任意 | 第2ラウンド Q7 |
| 撮り方の設定 | 利用者がプロジェクトの指示（`plan.md`）にアプリの起動などの撮り方を書き、`allow_tools_extra` を計画の実行にも渡す。加えて、switchboardが汎用の撮影の手順をプロンプトに入れる | 第2ラウンド Q8 |
| sandboxの緩め方 | まず、sandboxを保ったまま1回の呼び出しでサーバーとブラウザを動かせるかを検証項目として確かめる。動かなければ、sandboxの外で動かすコマンドの一覧をプロジェクトの設定に足し、計画の実行と実装の実行の両方でsandboxの外で動かす | 第2ラウンド Q9 |
| 画像の制限 | PNG、JPEG、WebPで、1枚5MBまで、1回の質問で10枚まで。SVGは拒否する | 第2ラウンド Q10 |
| 変更後の描き方の段階 | ①今の画面を撮り、枠、矢印、注記で変わる場所を示す。②撮る直前にページ上でJSを動かしてDOMやCSSを書き換え、変更後の見た目を撮る。ソースのファイルには触れない。③それでも表せないときだけ、worktreeを一時的に書き換えて試作する。この順に、足りるところで止める | 第3ラウンド Q11 |
| 汎用の撮影の手順の形 | 撮影のサブコマンド `switchboard shot` を足す。URL、出力先、画面の幅、撮る前に実行するJS、注記（枠、矢印、文字）を引数で受ける。ブラウザはホストのChrome/Chromiumを使い、開けるURLは `localhost` と `127.0.0.1` だけにする。Go側にCDPのライブラリが1つ増える | 第3ラウンド Q12 |
| 計画の実行への `Edit/Write` の許可 | プロジェクトの設定で③を有効にしたときだけ許す（既定は無効）。実行のあと、`.switchboard/` の画像を退避してから、`git reset --hard` と `git clean` でworktreeを計画の前に戻す | 第3ラウンド Q13 |
| 選択肢ごとの画像の置き方 | コメントでは、選択肢の行 `A: 文` の直後の別の行に画像を置く。問いの画像は、本文と選択肢の間（Mermaidの図の位置）に置く。Web表示では、カードの幅に縮めて出し、押すと元の大きさで開く | 第3ラウンド Q14 |
| 実装の実行での `switchboard shot` | 今回は計画の実行だけで使う。実装の実行は今までどおり `implement.md` の撮り方に任せる | 第4ラウンド Q15 |
| ブラウザの見つけ方 | 設定の `<agent.browser>`（実行ファイルのパス）で指定する。空なら、PATHの `chromium`、`chromium-browser`、`google-chrome` を順に探す。見つからなければ、プロンプトに画像の項を入れずMermaidだけにする | 第4ラウンド Q16 |
| Web表示が取りに行く画像の範囲 | そのissueのプロジェクトのGitLabのアップロードのURL（フォージのホストの `/uploads/…`）だけを、受信箱のトークンで取る。`forge.GetImage` の形式の検査を通し、大きさの上限は5MBにする。ほかのURLの画像は、今までどおりリンクとして出す | 第4ラウンド Q17 |
