# web Specification

## Purpose

受信箱をブラウザで見て、返答できるようにする。デスクトップとスマホの両方で使える。WUIは核とは別のモジュールで、フォージのトークンを持たず、核の `switchboard inbox serve` を通してだけ受信箱を扱う。

## Requirements

### Requirement: 待ち受けのアドレス
`<switchboard-web>` は、`<web.yaml>` の `<listen>` に書いたアドレスで待たなければならない（MUST）。既定のアドレスは持たない。
`<listen>` が無いとき、ホストが空のとき、`0.0.0.0` か `::` のとき、`<switchboard-web>` は起動を拒まなければならない（MUST）。
WUIの設定は `<web.yaml>` に置き、核の `config.yaml` には書かない。

#### Scenario: すべてのインターフェースで待とうとする
- **WHEN** `<listen>` に `0.0.0.0:8783` を書いて `<switchboard-web>` を起動する
- **THEN** 起動せず、LANのアドレスを明示するよう報告する

### Requirement: 核とのつなぎ
`<switchboard-web>` は、受信箱の一覧、1件の詳細、返答を、`<inboxapi>` を通して `switchboard inbox serve` に求めなければならない（MUST）。
`<switchboard-web>` は、フォージのトークンを持ってはならず、フォージのAPIを直接呼んではならない（MUST NOT）。
ソケットに届かないとき、WUIは、受信箱のサービスに届かないことを画面に示す。

#### Scenario: 受信箱のサービスが止まっている
- **WHEN** `switchboard inbox serve` が動いていない状態で、一覧の画面を開く
- **THEN** 受信箱のサービスに届かないことが表示される

### Requirement: 画面
WUIの画面は、ヘッダと本体からなり、ヘッダには、名前、待ちと実行中の件数、自動更新の状態、設定の画面へのリンクを表示しなければならない（MUST）。
幅1024px以上のとき、WUIは、左のペインに一覧を、右のペインに選んだissueの1件を並べて表示しなければならない（MUST）。
幅1024px未満のとき、WUIは、一覧と1件を別の画面として表示しなければならない（MUST）。
選んだissueは、`/issue/<ref>` のURLで表さなければならない（MUST）。issueを選んでいないとき、右のペインは、一覧から選ぶよう示す。
一覧は、`switchboard inbox` と同じ項目を表示しなければならない（MUST）。届かなかったフォージがあれば、そのことも示す。
プロジェクトでまとめない間、一覧は、各節の行を待ちが始まった古い順に表示しなければならない（MUST）。
プロジェクトでまとめる間、一覧は、各サブグループの中の行を古い順に表示しなければならない（MUST）。
プロジェクトでまとめる間、一覧は、各節のサブグループを、それぞれの最も古い行の古い順に並べなければならない（MUST）。
1件の表示は、エージェントの最後の投稿の全文、拒否された操作、フォージのissueへのリンク、返答の欄を表示しなければならない（MUST）。
画面は、デスクトップとスマホのどちらの幅でも、横へのスクロール無しで使えなければならない（MUST）。
issueから来た文字列（タイトル、本文、コメント）を、HTMLとして解釈させてはならない（MUST NOT）。
画面の静的ファイルは、すべて `<switchboard-web>` に埋め込み、外のCDNから読み込んではならない（MUST NOT）。

#### Scenario: デスクトップの幅で選ぶ
- **WHEN** 幅1280pxのブラウザで一覧の行を選ぶ
- **THEN** URLが `/issue/<ref>` になり、左に一覧を残したまま、右にそのissueと返答の欄が出る

#### Scenario: スマホの幅で開く
- **WHEN** 幅360pxのブラウザで一覧と1件の画面を開く
- **THEN** 一覧と1件は別の画面に出て、横へのスクロール無しで、返答を書いて送れる

#### Scenario: タイトルにHTMLが含まれる
- **WHEN** タイトルが `<script>` を含む待ちのissueを一覧に出す
- **THEN** その文字列がそのまま表示され、スクリプトは動かない

#### Scenario: まとめない一覧の順
- **WHEN** プロジェクトでまとめない状態にして、2つのプロジェクトの待ちのissueがある一覧を開く
- **THEN** 返答待ちの節に、プロジェクトに関わらず、待ちが始まった古い順で行が出る

### Requirement: 返答
1件の画面から送った返答を、`<switchboard-web>` は `<inboxapi>` で投稿しなければならない（MUST）。待ちでないと返されたら、そのことを画面に示す。
返答のPOSTについて、`<switchboard-web>` は、`Origin` と `Host` が `<listen>` のアドレスと一致することを確かめなければならない（MUST）。一致しないか、`Origin` が無いときは、投稿せずに403を返す。

#### Scenario: 外のWebページから送られる
- **WHEN** 別のオリジンのWebページが、WUIの返答のURLへPOSTを送る
- **THEN** 403が返り、issueには何も投稿されない

#### Scenario: 別の名前で届く
- **WHEN** `Host` が `<listen>` と違う名前の返答のPOSTが届く
- **THEN** 403が返り、issueには何も投稿されない

### Requirement: 認証
当面、WUIは利用者を認証しない。LANの中から届く要求は、すべて利用者のものとして扱う。認証が無くても、返答のPOSTでの `Origin` と `Host` の検査は省いてはならない（MUST NOT）。
この扱いは、ADR-036と、認証を課題として残したissueに記録する。

#### Scenario: LANの別の機器から開く
- **WHEN** LANの中のブラウザで、WUIのアドレスを開く
- **THEN** ログインを求めずに一覧が表示される

### Requirement: 設定の画面
WUIは、ヘッダから開ける設定の画面を持たなければならない（MUST）。
設定の画面は、全体と各プロジェクトの、計画用と実装用の指示の欄を並べ、欄ごとに保存できなければならない（MUST）。
設定の画面は、指示のファイルがどの端末のものかを表示しなければならない（MUST）。
保存の誤り（大きさの上限、秘密らしいもの、受信箱のサービスに届かない）は、どの欄の誤りかが分かる形で画面に示す。
設定の画面は、追加で許可するツールの設定を編集する手段を持ってはならない（MUST NOT）。

#### Scenario: プロジェクトの指示を保存する
- **WHEN** 設定の画面で `gh:uskanda/switchboard` の計画用の欄に指示を書いて保存する
- **THEN** `<inboxapi>` を通して保存され、画面には端末 `ubuntu-a` の指示として保存されたことが示される

#### Scenario: 実装用の指示を保存する
- **WHEN** 設定の画面で `gh:uskanda/switchboard` の実装用の欄に指示を書いて保存する
- **THEN** 実装用の指示として保存され、同じプロジェクトの計画用の欄の内容は変わらない

#### Scenario: トークンを貼り付けた
- **WHEN** 設定の画面で、トークンを含む指示を保存しようとする
- **THEN** 保存されず、その欄に、秘密らしいものを含むと示される

### Requirement: 追加の指示の保存の検査
指示の保存のPOSTについて、`<switchboard-web>` は、本文がJSONであることを確かめなければならない（MUST）。
同じPOSTについて、`<switchboard-web>` は、`Origin` と `Host` が `<listen>` のアドレスと一致することを確かめなければならない（MUST）。一致しないか、`Origin` が無いときは、保存せずに403を返す。

#### Scenario: 外のWebページから送られる
- **WHEN** 別のオリジンのWebページが、WUIの指示の保存のURLへPOSTを送る
- **THEN** 403が返り、指示のファイルは変わらない

### Requirement: 計画の待ちの表示
一覧の画面と1件の画面は、待ちの理由 `plan-questions` と `plan` を、ほかの理由と同じく理由として表示しなければならない（MUST）。
理由が `plan` のとき、1件の画面は、返答の欄の近くに、承認の語を送れば承認になることを示さなければならない（MUST）。
理由が `plan` のとき、1件の画面は、「承認する（<承認の語> を送る）」のボタンを置かなければならない（MUST）。押すと、確認を挟まずに、承認の語だけを返答のPOSTで投稿する。
返答の欄に空白以外の文があるとき、または待ちでないとき、承認のボタンは押せてはならない（MUST NOT）。
理由が `plan` 以外のとき、1件の画面は、承認のボタンを置いてはならない（MUST NOT）。
理由が `plan-questions` で問いを読み取れたとき、1件の画面は、返答の欄の近くに答え方を示さなければならない（MUST）。答え方とは、問いごとに選んで「この内容で返答」を押すことと、返答の欄の文が全体への補足として加わることをいう。
理由が `plan-questions` で問いを読み取れなかったとき、1件の画面は、返答の欄の近くに、問いごとの答えを返答の欄に書いて送るよう示さなければならない（MUST）。
理由が `plan-questions` のとき、1件の画面は、承認の語で答えるよう勧めてはならない（MUST NOT）。

#### Scenario: 計画の承認待ちを開く
- **WHEN** 理由が `plan` の待ちのissueを1件の画面で開く
- **THEN** 計画の全文と、`/ok` を送れば承認になることが表示される

#### Scenario: 計画の質問の待ちを開く
- **WHEN** 理由が `plan-questions` の待ちのissueを1件の画面で開く
- **THEN** 返答の欄の近くに、選んで「この内容で返答」を押す答え方が表示され、`/ok` を送るよう勧める文は表示されない

#### Scenario: 空の欄で承認のボタンを押す
- **WHEN** 理由が `plan` の待ちのissueで、返答の欄が空のまま、承認のボタン `承認する（/ok を送る）` を押す
- **THEN** `/ok` だけがissueへのコメントとして投稿され、「送りました」が表示される

#### Scenario: 返答の欄に文がある
- **WHEN** 理由が `plan` の待ちのissueで、返答の欄に直しの文を書く
- **THEN** 承認のボタンは押せず、「返答を送る」は押せる

#### Scenario: 計画の質問の待ちには承認のボタンが無い
- **WHEN** 理由が `plan-questions` の待ちのissueを1件の画面で開く
- **THEN** 承認のボタンは表示されない

### Requirement: スレッドの表示
1件の表示は、issueの本文とコメントを、古い順に表示しなければならない（MUST）。
1件の表示は、本文とコメントをMarkdownとして描かなければならない（MUST）。生のHTMLは描かずに文字として出し、画像は読み込まずにリンクとして出す。
1件の表示は、本文とコメントの段落の中の1つの改行を、改行として描かなければならない（MUST）。
1件の表示は、本文とコメントの中のHTMLのコメント（`<!--` から `-->` まで）を表示してはならない（MUST NOT）。
1件の表示は、エージェントの投稿に、エージェントのものであることを示す印を付けなければならない（MUST）。
1件の表示は、エージェントの着手のコメントと順番待ちのコメントを1行に畳み、進捗のコメントは最新の1件だけを表示しなければならない（MUST）。
1件の表示は、エージェントの投稿のマーカーを表示してはならない（MUST NOT）。
issueから来たリンクは、新しいタブで開き、参照元を送ってはならない（MUST NOT）。

#### Scenario: 本文にHTMLと画像がある
- **WHEN** 本文が `<img src=x onerror=alert(1)>` と、Markdownの画像 `![a](https://example.com/a.png)` を含むissueを開く
- **THEN** `<img` の文字列がそのまま表示され、画像は読み込まれずにリンクとして出る

#### Scenario: 本文にissueのテンプレートのコメントがある
- **WHEN** 本文が `<!-- 再現の手順を書く -->` と、その下の文を含むissueを開く
- **THEN** `<!--` で始まるコメントは出ず、その下の文だけが出る

#### Scenario: 着手と進捗のコメントがある
- **WHEN** 着手のコメント1件、進捗のコメント2件、人のコメント1件があるissueを開く
- **THEN** 着手のコメントは1行で出て、進捗のコメントは新しい1件だけが出て、人のコメントはそのまま出る

#### Scenario: 順番待ちのコメントがある
- **WHEN** 順番待ちのコメント1件と人のコメント1件があるissueを開く
- **THEN** 順番待ちのコメントは1行で出て、人のコメントはそのまま出る

#### Scenario: 選択肢を1行ずつ書いたコメント
- **WHEN** 空行を挟まずに `A: 右クリックだけ` と `B: 選択メニューだけ` の2行が続くコメントを開く
- **THEN** 2つの選択肢は1段落につながらず、別の行に表示される

### Requirement: 自動更新
画面を開いている間、WUIは、受信箱のサービスからの知らせを受けて、一覧とヘッダの件数を書き換えなければならない（MUST）。
選んだissueの更新の時刻、人のコメントの数、状態、理由、進捗のどれかが変わったとき、WUIは、その1件を取り直して表示しなければならない（MUST）。
選んだissueが一覧から消えたとき、WUIは、1件の表示を残したまま、待ちでも実行中でもなくなったことを示さなければならない（MUST）。
返答を書いている途中で表示を書き換えるとき、WUIは、返答の書きかけを消してはならない（MUST NOT）。
返答を書いている途中で、そのissueが待ちでなくなったとき、WUIは、返答を送れなくして、その旨を示さなければならない（MUST）。
返答を送ったあと、選んだissueが返答した待ちでなくなったとき、WUIは、送ったことの表示をやめなければならない（MUST）。このとき、WUIは、その時点の状態を表示し、新しい待ちなら返答の欄を出さなければならない（MUST）。返答した待ちでなくなるのは、issueが実行中、順番待ち、新しい待ちのどれかになったときと、一覧から消えたときである。完了したissueに返答したときは、完了のままのあいだを、返答した待ちと同じに扱う。
知らせの接続が切れている間、WUIは、ヘッダに、切れていて再接続を試みていることを示さなければならない（MUST）。
ページが見えていない間（ブラウザのタブが裏に回ったときなど）、WUIは、知らせの接続を閉じなければならない（MUST）。ページが再び見えたとき、WUIは、接続し直して一覧を書き換えなければならない（MUST）。

#### Scenario: 開いている間に待ちが増える
- **WHEN** 一覧を開いたまま、別のissueが待ちになる
- **THEN** 再読み込みせずに、そのissueが一覧に足され、ヘッダの待ちの件数が増える

#### Scenario: 書きかけの間に再開する
- **WHEN** 返答を書いている途中で、フォージから別の返答が届いて、そのissueが待ちでなくなる
- **THEN** 書きかけは残り、返答の送信のボタンは押せなくなり、待ちでなくなったことが示される

#### Scenario: 受信箱のサービスが止まる
- **WHEN** 画面を開いたまま、`switchboard inbox serve` が止まる
- **THEN** ヘッダに、自動更新が切れていて再接続を試みていることが示される

#### Scenario: タブが裏に回る
- **WHEN** 画面を開いたまま、ブラウザで別のタブに切り替え、しばらくして戻る
- **THEN** 切り替えている間は知らせの接続が閉じ、戻ったときに接続し直して、その時点の一覧が出る

#### Scenario: 返答のあと次の待ちが届く
- **WHEN** 返答を送ったあと、画面を読み込み直さないまま、エージェントが次の待ちを投稿する
- **THEN** 送ったことの表示が消え、返答の欄が出る

#### Scenario: 返答のあと実行が始まる
- **WHEN** 返答を送ったあと、画面を読み込み直さないまま、そのissueが実行中になる
- **THEN** 送ったことの表示が消え、実行中のため返答できないことが示される

### Requirement: 1件の読み込みの表示
1件を読んでいる間、WUIは、読み込み中であることを、回るアイコンと文字で示さなければならない（MUST）。
同じタブで前に読んだissueを開いたとき、WUIは、フォージから読み直す結果を待たずに、前回読んだ内容を出さなければならない（MUST）。読み直しが届くまで、WUIは「更新を取得中」と示さなければならない（MUST）。
WUIは、前回読んだ内容をメモリにだけ置かなければならない（MUST）。issueの内容をブラウザのストレージへ書いてはならない（MUST NOT）。
読み直しに失敗したとき、WUIは、前回読んだ内容を残し、それが前回のものであることを示さなければならない（MUST）。

#### Scenario: 初めて開く
- **WHEN** このタブでまだ読んでいないissueを開く
- **THEN** 回るアイコンと「読み込んでいます」が出て、届くと1件の内容に替わる

#### Scenario: 前に開いたissueに戻る
- **WHEN** 一覧で別のissueを開いたあと、前に開いたissueをもう一度開く
- **THEN** 前回読んだ内容がすぐに出て、「更新を取得中」と示され、読み直しが届くとその内容に替わる

#### Scenario: 読み直しに失敗する
- **WHEN** 前に開いたissueを開き、受信箱のサービスに届かない
- **THEN** 失敗の知らせとともに、前回読んだ内容を表示していることが示される

### Requirement: 設定の画面のプロジェクトの節
設定の画面は、指示の節より上に、プロジェクトの節を表示しなければならない（MUST）。
プロジェクトの節は、この端末の担当プロジェクトごとに、`ref`、`path`、`plan_first`、クローンの有無、無い状態ラベルを表示する。

#### Scenario: 設定の画面を開く
- **WHEN** 担当プロジェクトが2つある端末で、設定の画面を開く
- **THEN** 指示の節の上に、2つのプロジェクトとそれぞれの状態が表示される

### Requirement: クローンが無いときの案内
クローンが無いプロジェクトについて、プロジェクトの節は、エージェントのトークンの対象にそのリポジトリが入っているかを確かめるよう示さなければならない（MUST）。

#### Scenario: cloneできていない
- **WHEN** クローンの無いプロジェクトがある状態で、設定の画面を開く
- **THEN** そのプロジェクトの行に、エージェントのトークンの対象を確かめるよう示す文が表示される

### Requirement: プロジェクトの追加の欄
追加が有効なとき、プロジェクトの節は、`ref` の入力と `plan_first` の切り替えを持つ追加の欄を表示しなければならない（MUST）。`plan_first` の初期値はオンとする。
追加が無効なとき、プロジェクトの節は、追加の欄の代わりに、`<inbox.project_root>` を設定すれば追加できることを表示しなければならない（MUST）。
追加の欄は、`path`、`host`、`base_branch` などほかの項目を入力させてはならない（MUST NOT）。

#### Scenario: 追加が無効
- **WHEN** `<inbox.project_root>` の無い端末で、設定の画面を開く
- **THEN** 追加の欄は表示されず、`<inbox.project_root>` を設定すれば追加できることが表示される

### Requirement: 追加の結果の表示
追加に成功したとき、WUIは、足したプロジェクトの参照を成功のトーストで表示し、プロジェクトの一覧を取り直さなければならない（MUST）。応答にwebhookの案内があれば、案内とコマンドは、トーストにせず、プロジェクトの一覧の下に表示する。
追加が拒まれたとき、WUIは、追加の欄に、拒まれた理由を表示しなければならない（MUST）。

#### Scenario: 中継を使う端末で足す
- **WHEN** `<agent.relay>`のある端末で、`gh:uskanda/notes`を追加する
- **THEN** 成功のトーストに`uskanda/notes`と「GitHub」のバッジ、「を追加しました」が表示され、一覧に`uskanda/notes`のカードが現れる。一覧の下には、`switchboard relay hook add gh:uskanda/notes`を実行するよう表示される

#### Scenario: 同じプロジェクトを足す
- **WHEN** 既にある`gh:uskanda/switchboard`を追加する
- **THEN** 追加の欄に、既にあることが表示される

### Requirement: プロジェクトの追加のPOSTの検査
プロジェクトの追加のPOSTについて、`<switchboard-web>` は、本文がJSONであることを確かめなければならない（MUST）。
同じPOSTについて、`<switchboard-web>` は、`Origin` と `Host` が `<listen>` のアドレスと一致することを確かめなければならない（MUST）。一致しないか、`Origin` が無いときは、追加せずに403を返す。

#### Scenario: 外のWebページから送られる
- **WHEN** 別のオリジンのWebページが、WUIのプロジェクトの追加のURLへPOSTを送る
- **THEN** 403が返り、設定ファイルは変わらない

### Requirement: 計画の質問の読み取り
理由が `plan-questions` の待ちの間、1件の表示は、最新の待ちのコメントから問いを読み取らなければならない（MUST）。問いは、行頭の `❓` に続く太字の `Qn` と太字の題で始まる。1件の表示は、問いを番号と題と本文と推奨に分ける。推奨は、問いの中の `➡️` で始まる段落である。
問いを1つも読み取れなかったとき、1件の表示は、そのコメントを、ほかのコメントと同じく描かなければならない（MUST）。
最新でない質問のコメントについて、1件の表示は、選択肢と自由記述の欄を付けてはならない（MUST NOT）。
問いを読み取った質問のコメントで、1件の表示は、承認の語で答えるよう案内するエージェントの段落を表示してはならない（MUST NOT）。

#### Scenario: 6つの問いのコメント
- **WHEN** Q1からQ6を `---` で区切って並べた質問のコメントで待っているissueを開く
- **THEN** 6つの問いが、それぞれの番号、題、本文、推奨とともに表示される、コメントの最後の `/ok` で答えるよう案内する段落は表示されない

#### Scenario: 前のラウンドの質問
- **WHEN** Q1からQ3のコメントのあとに、Q4とQ5のコメントで待っているissueを開く
- **THEN** 選択肢と自由記述の欄は、Q4とQ5にだけ付く

### Requirement: 選択肢の組の読み取り
1件の表示は、問いの本文の中で、行頭にラベルを持つ行が2つ以上続くとき、それを1組の選択肢として読み取らなければならない（MUST）。
ラベルは、A〜Zの1文字か、1桁以上の数字とする。ラベルの前には `-`、`*`、`+` の箇条書きの印と空白、`**`、`(` があってもよく、ラベルの後ろには `)`、`）`、`**` のあとに、`:`、`：`、`.`、`、`、空白のどれかが続く。1組のラベルは、同じ種類（英字か数字）で、`A`、`B`、`C` や `1`、`2`、`3` のように1つずつ増えなければならない（MUST）。
1件の表示は、1行を `/` か `／` で区切り、区切ったそれぞれがラベルで始まるとき、その行を1組の選択肢として読み取らなければならない（MUST）。行頭の、`:` か `：` で終わる語を、その組の見出しとする。
1件の表示は、1つの問いの中の組を、いくつでも読み取らなければならない（MUST）。
コードのブロックの中の行を、1件の表示は、選択肢として読み取ってはならない（MUST NOT）。

#### Scenario: 1行ずつの選択肢
- **WHEN** 本文に `A: 右クリックだけ。`、`B: いまの選択メニュー。`、`C: AとBの両方。` の3行がある問いを開く
- **THEN** A、B、Cの3つの選択肢の組が表示される

#### Scenario: 1行に2組
- **WHEN** 本文に `範囲: A 全体 / B 購読フィード / C カテゴリ` と `欄: X タイトルと内容 / Y タイトルだけ` の2行がある問いを開く
- **THEN** 見出しが「範囲」の組と「欄」の組が表示される

#### Scenario: 英文の行頭
- **WHEN** 本文に `A user opens the page.` と `I think it is fine.` の2行が続く問いを開く
- **THEN** ラベルが1つずつ増えていないので、選択肢の組として読み取られない

### Requirement: 選択肢の描き方
1件の表示は、読み取った組の選択肢を、1行に1つずつ、ラジオボタンとして描かなければならない（MUST）。1組の中で選べるのは1つだけとする。
1件の表示は、組ごとに、最後のラジオボタンとして「選ばない（補足で答える）」を足さなければならない（MUST）。
1件の表示は、問いの最後の組の下に、その問いの自由記述の欄を置かなければならない（MUST）。組を読み取れなかった問いでは、本文の下に自由記述の欄だけを置く。
選択肢の文は、ほかのissueの文字列と同じく、HTMLとして解釈させてはならない（MUST NOT）。

#### Scenario: 組を読み取れなかった問い
- **WHEN** 本文に選択肢の組が無い問いを開く
- **THEN** 本文と推奨がそのまま表示され、自由記述の欄だけが付く

### Requirement: 推奨の既定の選択
1件の表示は、組ごとに、推奨の文で最初に出てくるその組のラベルを、既定で選ばなければならない（MUST）。英字か数字に挟まれた文字は、ラベルとして数えない。
推奨の文にその組のラベルが無いとき、1件の表示は、その組の「選ばない（補足で答える）」を既定で選ばなければならない（MUST）。

#### Scenario: 理由の中でほかの案に触れる
- **WHEN** 推奨が「A。全文を表示するのが普通なので、Bでは使える場面が減ります」である問いを開く
- **THEN** Aが選ばれた状態で表示される

#### Scenario: 2組の推奨
- **WHEN** 推奨が `範囲はA（全体）、欄はX（タイトルと内容）。` で、組が「範囲」と「欄」の問いを開く
- **THEN** 範囲の組ではA、欄の組ではXが選ばれた状態で表示される

#### Scenario: 推奨にラベルが無い
- **WHEN** 推奨が「APIの名前は今のままにします」で、組がAとBである問いを開く
- **THEN** その組では「選ばない（補足で答える）」が選ばれた状態で表示される

### Requirement: 選択の保持
同じ質問のコメントを表示している間、WUIは、自動更新で表示を書き換えても、選択と自由記述の欄の書きかけを消してはならない（MUST NOT）。
新しい質問のコメントで待つようになったとき、WUIは、選択と自由記述の欄を、新しい問いの既定の状態から始めなければならない（MUST）。

#### Scenario: 選んでいる途中で自動更新が来る
- **WHEN** Q2でBを選び、自由記述を書いている途中で、そのissueの一覧の行が変わる
- **THEN** Bの選択と自由記述の書きかけは残る

### Requirement: 返答の文
1件の表示は、問いを読み取れたとき、返答の欄に「この内容で返答」のボタンを置かなければならない（MUST）。今の返答の欄と「返答を送る」のボタンは残す。
「この内容で返答」が送る文は、問いごとに1行、`Q<番号> <題>: <答え>` の形でなければならない（MUST）。答えは、選んだラベルとする。2組以上の問いでは、見出しのある組を `<見出し>は<ラベル>` として、`、` でつなぐ。自由記述があれば、そのあとに `。補足：<自由記述>` を付ける。どの組でもラベルを選ばなかった問いでは、自由記述だけを答えとする。
選んだラベルと自由記述のどちらも無い問いの答えは、`回答なし` でなければならない（MUST）。
返答の欄に文があるとき、「この内容で返答」が送る文は、問いの行のあとに、その文を全体への補足として含まなければならない（MUST）。
「この内容で返答」が送る文は、承認の語で始まってはならない（MUST NOT）。
1件の表示は、「この内容で返答」のボタンの上に、送る文を読み取り専用で表示し、選択と自由記述の変化に合わせて書き換えなければならない（MUST）。

#### Scenario: 推奨と違う案を選んで補足を書く
- **WHEN** Q1の推奨のCを残し、Q2でBを選んで自由記述に「件数は出さない」と書く
- **THEN** 送る文は `Q1 操作の入口: C` と `Q2 選んだあとの流れ: B。補足：件数は出さない` の2行になる

#### Scenario: 2組の問い
- **WHEN** 組が「範囲」と「欄」のQ3で、範囲はA、欄はYを選ぶ
- **THEN** 送る文のQ3の行は `Q3 ダイアログの既定値: 範囲はA、欄はY` になる

#### Scenario: 何も選ばず何も書かない
- **WHEN** Q5のすべての組で「選ばない（補足で答える）」を選び、自由記述を空のままにする
- **THEN** 送る文のQ5の行は `Q5 <題>: 回答なし` になる

### Requirement: 返答の文の送信
「この内容で返答」が押されたとき、`<switchboard-web>` は、送る文を、今の返答と同じ返答のPOSTで、issueへのコメントとして投稿しなければならない（MUST）。
そのissueが待ちでないとき、1件の表示は、「この内容で返答」を押せなくしなければならない（MUST）。

#### Scenario: この内容で返答する
- **WHEN** 計画の質問の待ちのissueで、「この内容で返答」を押す
- **THEN** 表示されていた送る文が、そのままissueのコメントとして投稿され、送ったことが表示される

#### Scenario: 選んでいる途中で待ちでなくなる
- **WHEN** 選んでいる途中で、フォージから別の返答が届いて、そのissueが待ちでなくなる
- **THEN** ボタン「この内容で返答」は押せなくなり、待ちでなくなったことが示される

### Requirement: 順番待ちの表示
WUIは、一覧の「実行中」の節の下に「順番待ち」の節を出さなければならない（MUST）。各行には、順番待ちの印、当たった上限、順番待ちの経過時間を出す。
順番待ちのissueがあるとき、WUIは、ヘッダに順番待ちの件数も表示しなければならない（MUST）。
順番待ちのissueを選んだとき、1件の表示は、順番待ちであることと経過時間を示さなければならない（MUST）。
`agent:waiting` が付いた順番待ちのissueでは、1件の表示は、返答の欄を今までどおり使えるようにしなければならない（MUST）。

#### Scenario: 順番待ちのissueを選ぶ
- **WHEN** 順番待ちの節の行を選ぶ
- **THEN** 右のペインに、順番待ちの印と経過時間、順番待ちのコメントが出る

#### Scenario: 返答の待ちが順番待ちになる
- **WHEN** 開いている待ちのissueが、返答のあとで順番待ちになる
- **THEN** 一覧ではその行が順番待ちの節に移り、1件の表示の返答の欄は使えるままである

### Requirement: pushとCIの待ちの表示
一覧の画面と1件の画面は、待ちの理由 `push` と `ci` を、ほかの理由と同じく理由として表示しなければならない（MUST）。
理由が `ci` のとき、1件の画面は、返答の欄の近くに、返信すれば実行が再開し、自動で直す回数を数え直すことを示さなければならない（MUST）。
理由が `push` のとき、1件の画面は、返答の欄の近くに、トークンかリモートの設定を確かめる必要があることを示さなければならない（MUST）。

#### Scenario: CIの待ちを開く
- **WHEN** 理由が `ci` の待ちのissueを1件の画面で開く
- **THEN** 画面は、理由 `ci` と、返信で実行を再開できるという案内を表示し、承認のボタンを表示しない

#### Scenario: pushの待ちを一覧で見る
- **WHEN** 理由が `push` の待ちのissueがある
- **THEN** 一覧の画面のその行に、理由 `push` が表示される

### Requirement: 実行中の表示
一覧の画面は、待ちの欄とは別に、実行中のissueの欄を表示しなければならない（MUST）。実行中の行には、プロジェクトとissue番号、タイトル、端末の名前、経過時間、最新の進捗の1行を出す。
実行中のissueの1件の画面は、進捗のコメントの全文を表示し、返答の欄を表示してはならない（MUST NOT）。

#### Scenario: 実行中のissueを開く
- **WHEN** 一覧の実行中の欄の行を開く
- **THEN** 進捗のコメントの全文が出て、返答の欄は出ない

### Requirement: 新規issueのダイアログ
WUIは、一覧のペインの先頭に「新規issue」のボタンを表示しなければならない（MUST）。押すと、ダイアログを開く。
ダイアログは、プロジェクトの選択、タイトル、本文、開始ラベルの選択の4つを持たなければならない（MUST）。プロジェクトの選択肢は、作れる先の一覧のすべてのプロジェクトとし、各選択肢に担当の端末の名前を表示する。開始ラベルの初期値は `ready` とし、各選択肢にラベル名を表示する。
タイトルが空白だけのあいだ、WUIは作成のボタンを押せなくしなければならない（MUST）。
ダイアログは、ラベル名や、ほかの項目を入力させてはならない（MUST NOT）。

#### Scenario: ダイアログを開く
- **WHEN** 一覧の画面で「新規issue」を押す
- **THEN** ダイアログが開き、最初のプロジェクトと開始ラベル `ready` が選ばれている

#### Scenario: タイトルが無い
- **WHEN** 本文だけを書く
- **THEN** 作成のボタンは押せない

### Requirement: issueの作成の結果の表示
作成に成功したとき、WUIは、ダイアログを閉じ、成功のトーストで、作ったissueの参照とフォージのページへのリンクを表示しなければならない（MUST）。リンクは新しいタブで開く。一覧の上には知らせを残さない。
作成が拒まれたとき、WUIは、ダイアログの中に理由を表示し、書いた内容を残さなければならない（MUST）。

#### Scenario: 作れた
- **WHEN** `gl:nas/sb`に、タイトル「Add a flag」で種別`plan`のissueを作る
- **THEN** ダイアログが閉じ、成功のトーストで`gl:nas/sb#7 を作りました`と、フォージで開くリンクが表示される

#### Scenario: フォージが拒んだ
- **WHEN** フォージがissueの作成を拒む
- **THEN** ダイアログは開いたままで、理由が表示され、タイトルと本文は残る

### Requirement: issueの作成のPOSTの検査
issueの作成のPOSTについて、`<switchboard-web>` は、返答のPOSTと同じ検査をしなければならない（MUST）。本文がJSONであることと、`Origin` と `Host` が `<listen>` のアドレスと一致することである。どちらかに当たらないPOSTは、受信箱のサービスに渡してはならない（MUST NOT）。

#### Scenario: Originの無いPOST
- **WHEN** `Origin` の無いPOSTで、issueの作成を求める
- **THEN** 403が返り、issueは作られない

### Requirement: 完了の表示
WUIは、一覧の「順番待ち」の節の下に「完了（close待ち）」の節を出さなければならない（MUST）。各行には、完了の印、端末、完了からの経過時間、PR/MRへのリンクを出す。PR/MRへのリンクは、issueの行のリンクとは別のリンクにする。
完了のissueがあるとき、WUIは、ヘッダに完了の件数も表示しなければならない（MUST）。1件も無いときは出さない。
完了のissueを選んだとき、1件の表示は、完了の印と返答の欄を出さなければならない（MUST）。返答を送ると、エージェントが同じPR/MRで作業を再開する。

#### Scenario: 完了のissueが一覧に出る
- **WHEN** openのまま `agent:done` のissueが1件ある状態で一覧を開く
- **THEN** 順番待ちの節の下の完了の節にその行とPRへのリンクが出て、ヘッダに完了の件数が1と出る

#### Scenario: 完了のissueに返答する
- **WHEN** 完了の節の行を選ぶ
- **THEN** 1件の表示に完了の印と返答の欄が出て、返答を送れる

### Requirement: 自動更新の速さの表示
知らせの接続がつながっている間、WUIは、ヘッダの自動更新の表示を、一覧の `relay` で分けなければならない（MUST）。`connected` なら「自動更新中（即時）」、`disconnected` なら「自動更新中（N秒ごと）」とする。Nは一覧の `refresh_interval_seconds` である。空なら「自動更新中」とする。
知らせの接続が切れている間、WUIは、中継の状態にかかわらず、切れていて再接続を試みていることを示さなければならない（MUST）。
WUIは、中継の状態で、ヘッダの状態の点の印を変えてはならない（MUST NOT）。

#### Scenario: 中継が切れる
- **WHEN** 画面を開いている間に、中継が止まる
- **THEN** ヘッダの表示が「自動更新中（即時）」から「自動更新中（30秒ごと）」に変わり、点は塗られたままである

### Requirement: トースト
WUIは、一時的な知らせをトーストとして、受信箱と設定のどちらの画面でも表示できなければならない（MUST）。
トーストの種類は、通常、成功、警告、誤りの4つとし、種類ごとにDESIGN.mdの色と印を付ける。
トーストは✗のボタンを持ち、押すと消えなければならない（MUST）。
トーストは、既定では5秒で消えなければならない（MUST）。表示時間は、トーストを出す側が指定できる。マウスがトーストの上にある間と、フォーカスがトーストの中にある間は、時間を数えてはならない（MUST NOT）。
複数のトーストは、重ねずに縦へ並べ、新しいものを最も下に置く。同時に表示するのは5個までとし、6個目を出すときは最も古いものを消す。
トーストは画面の右下に出す。幅1024px未満では、下の端に全幅で出す。
誤りのトーストは`role="alert"`、ほかの種類は`role="status"`で読み上げさせる。

#### Scenario: 5秒で消える
- **WHEN** 表示時間を指定せずに、成功のトーストを出す
- **THEN** トーストが右下に表示され、5秒たつと消える

#### Scenario: マウスを載せている
- **WHEN** トーストを出した1秒後にマウスを載せ、10秒たってからマウスを外す
- **THEN** マウスを載せている間は消えず、外してから4秒たつと消える

#### Scenario: 6個目を出す
- **WHEN** 5個のトーストが表示されている間に、6個目を出す
- **THEN** 最も古いトーストが消え、表示は5個のままになる

### Requirement: 設定の画面の保存の結果
追加の指示の保存に成功したとき、WUIは、保存した欄の名前と、保存したことを、成功のトーストで表示しなければならない（MUST）。
保存の誤りは、トーストにせず、その欄の中に表示しなければならない（MUST）。

#### Scenario: 指示を保存する
- **WHEN** 設定の画面で、`gl:nas/sb`の計画の指示の欄に指示を書いて保存する
- **THEN** `nas/sb GitLabの計画の指示を保存しました`という成功のトーストが表示され、欄の中には知らせが残らない

### Requirement: 1件の表示の位置と固定の見出し
待ちのissueを開いた直後、WUIは、エージェントの最新の質問のカードが見出しの直下に来るようにスクロールしなければならない（MUST）。完了のissueでは、エージェントの最新の完了の報告のカードへ、それが無ければスレッドの最後のカードへスクロールしなければならない（MUST）。ほかの状態のissueでは、スクロールしてはならない（MUST NOT）。
このスクロールは、issueを開くごとに1回だけでなければならない（MUST）。前回読んだ内容を先に出したときは、それを描いた時点で1回とし、後から届いた読み直しではスクロールしてはならない（MUST NOT）。
開いている間の読み直しで、表示するカードが増えたとき、WUIは、スクロールの位置を変えずに、画面の下に「自動更新がありました」の知らせを出さなければならない（MUST）。進捗のカードが書き換わったときも、カードが増えたものとして扱う。状態や時刻だけが変わったときは、知らせを出してはならない（MUST NOT）。
知らせを押したとき、WUIは、待ちと完了のissueでは開いた直後と同じカードへ、ほかの状態では新しく加わったカードの最初のものへスクロールし、知らせを消さなければならない（MUST）。行き先のカードが画面に入ったときと、別のissueへ移ったときも、知らせを消さなければならない（MUST）。
1件の表示の「← 一覧へ」（幅1024px未満）、参照、タイトル、状態の行は、スクロールしても上に残らなければならない（MUST）。完了のissueでマージのボタンを出すときは、状態の行の下のPR/MRのリンク、マージのボタン、自動マージを取り消すボタンも、スクロールしても上に残らなければならない（MUST）。スクロールが一番上でないとき、タイトルは2行までにして、全文をtitle属性に持たせる。一番上では全文を出す。

#### Scenario: 待ちのissueを開く
- **WHEN** 最新の質問の後に人のコメントがある待ちのissueを開く
- **THEN** 最新の質問のカードへスクロールする

#### Scenario: 完了のissueを開く
- **WHEN** 完了の報告の後に人のコメントがある完了のissueを開く
- **THEN** 完了の報告のカードへスクロールする

#### Scenario: 実行中のissueを開く
- **WHEN** 実行中のissueを開く
- **THEN** スクロールしない

#### Scenario: 開いている間にカードが増える
- **WHEN** 待ちのissueを開いたまま、人のコメントが付いて読み直しが届く
- **THEN** スクロールの位置は変わらず、画面の下に「自動更新がありました」が出る

#### Scenario: 状態だけが変わる
- **WHEN** issueを開いたまま、カードは同じで状態と時刻だけが変わった読み直しが届く
- **THEN** 知らせは出ない

#### Scenario: 知らせを押す
- **WHEN** 実行中のissueを開いたまま、待ちになって進捗と質問のカードが加わり、知らせを押す
- **THEN** 質問のカードへスクロールし、知らせが消える

### Requirement: 受信箱のサービスより先に起動したときのつなぎ
`<web.yaml>` の `socket` が空のとき、`<switchboard-web>` は、受信箱のサービスのソケットの場所を、起動時でなく要求ごとに探さなければならない（MUST）。

#### Scenario: まとめて再起動する
- **WHEN** 3つのサービスをまとめて再起動し、`<switchboard-web>` が `switchboard inbox serve` より先に起動する
- **THEN** 受信箱のサービスがソケットを作ったあとは、`<switchboard-web>` を再起動しなくても、一覧の画面に一覧が出る

### Requirement: 一覧のペインの幅
幅1024px以上の間、WUIは、一覧のペインと1件のペインの境目を、`role="separator"`の要素として置かなければならない（MUST）。幅1024px未満の間、WUIは、境目を表示してはならない（MUST NOT）。
一覧のペインの幅は、既定で360pxとし、280px以上640px以下でなければならない（MUST）。ウィンドウの幅から480pxを引いた値が上限より小さいとき、WUIは、その値を上限としなければならない（MUST）。ただし、280pxを下回らせてはならない（MUST NOT）。
境目をドラッグしたとき、WUIは、一覧の幅をドラッグに合わせて変えなければならない（MUST）。
境目にフォーカスがある間、WUIは、左右の矢印キーで幅を16pxずつ変え、Homeで280px、Endで640pxにしなければならない（MUST）。いずれも上の範囲に収める。
境目をダブルクリックしたとき、WUIは、一覧の幅を360pxに戻さなければならない（MUST）。
一覧の幅を変えたとき、WUIは、その幅をブラウザに保存しなければならない（MUST）。次に開いたとき、WUIは、保存した幅を上の範囲に収めて使わなければならない（MUST）。保存した値が数でないときは、既定の幅を使う。
ウィンドウの幅が変わったとき、WUIは、保存した幅を新しいウィンドウの幅で範囲に収め直さなければならない（MUST）。

#### Scenario: 既定の幅で開く
- **WHEN** 幅1440pxのブラウザで、幅を保存していない状態で一覧の画面を開く
- **THEN** 一覧のペインは360pxで、境目の値も360である

#### Scenario: 矢印キーで動かす
- **WHEN** 境目にフォーカスを置き、右の矢印キーを2回、左の矢印キーを1回押す
- **THEN** 一覧の幅は376pxになり、その幅が保存される

#### Scenario: ドラッグで最小を下回る
- **WHEN** 境目を左へ大きくドラッグする
- **THEN** 一覧の幅は280pxで止まる

#### Scenario: ダブルクリックで戻す
- **WHEN** 幅500pxを保存した状態で開き、境目をダブルクリックする
- **THEN** 一覧の幅は360pxに戻る

#### Scenario: 狭いウィンドウ
- **WHEN** 幅640pxを保存した状態で、幅1024pxのブラウザで開く
- **THEN** 一覧の幅は544pxになり、右のペインに480pxが残る

#### Scenario: スマホの幅で開く
- **WHEN** 幅360pxのブラウザで一覧の画面を開く
- **THEN** 境目は出ず、横へのスクロールも出ない

### Requirement: ヘッダの名前
WUIのヘッダは、名前として「SwitchBoard Inbox」を表示しなければならない（MUST）。名前は一覧の画面へのリンクとする。
幅640px未満の画面では、WUIのヘッダは、名前を「SwitchBoard」に縮めて表示しなければならない（MUST）。

#### Scenario: デスクトップの幅で開く
- **WHEN** 幅1280pxのブラウザで一覧の画面を開く
- **THEN** ヘッダの見出しに「SwitchBoard Inbox」が出る

#### Scenario: スマホの幅で開く
- **WHEN** 幅360pxのブラウザで一覧の画面を開く
- **THEN** ヘッダの見出しには「SwitchBoard」だけが出る

### Requirement: マージのボタン
完了のissueの `change_number` と `change_sha` があるとき、WUIは、一覧の完了の行と1件の表示に「マージ」のボタンを出さなければならない（MUST）。一覧の行では、ボタンをPR/MRのリンクの隣で、行のリンクの外に置く。1件の表示では、ボタンを固定の見出しの状態の行の下に、PR/MRのリンクと並べて1か所だけ置く。
`change_number` か `change_sha` が無いとき、WUIは、マージのボタンを出してはならない（MUST NOT）。
WUIは、GitHubのPR/MRを `PR #N`、GitLabのPR/MRを `MR !N` と表記しなければならない（MUST）。

#### Scenario: 完了の行のボタン
- **WHEN** `change_number` が73で `change_sha` のある完了の行を、一覧で見る
- **THEN** PRのリンクの隣にマージのボタンが出て、ボタンを押しても1件の表示には移らない

#### Scenario: 古い完了
- **WHEN** `change_number` の無い完了のissueを選ぶ
- **THEN** 1件の表示にマージのボタンは出ない

#### Scenario: 長いスレッドを下まで読む
- **WHEN** `change_number` と `change_sha` のある完了のissueを開き、スレッドの末尾までスクロールする
- **THEN** マージのボタンとPR/MRのリンクは、固定の見出しの中に見えたままである

### Requirement: マージの確認のダイアログ
マージのボタンを押したとき、WUIは、送る前に確認のダイアログを開かなければならない（MUST）。ダイアログには、マージするPR/MRの名前、取り消せないことの1文、PR/MRへのリンク、「やめる」と「マージする」のボタンを出す。
ダイアログで「やめる」を押したとき、WUIは、マージを送ってはならない（MUST NOT）。
送っている間、WUIは、ダイアログの両方のボタンを押せなくし、送信中であることを示さなければならない（MUST）。

#### Scenario: やめる
- **WHEN** マージのボタンを押し、ダイアログで「やめる」を押す
- **THEN** ダイアログが閉じ、マージの要求は送られない

#### Scenario: マージする
- **WHEN** マージのボタンを押し、ダイアログで「マージする」を押す
- **THEN** 行か詳細が示すissueと `change_sha` を付けて、マージの要求が送られる

### Requirement: マージの結果の表示
マージの結果が返ったとき、WUIは、ダイアログを閉じ、結果をトーストで表示しなければならない（MUST）。成功は成功のトースト、断られたときは誤りのトーストとし、誤りのトーストは理由を2行目に出す。
WUIは、マージの誤りをダイアログの中に残してはならない（MUST NOT）。
権限が無いと断られたとき、誤りのトーストは、受信箱のトークンに要る権限を名指さなければならない（MUST）。

#### Scenario: マージできた
- **WHEN** ダイアログで「マージする」を押し、マージが成功する
- **THEN** ダイアログが閉じ、`PR #73をマージしました` の成功のトーストが出る

#### Scenario: 画面が古い
- **WHEN** 画面を読んだ後にPRへコミットが足され、マージが `stale` で断られる
- **THEN** ダイアログが閉じ、開き直すよう促す誤りのトーストが出る

#### Scenario: 権限が無い
- **WHEN** マージが `forbidden` で断られる
- **THEN** 誤りのトーストに、GitHubの `Pull requests` と `Contents` の書き込みと、GitLabの `api` のスコープが出る

### Requirement: マージのPOSTの検査
マージのPOSTについて、`<switchboard-web>` は、返答のPOSTと同じ検査をしなければならない（MUST）。本文がJSONであることと、`Origin` と `Host` が `<listen>` のアドレスと一致することである。
どちらかに当たらないPOSTを、`<switchboard-web>` は受信箱のサービスに渡してはならない（MUST NOT）。

#### Scenario: 外のWebページから送られる
- **WHEN** 別のオリジンのWebページが、WUIのマージのURLへPOSTを送る
- **THEN** 403が返り、PR/MRはマージされない

### Requirement: 返答の書きかけの保持
別のissueを開いたとき、WUIは、前のissueの返答の書きかけと選んだ答えを、issueごとに残さなければならない（MUST）。前のissueを開き直したとき、WUIは、残した書きかけと答えを返答の欄に戻さなければならない（MUST）。
WUIは、書きかけをメモリにだけ置かなければならない（MUST）。書きかけをブラウザのストレージへ書いてはならない（MUST NOT）。ページを読み込み直すと、書きかけは消える。
返答を送れたとき、WUIは、そのissueの書きかけを消さなければならない（MUST）。

#### Scenario: 別のissueへ移って戻る
- **WHEN** issue #12の返答の欄に「Use B.」と書き、一覧で#13を開いてから#12を開き直す
- **THEN** #13の返答の欄は空で、#12の返答の欄には「Use B.」が残っている

### Requirement: 返答の欄のキー操作
返答の欄にフォーカスがある間、Ctrl+Enter（macOSでは⌘+Enter）を押したとき、WUIは、「返答を送る」と同じく欄の文を送らなければならない（MUST）。
欄が空白だけのとき、送っている途中のとき、そのissueが返答を受け付けないときは、キーを押しても送ってはならない（MUST NOT）。

#### Scenario: Ctrl+Enterで送る
- **WHEN** 待ちのissueの返答の欄に「Use B.」と書き、Ctrl+Enterを押す
- **THEN** 返答のPOSTが送られる

### Requirement: 送ったあとのフォーカス
返答を送れたとき、WUIは、返答の欄の代わりに出る「送りました」の行へフォーカスを移さなければならない（MUST）。

#### Scenario: 返答を送る
- **WHEN** 返答の欄に文を書き、「返答を送る」を押す
- **THEN** フォーカスは「送りました」で始まる行にある

### Requirement: 返答の欄の案内の読み上げ
返答の欄の上に案内を出すとき、WUIは、その案内を返答の欄の説明として結ばなければならない（MUST）。

#### Scenario: CIの待ちの案内
- **WHEN** 理由が `ci` の待ちのissueを開く
- **THEN** 返答の欄の説明として、CIの失敗を自動で直す回数を数え直すという案内が読み上げられる

### Requirement: エージェントの投稿の書き手
1件の表示は、エージェントの投稿のカードに、書いた人のアカウント名を表示してはならない（MUST NOT）。カードの上には、エージェントの印と時刻だけを出す。
人のコメントのカードには、今までどおりアカウント名を出す。

#### Scenario: エージェントの質問のカード
- **WHEN** アカウント `bot` でエージェントが投稿した質問のあるissueを開く
- **THEN** そのカードには「エージェント」の印が出て、`bot` は出ない

### Requirement: 推奨の選択肢の印
計画の質問を表示する間、1件の表示は、推奨に当たる選択肢の文の後ろに「（推奨）」を表示しなければならない（MUST）。推奨に当たる選択肢は、推奨の既定の選択で選ぶものと同じである。

#### Scenario: 推奨のある問い
- **WHEN** 推奨が付いた計画の質問のissueを開く
- **THEN** 既定で選ばれた選択肢の文に「（推奨）」が付いている

### Requirement: 実行中の行の進捗
一覧の実行中の行は、進捗の行に `?` を表示してはならない（MUST NOT）。
進捗のコメントがまだ無いとき、一覧の実行中の行は、`進捗はまだありません`を表示しなければならない（MUST）。
進捗の行が `｜ ?` で終わるとき、一覧の実行中の行は、その末尾を除いて表示しなければならない（MUST）。

#### Scenario: 進捗がまだ無い
- **WHEN** 進捗が `?` の実行中のissueがある状態で一覧を開く
- **THEN** その行に`進捗はまだありません`が出る

#### Scenario: エージェントの言葉がまだ無い
- **WHEN** 進捗が `14:24 2分 Bash 1 ｜ ?` の実行中のissueがある状態で一覧を開く
- **THEN** その行には `14:24 2分 Bash 1` が出る

### Requirement: 一覧の質問の冒頭
一覧の待ちの行は、質問の冒頭を、Markdownの太字とコードの記号を除いた文として表示しなければならない（MUST）。行頭の見出しの記号も除く。

#### Scenario: 太字とコードを含む質問
- **WHEN** 質問の冒頭が ``1. **設定（`a.go`）** - `Agent` に…`` の待ちのissueがある状態で一覧を開く
- **THEN** その行には`1. 設定（a.go） - Agent に…`が出る

### Requirement: 返答待ちの節の見出し
一覧を受け取った後、WUIは、待ちのissueの節に「返答待ち」の見出しを付けなければならない（MUST）。待ちのissueが無いときも、見出しの下に、待ちのissueが無いことを示す。

#### Scenario: 待ちのissueがある
- **WHEN** 待ちのissueが1件ある状態で一覧を開く
- **THEN** 見出し「返答待ち」の下に、その行が出る

### Requirement: 完了のPR/MRのリンクの名前
PR/MRの番号が分かるとき、WUIは、完了のPR/MRへのリンクを、GitHubでは `PR #N`、GitLabでは `MR !N` と表示しなければならない（MUST）。リンクの行き先はPR/MRのURLのままとする。
一覧の完了の行と1件の表示のどちらも、この名前を使う。番号が分からないとき、一覧の完了の行は、URLをそのまま表示する。

#### Scenario: 番号の分かる完了
- **WHEN** PR #9のURLと番号を持つ完了のissueがある状態で一覧を開く
- **THEN** 完了の行に`PR #9` のリンクが出て、行き先はPR #9のURLである

### Requirement: 一覧と設定の読み込みの表示
一覧を受け取るまでの間、WUIは、一覧の代わりに、回るアイコンと`読み込んでいます`を表示しなければならない（MUST）。
設定の画面のプロジェクトの節と指示の節は、それぞれの内容を受け取るまでの間、回るアイコンと`読み込んでいます`を表示しなければならない（MUST）。
新規issueのダイアログは、作れる先の一覧を受け取るまでの間、回るアイコンと`読み込んでいます`を表示しなければならない（MUST）。
読み込みに失敗したときは、`読み込んでいます`の代わりに誤りを示す。

#### Scenario: 一覧がまだ届かない
- **WHEN** 受信箱のサービスが一覧をまだ返さない間に、一覧の画面を開く
- **THEN** `読み込んでいます`が出る

#### Scenario: 設定がまだ届かない
- **WHEN** プロジェクトと指示の一覧がまだ届かない間に、設定の画面を開く
- **THEN** 2つの節のそれぞれに`読み込んでいます`が出る

#### Scenario: 作れる先がまだ届かない
- **WHEN** 作れる先の一覧がまだ届かない間に、「新規issue」を押す
- **THEN** ダイアログの中に`読み込んでいます`が出る

### Requirement: タブのタイトル
WUIは、ブラウザのタブのタイトルを、画面の名前と「SwitchBoard Inbox」を ` - ` でつないだものにしなければならない（MUST）。画面の名前は、1件の画面ではissueのタイトル、設定の画面では「設定」とする。一覧だけの画面では、名前を付けずに「SwitchBoard Inbox」とする。
待ちのissueが1件以上ある間、WUIは、タブのタイトルの先頭に`(N) ` の形で待ちの件数を付けなければならない（MUST）。

#### Scenario: 一覧の画面
- **WHEN** 待ちのissueが1件ある状態で一覧の画面を開く
- **THEN** タブのタイトルは`(1) SwitchBoard Inbox`になる

#### Scenario: 1件の画面
- **WHEN** 待ちのissue「Add a flag」を開く
- **THEN** タブのタイトルは`(1) Add a flag - SwitchBoard Inbox`になる

#### Scenario: 設定の画面
- **WHEN** 待ちのissueが無い状態で設定の画面を開く
- **THEN** タブのタイトルは`設定 - SwitchBoard Inbox`になる

### Requirement: ヘッダの件数の読み上げ
WUIのヘッダは、件数を、画面に出す短い表記とは別に、読み上げ用の文として持たなければならない（MUST）。文は「待ちN件、実行中N件」とし、順番待ちと完了は1件以上のときだけ「、順番待ちN件」「、完了N件」を足す。
画面に出す短い表記は、読み上げさせてはならない（MUST NOT）。

#### Scenario: 4種類の件数がある
- **WHEN** 待ち、実行中、順番待ち、完了のissueが1件ずつある状態で一覧を開く
- **THEN** ヘッダに「待ち1件、実行中1件、順番待ち1件、完了1件」の読み上げ用の文がある

### Requirement: 参照とフォージのバッジ
WUIは、issueとプロジェクトの参照を、`gh:`と`gl:`のプレフィックスを外した形で表示しなければならない（MUST）。
WUIは、参照のすぐ後ろに、フォージのバッジを表示しなければならない（MUST）。バッジの文字は、`gh:`なら「GitHub」、`gl:`なら「GitLab」とする。
バッジの色はフォージごとに分ける。色は補助とし、フォージは文字で読み取れなければならない（MUST）。
この形は、一覧の行、1件の表示の見出し、プロジェクトの節のカード、新規issueの作成のトースト、プロジェクトの追加のトースト、指示の欄の名前に使う。
どちらのプレフィックスも無い参照は、そのまま表示し、バッジを付けてはならない（MUST NOT）。

#### Scenario: 一覧の行
- **WHEN** 一覧に`gh:o/r#12`のissueがある
- **THEN** 行には`o/r#12`と「GitHub」のバッジが並び、`gh:o/r#12`の文字は出ない

#### Scenario: GitLabのissue
- **WHEN** `gl:nas/sb#3`のissueを開く
- **THEN** 見出しには`nas/sb#3`と「GitLab」のバッジが並ぶ

### Requirement: 参照の形を変えない箇所
参照の表示を変えたあとも、URL、APIに送る`ref`、プロジェクトの追加の欄の入力の形（`gh:owner/repo`）は、変えてはならない（MUST NOT）。

#### Scenario: 1件の表示へのリンク
- **WHEN** 一覧で`gh:o/r#12`の行のリンク先を見る
- **THEN** リンク先は`/issue/gh%3Ao%2Fr%2312`のままである

### Requirement: 新規issueのプロジェクトの選択肢
新規issueのダイアログのプロジェクトの選択肢は、プレフィックスを外した参照とフォージの名前を、「o/r GitHub（担当：desk）」の形の文字で表示しなければならない（MUST）。

#### Scenario: 選択肢を見る
- **WHEN** 端末`desk`の担当する`gh:o/r`がある端末で、新規issueのダイアログを開く
- **THEN** プロジェクトの選択肢に「o/r GitHub（担当：desk）」が出る

### Requirement: 実行の失敗の待ちの案内
理由が `error` の待ちの間、1件の画面は、返答の欄の近くに、「再実行する」で同じ作業をやり直せることと、直し方は返答の欄に書いて「返答を送る」で伝えることを示さなければならない（MUST）。

#### Scenario: 実行の失敗の待ちを開く
- **WHEN** 理由が `error` の待ちのissueを1件の画面で開く
- **THEN** 返答の欄の近くに、実行が失敗したことと「再実行する」の使い方を示す案内が表示される

### Requirement: 再実行のボタン
理由が `error` の待ちの間、1件の画面は、「再実行する」のボタンを主のボタンとして置かなければならない（MUST）。
「再実行する」を押したとき、1件の画面は、確認を挟まずに、再実行を頼む決まった文だけを返答のPOSTで1回投稿しなければならない（MUST）。
理由が `error` の待ちの間、1件の画面は、「返答を送る」を副のボタンとして「再実行する」と並べなければならない（MUST）。

#### Scenario: 空の欄で再実行のボタンを押す
- **WHEN** 理由が `error` の待ちのissueで、返答の欄が空のまま「再実行する」を押す
- **THEN** 再実行を頼む決まった文だけが1回、issueへのコメントとして投稿され、「送りました」が表示される

#### Scenario: 欄が空の間は返答を送れない
- **WHEN** 理由が `error` の待ちのissueを、返答の欄が空のまま開いている
- **THEN** 画面の「再実行する」は押せ、「返答を送る」は押せない

### Requirement: 欄に文があるときの再実行のボタン
返答の欄に空白以外の文がある間、1件の画面は、「再実行する」を押せなくしなければならない（MUST）。

#### Scenario: 返答の欄に直し方を書く
- **WHEN** 理由が `error` の待ちのissueで、返答の欄に直し方の文を書き、「返答を送る」を押す
- **THEN** 書いている間「再実行する」は押せず、書いた文がそのままissueへのコメントとして投稿される

### Requirement: 待ちでないときの再実行のボタン
issueが待ちでない間、1件の画面は、「再実行する」を押せるように出してはならない（MUST NOT）。

#### Scenario: 実行中になったissueを開く
- **WHEN** 最後の理由が `error` のissueが、実行中か順番待ちになっている
- **THEN** 画面の「再実行する」は表示されないか、押せない

### Requirement: ほかの失敗の理由では再実行のボタンを出さない
理由が `verify`、`permission`、`push`、`ci` の待ちの間、1件の画面は、「再実行する」のボタンを置いてはならない（MUST NOT）。

#### Scenario: CIの待ちを開く
- **WHEN** 理由が `ci` の待ちのissueを1件の画面で開く
- **THEN** 画面に「再実行する」のボタンは表示されない

#### Scenario: 出力検査の待ちを開く
- **WHEN** 理由が `verify` の待ちのissueを1件の画面で開く
- **THEN** 画面に「再実行する」のボタンは表示されない

### Requirement: 完了のカードの操作
一覧が完了の行をカードで示す間、WUIは、PR/MRへのリンクとマージのボタンを、そのカードの枠の中に置かなければならない（MUST）。
一覧が完了の行をカードで示す間、WUIは、PR/MRへのリンクとマージのボタンを、1件へのリンクの中に置いてはならない（MUST NOT）。
一覧が完了の行をカードで示す間、WUIは、1件へのリンクとPR/MRの行の間を、`outline`の線で区切らなければならない（MUST）。
カードの形は、幅640px未満の一覧と、幅1024px以上の左のペインで使う。

#### Scenario: 完了のカードの操作は枠の中にある
- **WHEN** PR #9の番号とコミットを持つ完了のissueを選び、左のペインのカードを見る
- **THEN** そのカードの枠の中に、`PR #9`のリンクと「PR #9をマージ」のボタンがある

#### Scenario: 操作は1件へのリンクの外にある
- **WHEN** PR #9の番号とコミットを持つ完了のissueを選び、左のペインのカードを見る
- **THEN** `PR #9`のリンクと「PR #9をマージ」のボタンは、`aria-current="page"`の付いた1件へのリンクの中に無い

### Requirement: 一覧の節のプロジェクトのサブグループ
プロジェクトでまとめる間、一覧は、4つの節（返答待ち・実行中・順番待ち・完了）の行を、節ごとにプロジェクトのサブグループに分けて表示しなければならない（MUST）。
各サブグループは、プロジェクトの参照、フォージのバッジ、行の件数からなる見出しを持たなければならない（MUST）。
節の中のプロジェクトが1つだけのときも、一覧は、サブグループの見出しを表示しなければならない（MUST）。
サブグループの中の行は、今までどおりissueの参照とフォージのバッジを表示しなければならない（MUST）。
フォージが違う同名のリポジトリの行を、一覧は、同じサブグループにまとめてはならない（MUST NOT）。

#### Scenario: 2つのプロジェクトの待ちがある
- **WHEN** `o/a` の待ちが始まって5分、`o/b` の待ちが始まって10分と1分のissueがある一覧を開く
- **THEN** 返答待ちの節に、`o/b`［GitHub］2件の見出しが先、`o/a`［GitHub］1件の見出しが後に出て、`o/b` の下には10分のissue、1分のissueの順で行が出る

#### Scenario: プロジェクトが1つだけ
- **WHEN** 実行中のissueが1つのプロジェクトの1件だけの一覧を開く
- **THEN** 実行中の節に、そのプロジェクトの参照、バッジ、1件の見出しが出て、その下に行が出る

#### Scenario: GitHubとGitLabの同名のリポジトリ
- **WHEN** `gh:o/r` と `gl:o/r` のそれぞれに待ちのissueがある一覧を開く
- **THEN** 返答待ちの節に、`o/r`［GitHub］と`o/r`［GitLab］の2つのサブグループが出る

### Requirement: まとめる表示の切り替え
一覧は、ペインの先頭に、プロジェクトでまとめるかどうかを切り替えるトグルボタンを表示しなければならない（MUST）。
トグルボタンは、オンかオフかを支援技術に伝えなければならない（MUST）。
一度も切り替えていないブラウザで開いたとき、一覧は、プロジェクトでまとめて表示しなければならない（MUST）。
トグルボタンを押したとき、一覧は、4つの節をそろえて切り替えなければならない（MUST）。
トグルボタンを押したとき、WUIは、選んだ状態をそのブラウザに保存しなければならない（MUST）。
保存した状態があるとき、WUIは、開き直した一覧にその状態を使わなければならない（MUST）。

#### Scenario: 初めて開く
- **WHEN** 一度も切り替えていないブラウザで一覧を開く
- **THEN** 各節がプロジェクトのサブグループにまとまって出て、トグルボタンは押された状態になっている

#### Scenario: まとめない表示に切り替える
- **WHEN** 待ちと実行中のissueがある一覧で、トグルボタン「プロジェクトでまとめる」を押す
- **THEN** 4つの節のサブグループの見出しが消えて、行が古い順で出て、トグルボタンは押されていない状態になる

#### Scenario: 開き直しても残る
- **WHEN** トグルボタンでまとめない表示に切り替えてから、ページを再読み込みする
- **THEN** 一覧はまとめない表示のまま出る
