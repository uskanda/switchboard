# 設計判断の記録（ADR）

形式：番号 / 状態（採用・保留・却下）/ 決定 / 理由。覆す場合は新しい番号で追加し、旧 ADR に「置換」を記す。

## ADR-001 自作する（採用）
- 決定：既存 OSS を採用せず、自作する
- 理由：要件（issue 駆動・複数端末・GitHub/GitLab 両対応・ローカル文脈）をそのまま満たす広く使われた製品がない。類似 OSS は小規模な個人プロジェクトで、保守継続性と監査コストに懸念がある。信頼境界を自分で引けることを重視する。既存 OSS は設計の参考に留める

## ADR-002 稼働中セッションへの直接注入はしない（採用）
- 決定：Channels 等による稼働中対話セッションへのメッセージ注入は採用しない
- 理由：外部からの注入口は実質的にリモート実行の入口になり、リスクが大きい。issue 駆動で同等の目的を達成できる

## ADR-003 issue を制御面とする（採用）
- 決定：作業単位・状態・応答経路を issue（ラベル・コメント）に統一する
- 理由：認証・認可・監査をフォージに委ねられる。フォージのモバイルアプリが応答 UI になる。トレンド（OpenAI Symphony 等）とも一致

## ADR-004 中継は ID 通知のみ（採用）
- 決定：中継は issue の識別子とイベント種別だけを流し、本文はローカルが再取得する
- 理由：中継が侵害されても内容を注入できない

## ADR-005 状態は issue とリポジトリに置き、resume は最適化扱い（採用）
- 決定：毎回まっさらな文脈で起動できる設計を基本とする。`--resume` は同一端末・新しいセッションに限り使い、失敗時は通常起動にフォールバック
- 理由：対話セッションとの競合リスクを避け、端末をまたいでも同じ状態から再開できる（Ralph 型ループの考え方）

## ADR-006 横断受信箱はローカルで集約（採用）
- 決定：受信箱は中継ではなくローカルの CLI が両フォージを直接検索して作る
- 理由：中継にタイトル等を持たせると ADR-004 が崩れる。フォージ単体のラベル検索で必要な情報は取れる

## ADR-007 中継の公開方法（採用、2026-10-30）
- 決定：当面は公開しない。中継のwebhookの受け口は `127.0.0.1` で待ち、同じ端末のGitLabからだけ受ける（受け口をLANのアドレスで待つことは、ADR-060で認めた）。GitLabには、ローカルへの送信の許可リストに受け口のアドレスだけを足してもらい、全体の許可はしない。公開の受け口が要るGitHubは、当面ポーリングで扱う。公開するときは、中継用のサーバーを別に用意して改めて決める
- 理由：受け口を公開すると、外から届く範囲が広がる。すぐに使うGitLabは同じ端末にあるので、公開しなくても受けられる。Tailscale Funnelなどの候補は、別のサーバーを用意するときに比べる（grilling `add-phase4-relay` 第1ラウンドQ1、Q2、第2ラウンドQ7）

## ADR-008 受信箱用トークンの分離（保留）
- 論点：受信箱（読み取り＋コメント）とエージェント（PR 作成まで）でトークンを分けるか

## ADR-009 状態ラベル（採用）
- 決定：`agent:ready` / `agent:running` / `agent:waiting` / `agent:done` の 4 種。`switchboard labels sync` で全リポジトリに統一作成
- 理由：状態を少数に保ち、フォージの検索だけで受信箱が作れるようにする

## ADR-010 技術スタック（採用、2026-10-29）
- 候補：Go（単一バイナリで配布しやすい、常駐向き）/ Python（試作が速い）/ TypeScript（Claude Code・gh 周辺との親和性）
- 論点：複数端末への配布のしやすさ、常駐プロセスの安定性、フォージ SDK の充実度
- 決定：Goを使う。CLI、常駐エージェント、フック、中継を、1つのバイナリのサブコマンドとして作る。WUIはこの範囲の外とする（ADR-037）
- 理由：macOSとLinuxの端末に単一バイナリで配れる。常駐、SSE、並行処理を標準ライブラリで書ける。GitHubとGitLabのGo SDKがある（grilling `add-phase1-minimal` 第2ラウンドQ1）

## ADR-011 フォージへの書き込みはエージェントが行う（採用、2026-10-29）
- 決定：issueへのコメントとラベルの付け替えは、親のエージェントだけが行う。フックはフォージと通信せず、ローカルでの検査だけを受け持つ
- 理由：フックはClaude Codeの子プロセスで動くため、フックにトークンを渡すと、Claudeのツール実行からもトークンに届く。書き手を1つにすると、ラベルの付け替えと二重投稿の防止を1か所で扱える。設計はDESIGN.mdの4.3節と4.5節にある（grilling `add-phase1-minimal` 第2ラウンドQ2）

## ADR-012 pushとPRの作成はエージェントが行う（採用、2026-10-29）
- 決定：pushとPR（GitLabではMR）の作成は、親のエージェントが行う。Claude Codeのプロセスにはフォージのトークンを渡さず、Claudeはローカルでのコミットまでを行う
- 理由：プロンプトインジェクションを受けたときに、任意のpushやトークンの持ち出しを防げる。push前に、差分の保護パスと秘密情報を検査できる。設計はDESIGN.mdの6.3節にある（grilling `add-phase1-minimal` 第2ラウンドQ2）

## ADR-013 終了プロトコル（採用、2026-10-29）
- 決定：各実行は、`--json-schema` の構造化出力で `waiting` か `done` を宣言して終える。宣言が無い場合と異常終了は、理由を `error` とする待ちにする
- 理由：Phase 0で、構造化出力がresultの `structured_output` に入ることを確かめた（V8）。人間の入力を待って止まる状態が `-p` には無いため、終わり方を機械で判定できる形にする（grilling `add-phase1-minimal` 第6ラウンドQ2）

## ADR-014 信頼判定の対象の拡大（採用、2026-10-29）
- 決定：コメントの投稿者に加えて、issue本文の作成者と編集者、`agent:ready` を付けた人、コメントの編集者を確かめる。判定はログイン名ではなくユーザーIDで行う。Phase 1から入れる
- 理由：書き込み権限を持つ人は、他人のコメントや本文を編集できる。ログイン名は改名と再取得で持ち主が変わりうる（grilling `add-phase1-minimal` 第6ラウンドQ3）

## ADR-015 エージェントが投稿するアカウント（採用、2026-10-29）
- 決定：Phase 1は、エージェントもマスターと同じアカウントで投稿し、エージェントの投稿はマーカーで見分ける。別アカウントへの移行はPhase 3で行う
- 理由：Phase 1の目的は流れを通すことで、別アカウントの用意は後でもできる。同じアカウントではフォージのプッシュ通知が本人に届かないが、その分は受信箱で補う（grilling `add-phase1-minimal` 第1ラウンドQ4）

## ADR-016 実行中に届いたコメントの扱い（採用、2026-10-29）
- 決定：実行中に届いた信頼済みのコメントは、その実行が待ちで終わった後、直ちに次の入力として取り込む
- 理由：返答と実行が行き違っても、返答を取りこぼさない（grilling `add-phase1-minimal` 第6ラウンドQ4）

## ADR-017 GitLabのwebhookの検証方式（採用、2026-10-30）
- 決定：署名トークン（`webhook-signature`、HMAC-SHA256）で検証し、`webhook-timestamp` が5分を外れたものは破棄する。重複の除去には `webhook-id` を使う。署名トークンを使えないGitLabに限り、設定でプロジェクトごとに `gitlab_token: true` を指定して、`X-Gitlab-Token` の定数時間の比較を許す（受け口がループバックでないときは許さない。ADR-060で改めた）
- 理由：`X-Gitlab-Token` は平文の共有シークレットで、GitLab自身も非推奨としている。`gl.uskan.dev`（CE 19.5.1）では、APIから署名トークンを設定できた。署名も、文書の計算方法と一致した（V16、grilling `add-phase4-relay` 第1ラウンドQ5、第3ラウンドQ13）

## ADR-018 worktreeのClaude Code設定の検査（採用、2026-10-29）
- 決定：実行前に、worktreeの `.claude/`、`.mcp.json`、`CLAUDE.md`、`AGENTS.md` がベースブランチと一致するかを検査し、一致しなければ実行しない
- 理由：前回の実行でClaude自身が設定を書き換えると、次の実行でその設定が読み込まれる。ベースブランチと一致する設定は、マスターがコミットしたものなので信頼できる（grilling `add-phase1-minimal` 第6ラウンドQ1）

## ADR-019 「待ち」の定義（採用、2026-10-29）
- 決定：「待ち」は、実行が人間への質問を残して終わり、返答を待っている状態とする。Claude Codeが止まって入力を待つ状態は指さない
- 理由：`claude -p` は人間の入力を待って止まらず、承認の要るツール呼び出しは拒否して先へ進む。そのため、SPEC.md F2が前提にしたNotificationフックでの検知は、ヘッドレス実行では成り立たない（grilling `add-phase1-minimal` 第1ラウンドQ2）

## ADR-020 独立した製品として作る（採用、2026-10-29）
- 決定：switchboardを独立した製品として作り、`claude -p` を起動する実行器もswitchboardが持つ。uskn-harnessの `uskn-loop` は、switchboardが形になった時点で、switchboardを前提にした形へ整理する
- 理由：uskn-loopの受け付け条件（仕様PRとchangeが1つ）とswitchboardのissue駆動は前提が異なる。先にswitchboardを形にしてから、両者の役割分担を決め直す（grilling `add-phase1-minimal` 第1ラウンドQ1）

## ADR-021 ハーネスが無くても動く（採用、2026-10-29）
- 決定：最終的に単体のOSSとして公開するため、特定の開発ハーネスが無くても動く作りにする。検証コマンドとコメントの検査は、ハーネスの規約に頼らず、プロジェクトごとの設定で決める
- 決定：実行時は、Claude Codeのユーザー層の設定を読み込み、対象リポジトリのプロジェクト設定は読み込まない。ユーザー層にハーネスがあれば、そのフックとスキルも適用される（この項はADR-028で置換）
- 確かめ方：ハーネスを入れないCIで結合テストを実行する。製品のコードと既定の設定に `uskn` が現れないことを、テストで確かめる
- 理由：利用者の環境は開発者と同じではない。ユーザー層の設定を読み込めば、開発者の環境では手作業と同じ規約が自動実行にも適用される（grilling `add-phase1-minimal` 第2ラウンドQ3、第4ラウンドQ1・Q2・Q6）

## ADR-022 doneの条件と検証コマンド（採用、2026-10-29）
- 決定：doneの条件は、終了プロトコルでの `done` の宣言、検証の成功、push前の出力検査の3つとする。Phase 1では独立した監査役を入れない
- 決定：検証は、プロジェクトごとの設定 `verify_command` をエージェントが実行して確かめる。未設定のプロジェクトでは検証を省き、PRの本文に「検証なし」と書く
- 理由：ハーネスのStopフックは差し戻しの回数に上限があり、doneの判定に使うには足りない（grilling `add-phase1-minimal` 第2ラウンドQ4、第4ラウンドQ1）

## ADR-023 実行の隔離の段階（採用、2026-10-29）
- 決定：Phase 1は、Claude Codeに渡す環境変数から資格情報を除くだけにする。その代わり、対象を非公開リポジトリかつマスターだけが書けるissueに限る。専用のOSユーザーでの実行は、常駐化と同じPhase 3で入れる
- 理由：同じOSユーザーで動かす限り、Claudeは `~/.ssh` などの資格情報に届く。対象を限れば非信頼の入力が入らないため、Phase 1の目的には足りる（grilling `add-phase1-minimal` 第1ラウンドQ5）

## ADR-024 非信頼コメントの扱い（採用、2026-10-29）
- 決定：`trusted_authors` 以外のコメントは、既定ではプロンプトにまったく含めない。非公開リポジトリに限り、プロジェクトの設定で参考データとして含められる
- 理由：区切りタグで分けても、プロンプトインジェクションを防げる保証にならない（grilling `add-phase1-minimal` 第1ラウンドQ6）

## ADR-025 言語の方針（採用、2026-10-29）
- 決定：識別子、コードのコメント、CLIの出力は英語にする。docs/、ADR、OpenSpecの成果物は日本語で書き、英語版のREADMEは公開の準備で作る
- 決定：エージェントがissueに書くコメントの言語は設定で選び、既定は英語とする。投稿前の検査は任意の外部コマンド（`comment_check_command`）とし、既定では何もしない
- 理由：OSSの利用者に英語で読める製品にしつつ、開発中の文書は書き手の言語で進める（grilling `add-phase1-minimal` 第4ラウンドQ2・Q3）

## ADR-026 ライセンス（採用、2026-10-29）
- 決定：OSSとして公開するときのライセンスはMITとする（grilling `add-phase1-minimal` 第4ラウンドQ4）

## ADR-027 Claudeの認証方式（採用、2026-10-29）
- 決定：認証方式は設定で選べるようにし、既定はサブスクリプションとする。既定では、Claude Codeに渡す環境から `ANTHROPIC_API_KEY` を除く。APIキーは、利用者が明示的に設定したときだけ渡す
- 理由：`claude -p` は、`ANTHROPIC_API_KEY` があると常にそれを使う。除かないと、サブスクリプションの利用者もAPI課金で動いてしまう（grilling `add-phase1-minimal` 第4ラウンドQ5）

## ADR-028 プロジェクト設定も読み込む（採用、2026-10-29）
- 決定：実行時は、ユーザー層に加えて、対象リポジトリのプロジェクト設定も読み込む。ADR-018の検査で、設定がベースブランチと一致することを実行前に確かめる。ADR-021のうち、プロジェクト設定を読み込まないとした項を置き換える（ユーザー層を読み込む部分はADR-057で置換）
- 理由：Phase 0で、`--setting-sources user` ではプロジェクトの `CLAUDE.md` も読み込まれないと分かった（V17）。プロジェクト設定を外すと、リポジトリの指示がClaudeに届かない（grilling `add-phase1-minimal` 第6ラウンドQ1）

## ADR-029 最初に対応するOS（採用、2026-10-29）
- 決定：最初の実装はLinux（Ubuntu）向けとする。トークンはSecret Serviceに保管し、開発時に限り環境変数からも読めるようにする。Phase 1のエージェントもUbuntuの端末で動かす。macOSのキーチェーンと、systemdの暗号化クレデンシャルはPhase 3で扱う
- 理由：マスターの指定による（grilling `add-phase1-minimal` 第6ラウンドQ6）

## ADR-030 GitLabの扱い（採用、2026-10-30）
- 決定：設定できるGitLabのインスタンスは1つとし、`forges.gitlab` の `base_url` で指定する。既定は `https://gitlab.com` とする。プロジェクトは `gl:group/project` のパスで書き、サブグループも書ける。GitLabの `internal` のプロジェクトは、公開のプロジェクトとして数える
- 理由：公開したときに一番多い使い方はGitLab.comで、既定値があればそのまま使える。パスのほうが読んで分かる。`internal` は、インスタンスの全ユーザーが見てコメントできる。そのため、第三者の入力が入りうる（grilling `add-phase2-gitlab` 第3ラウンドQ12、第2ラウンドQ7、第5ラウンドQ18）

## ADR-031 エージェントの身元の上書き（採用、2026-10-30）
- 決定：エージェントのトークン（`token_ref`）と `agent_identity` は、組にしてプロジェクトの設定で上書きできる。片方だけの上書きは、設定の誤りとする。受信箱のトークン（`inbox_token_ref`）は、フォージに1つとし、上書きしない。上書きはGitHubとGitLabの両方で使える
- 理由：プロジェクトごとのProject Access Tokenやbotアカウントを使えば、エージェントの投稿を自分の投稿と分けられ、影響も1つのプロジェクトに限れる。従来のGitLabのPAT（`api` スコープ）は自分の全プロジェクトを操作できる。GitLab 19.2以降のfine-grainedのPATならプロジェクトを絞れるが、投稿者は自分のままで、switchboardでの動作も確かめていない。トークンの持ち主と `agent_identity` がずれると、エージェント自身の投稿を見分けられなくなる。受信箱は自分の身元で読み書きするので、上書きは要らない（grilling `add-phase2-gitlab` 第2ラウンドQ6、第3ラウンドQ11）

## ADR-032 常駐の形（採用、2026-10-30）
- 決定：Linuxでは、エージェントを `User=` に利用者のOSユーザーを指定したsystemdのシステムサービスとして常駐させる。この端末の担当プロジェクトのエージェント用トークンだけを、ホストの鍵で暗号化したsystemdのクレデンシャルにして渡す。受信箱のトークンは渡さない
- 理由：ログインしていないとgnome-keyringは解錠されず、Secret Serviceからトークンを読めない。systemd 255（Ubuntu 24.04）では、ユーザーサービスは暗号化したクレデンシャルを読めない。システムサービスなら、トークンを平文で置かずに再起動の後も自動で動かせる（grilling `add-phase3-multihost` 第1ラウンドQ4、第2ラウンドQ5、第3ラウンドQ10）

## ADR-033 端末をまたいだ重複の防止（採用、2026-10-30）
- 決定：エージェントは、マーカー付きの着手のコメントを投稿して取り直してから、`agent:running` へ付け替える。同じ `ack` の着手のコメントのうち、コメントIDが最も小さいものを出した端末だけが付け替えて実行する。退いた端末は、自分の着手のコメントを消し、ラベルに触れない
- 理由：エージェントは同じアカウントで投稿するので、ラベルだけではどの端末が着手したかを見分けられない。コメントIDはフォージが振るので、端末の時計を使わずに先後を決められる。付け替えを先にすると、退く端末がラベルを上書きしうる（grilling `add-phase3-multihost` 第1ラウンドQ2、第2ラウンドQ6、第3ラウンドQ12）

## ADR-034 sudoを要する操作（採用、2026-10-30）
- 決定：常駐の設定のうちsudoを要する操作は、`switchboard service install` と `uninstall` の中で行う。実行するコマンドを対象のパスとともに全部表示し、確認を取ってから、1つずつsudoで実行する。`--dry-run` は表示だけで終わり、端末が無いときは `--yes` が無ければ実行しない
- 理由：手順を利用者に打たせると、誤りやすい。一方で、何をrootで実行するかは、実行の前に読めなければならない（grilling `add-phase3-multihost` 第2ラウンドQ7、第3ラウンドQ9）

## ADR-035 中継の認証とシークレット（採用、2026-10-30）
- 決定：SSEの配信口は、webhookの受け口とは別のリスナーで待ち、端末ごとのbearerトークンで認証する。中継はトークンのSHA-256だけを設定に持つ。webhookのシークレットはプロジェクトごとに作り、推測できない `hook-key` で引く。シークレットとトークンはSecret Serviceに置き、常駐のときは暗号化したsystemdのクレデンシャルで渡す。webhookの登録は受信箱のトークンで行い、権限が足りなければ画面での登録を案内する。`switchboard` は設定ファイルを書き換えず、足す項目を表示する（設定ファイルの書き換えは、ADR-039でプロジェクトの追加に限って改めた）
- 理由：配信口と受け口を分ければ、受け口だけを公開できる。ハッシュだけを持てば、設定が漏れても購読はできない。エージェントのトークンにwebhookを管理する権限を足さずに済む（grilling `add-phase4-relay` 第1ラウンドQ4、第2ラウンドQ8、Q9、Q10）
- 追記（2026-11-01）：受信箱のサービス（`switchboard inbox serve`）も、エージェントとは別の端末のトークンで配信口につなぐ。名前は `<端末名>-inbox` とする。トークンは `switchboard/relay-<端末名>-inbox` に置き、`relay token add --inbox` で作る。受信箱のサービスにとって、イベントは一覧を取り直すきっかけでしかない。`inbox.refresh_interval` ごとの問い合わせは延ばさない。延ばすと、webhookの無いプロジェクトの変化が遅れる。受信箱はフォージ単位で問い合わせるからである（grilling `add-inbox-relay-refresh` Q1、Q2）

## ADR-036 WUIの受信ポート（採用、2026-10-31）
- 決定：受信箱のWeb表示（WUI、`switchboard-web`）に限って、端末がLANのアドレスで受信ポートを開くことを許す。待ち受けのアドレスは `web.yaml` の `listen` にIPアドレスで明示させ、既定のアドレスは持たず、すべてのインターフェース（`0.0.0.0`、`::`）は拒む。当面は利用者を認証しない。返答のPOSTだけは、本文がJSONであることと、`Origin` と `Host` が `listen` のアドレスと一致することを確かめる。エージェント、受信箱のサービス、中継の端末側は、今までどおり受信ポートを開かない
- 理由：スマホから受信箱を見て返答するには、端末の側で待つ必要がある。LANの中だけに出し、使うのは1人で、扱う情報も非常に機微ではない。返答は信頼された指示としてエージェントに渡るので、外のWebページからのCSRFとDNS rebindingは防ぐ。LANの中の別の機器から返答できることは受け入れる。認証は課題として#15に残す（grilling `add-phase5-notify-web` 第1ラウンドQ2、第7ラウンドQ26、第8ラウンドQ27）

## ADR-037 WUIを別のモジュールにする（採用、2026-10-31）
- 決定：ADR-010の「1つのバイナリ」は、核の `switchboard` についての決定とする。WUIは同じリポジトリの `web/` に別のGoのモジュールとして置き、別のバイナリ `switchboard-web` にする。フロントエンドはVite、React、TypeScript、shadcn/uiで作り、パッケージはpnpmで管理する。ビルドの成果物は `go:embed` で埋め込む。核とWUIは、2つだけでつなぐ。核が公開する `inboxapi` の型と、`switchboard inbox serve` がUnixソケットで出すHTTPとJSONのAPIである。受信箱のトークンを持つのは、核の `inbox serve` だけである
- 理由：GUIやWUIは核と別に変わり、別の道具で作るほうが自然である。CLIを呼ぶ形は、要求ごとのプロセスの起動、誤りの読み取り、キャッシュの置き場所に無理がある。APIとクライアントを公開すれば、将来のGUIも同じ契約で作れる。WUIが侵害されても、フォージのトークンは取られない（grilling `add-phase5-notify-web` 第4ラウンドQ17'、第6ラウンドQ19、Q20'）

## ADR-038 計画を先に立てるモード（採用、2026-10-31）
- 決定：計画のモードでは、実装の前に、issueのコメントだけで質問と計画を往復する。信頼済みの人が承認の語（既定は `/ok`）で承認するまで、実装しない。始めるラベルは `agent:ready`、`agent:plan`、`agent:go` の3つとし、付けるのは常に1つでよい。状態ラベルの数は増やさず、計画の待ちはマーカーの `reason` で表す
- 決定：計画の段階かどうかは、端末に記録せず、着手のコメントのマーカーの `mode` と、最新の計画のあとの承認のコメントから毎回導く。承認は、switchboardが文字列で判定し、Claudeに判断させない
- 決定：計画の実行は、読み取りの権限で動かし、実行のあとにworktreeの変更を捨てる。権限ではリダイレクトの書き込みを止められないため、実行のあとの検査を防壁とする
- 決定：計画の実行に渡す利用者の追加の指示は、端末のローカルのファイルに置き、CLIと受信箱のWeb表示から編集できる。受信箱のトークンの権限は広げない
- 決定：webhookは自動で登録しない。`switchboard relay hook add <ref>` の案内は、中継を使う端末でGitLabのプロジェクトを足したときだけ出す。GitHubは中継に届かないので（ADR-007）、ポーリングで扱う
- 理由：`gh:uskanda/switchboard` #19では、エージェントが質問をせずに実装し、PRまで出した。手作業のgrillingと同じ進め方を、ハーネスを使わずとも、無人の実行で再現する（ADR-021）。承認の判定をClaudeに任せると、「進めてよさそう」と読んで実装に入りうる。grillingの記録は `add-plan-first-mode` の第1ラウンドQ1〜Q3、第2ラウンドQ4〜Q8、第3ラウンドQ11〜Q12、第4ラウンドQ15

## ADR-039 WUIからのプロジェクトの追加（採用、2026-11-01）
- 決定：ADR-035の「`switchboard` は設定ファイルを書き換えない」を、受信箱のサービス（`switchboard inbox serve`）がプロジェクトを1項目足す場合に限って改める。書き込みは `projects` の最後の項目の後に文字列として差し込み、コメント、空行、ほかの項目を変えない。足したあとの設定が検証を通り、ほかの節が変わらないことを確かめてから、元を `<config.yaml.bak>` に残して置き換える。読んでから書くまでに手で編集されていれば書かない
- 決定：WUIから決められるのは `ref` と `plan_first` だけとする。`path` は `<inbox.project_root>` の下のリポジトリ名、`host` は受信箱のサービスの端末、`base_branch` はフォージの既定のブランチとする。`verify_command`、`include_untrusted`、エージェントの身元の上書き、`protected_paths_extra` は、手で編集したときだけ書ける。機能は `<inbox.project_root>` を書いたときだけ有効になる。この端末のプロジェクトがまだ使っていないフォージの追加は拒む
- 決定：エージェントと受信箱のサービスは、10秒ごとに設定ファイルを確かめ、`projects` だけを読み直す。ほかの節は再起動まで反映しない。読み直しで現れたプロジェクトは、エージェントが自分のトークンでcloneし、状態ラベルを作ってから扱う。受信箱のトークンの権限は広げない
- 理由：プロジェクトを足すには、設定を手で書いてラベルを作り、sudoで再起動する必要があった。スマホからは済ませられない。WUIは認証が無いので（ADR-036）、`verify_command` のように端末でコマンドを動かせる項目や、任意のディレクトリを指す `path` は渡さない。実行の対象は今までどおり `trusted_authors` のコメントに限られる。丸ごと書き戻す形は、コメントの桁揃えと空行を失う。webhookを自動で登録するなら、Webから届くサービスにwebhookを管理する権限が要る。Secret Serviceへの書き込みも要る。中継を入れ直すsudo（ADR-034）も自動になる。得るのは着手の早さだけで、webhookが無くてもポーリングで扱える（grilling `add-web-project-add` 第1ラウンドQ1〜Q7、第2ラウンドQ8〜Q16、第3ラウンドQ17）

## ADR-040 WUIからのissueの作成（採用、2026-11-01）
- 決定：受信箱のサービス（`switchboard inbox serve`）は、受信箱のトークンで、設定にあるどのプロジェクトにもissueを作れる。担当の端末は問わない。issueには開始ラベルを1つ付ける（ADR-049で「1つ付けるか、付けない」に改めた）。ブラウザが選べるのは種別（`ready`、`plan`、`go`）だけで、ラベル名は設定の `labels.ready`、`labels.plan`、`labels.go` から核が決める。ほかのラベルは付けられない
- 決定：受信箱のトークンは利用者本人の身元なので、作ったissueは信頼済みの人のissueになり、エージェントがそのまま着手する。認証の無いWUI（ADR-036）から、LANの中の別の機器でも、設定のどのプロジェクトにでも実行を起こせるようになる。このことを受け入れる
- 決定：issueの作成のPOSTには、返答と同じ検査をかける。本文がJSONであること、`Origin` と `Host` が `listen` のアドレスと一致することである。受信箱のトークンの権限は広げない（Issuesの読み書きで足りる）。認証は引き続き#15の課題とする
- 理由：スマホからissueを立てて、そのまま実行に回したい。返答でも信頼済みの指示をエージェントに渡せるので、危険の種類は今と同じである。LANの中だけで使い、使うのは1人という前提も変わらない。ただし、ADR-036が受け入れたのは返答までで、新しい実行を起こせる点は広がるので、ここに残す。任意のラベル名を受けると、`agent:done` などの状態ラベルを外から付けられるので、種別だけを受ける（issue #40 のQ1〜Q4）

## ADR-041 CIの失敗とpushの失敗への自動の対処（採用、2026-11-02）
- 決定：エージェントは、PRかMRを作って `agent:done` にした後、自分がpushしたコミットのCIをポーリングで見張る。CIが失敗したら、人のきっかけ（ラベルや返信）が無くても、issueを `agent:running` に戻して直す実行を始める。pushがnon-fast-forwardで拒否されたときも、リモートのブランチを取り込む直す実行を始める。直す回数は1つのissueで `agent.max_fix_attempts`（既定2）までとし、信頼済みの人のコメントか始めるラベルで数え直す
- 決定：GitHubのエージェントのトークンに、`Actions: Read` と `Commit statuses: Read` を足す。どちらも読み取りだけである。足さないうちは、エージェントはCIを見張らず、`switchboard doctor` が警告する。GitLabは今の `api` スコープで足りる
- 決定：中継のイベントの種別は増やさない。GitHubのwebhookは中継に届かない（ADR-007）ので、CIの結果はどちらのフォージでもポーリングで知る
- 理由：PRができた後のCIの失敗は、人がログを読んで返信するまで止まっていた。直す実行の対象は、既に信頼済みの人が着手させたissueと、エージェント自身がpushしたコミットに限る。CIのログは非信頼のデータとして渡し、許可するツールはnon-fast-forwardの直しの `git merge` だけ増やす。保護パスの検査と、PRがdraftであることも変わらない。grillingの記録は `handle-push-and-ci-failures` の第1ラウンドQ2〜Q5、第3ラウンドQ15

## ADR-042 doneのissueをcloseまで受信箱に残し、信頼済みのコメントで再開する（採用、2026-11-01）
- 決定：openのまま `agent:done` のissueは、closeされるまで受信箱の「完了（close待ち）」の節に出す。エージェントの最新のdoneの投稿より後に信頼済みのコメントが付けば、waitingと同じ規則で再開し、runningに移す。受信箱からの返答も、waitingとdoneの両方で受け付ける。GitLabでは、doneのissueのコメント数も見る
- 決定：doneで終える実行は、pushの後にissueのブランチからbaseへの開いたPR/MRを探し、あればそのURLを使う（`reuse-open-change-request` の仕組み）。そのときdoneの投稿には「PRを更新しました」と書く。closeやmergeの済んだものは使わない
- 決定：pushはforceなしのまま変えない。baseとの衝突は `git merge origin/<base>` で解消させ、rebase、amend、履歴の書き換えはさせない。実装する実行の許可ツールに `git merge` を足す。ADR-041がpushの直しに限った `git merge` は、これで実装する実行のすべてに広がる
- 決定：計画を先に立てるモードで承認済みの計画を実装したissueは、doneから再開しても、承認された計画の実装（approvedRun）として動かす。範囲を超える頼みは `agent:plan` を付け直して計画から立て直す
- 理由：作ったPR/MRに問題やコンフリクトがあれば、doneの後もやりとりが要る。表示だけ残しても、返答で動かなければ目的を果たせない。PR/MRの作成の失敗（GitHubの422、GitLabの409）から既存のURLを読み取る形は、誤りの本文の形に頼る。force pushを入れると、人間がPRのブランチに積んだコミットを消すおそれがあり、PRは最後にsquash mergeすれば履歴も気にならない。承認した計画の範囲に収まる直しで、毎回承認を挟むと遅い（issue `gh:uskanda/switchboard` #53のQ1〜Q7）

## ADR-043 受信箱のWeb表示から完了のPR/MRをマージする（採用、2026-11-02）
- 決定：受信箱のWeb表示（WUI）で、完了（close待ち）のissueのPR/MRを、draftを解除してマージできるようにする。ボタンは詳細のペインと、一覧の完了の行の両方に置き、どちらも確認のダイアログを経てから送る。マージは受信箱のサービス（`switchboard inbox serve`）が受信箱のトークンで行う。WUIから人が押すマージは、ARCHITECTURE 4.4の「マージは人間が行う」に当たる。受信箱のトークンは人の身元なので、フォージにも人のマージとして残る
- 決定：受信箱のトークンの権限を広げる。GitHubでは `Pull requests: write` と `Contents: write` を足す。GitLabは今の `api` スコープで足りる。ADR-038、ADR-039、ADR-040の「受信箱のトークンの権限は広げない」は、この点だけ改める。権限を足さないうちは、マージだけが403で断られ、ほかの機能は変わらない
- 決定：対象はopenで `agent:done` のissueに限る。マージするのは、エージェントの最新のdoneの投稿のマーカーにある `cr`（PR/MRの番号）だけで、同じマーカーの `sha` のコミットに限る。ブラウザは画面で見た `sha` を送り、マーカーの `sha` と違えば断る。フォージにも `sha` を渡し、headが動いていればマージさせない。CIやマージできるかの判定はフォージに任せ、断られたら理由を誤りのトーストに出す。マーカーに `cr` の無い古い投稿では、ボタンを出さない
- 決定：受信箱のサービスは、issueを直接closeせず、ラベルとコメントにも触らない。issueのcloseは、PR/MRの本文の `Closes #N` に任せる。baseが既定のブランチでなければissueは閉じず、受信箱に残る。そのときもう一度押すと、フォージが「マージ済み」で断り、その理由を出すだけにとどめる。マージの方式は指定せず（GitHubはAPIの既定のマージコミット、GitLabはプロジェクトの設定）、リモートのブランチも消さない
- 決定：認証の無いWUI（ADR-036、ADR-040）から、LANの中ならマージまでできるようになる。このことを受け入れる。マージのPOSTには、返答と同じ検査をかける。本文がJSONであること、`Origin` と `Host` が `listen` のアドレスと一致することである。認証は引き続き#15の課題とする
- 理由：完了のissueを片付けるたびに、PRを開いてdraftを解除し、マージする操作がスマホでは手間だった。エージェントのトークンでマージすると、botがマージした記録になり、「マージは人間が行う」と食い違う。3本目のトークンは、設定が増えるわりに得るものが少ない。画面で見た `sha` に限れば、見ていないコミットをマージしない保証が、追加のAPIの呼び出しなしで手に入る。CIの必須化はブランチの保護で済み、受信箱のサービスはCIを見ないという今の分担も保てる。issueを受信箱から直接閉じるボタンは、マージせずに閉じる操作をLANの中の誰にでも許すわりに、使う場面が少ない（issue `gh:uskanda/switchboard` #69のQ1〜Q7）

## ADR-044 doneのPR/MRとbaseの衝突への自動の対処（採用、2026-11-02）
- 決定：ADR-041の直す実行のきっかけに、エージェントが作ったPR/MRとbaseとの衝突を加える。衝突とみなすのは、GitHubの `mergeable=false` かつ `mergeable_state=dirty` と、GitLabの `has_conflicts=true` だけとする。計算中は次の問い合わせに回し、`behind` と `blocked` は扱わない
- 決定：CIの段（pushから6時間まで、`poll_interval` ごと）が終わっても見張りは外さない。PR/MRがopenでissueが `agent:done` の間、`reconcile_interval` ごとにPR/MRを1回読んで衝突を見る。PR/MRのheadがエージェントの最新のdoneのマーカーの `sha` と違えば見張りをやめ、人がpushした後の衝突は直さない
- 決定：衝突を直す実行は `git merge origin/<base>` で解消させる。回数は、CIの失敗とnon-fast-forwardと同じ `agent.max_fix_attempts` で数える。上限を超える衝突では、issueを `waiting(reason=conflict)` で待たせる。CIの失敗と衝突が同時にあれば衝突を先に直す
- 決定：トークンの権限は増やさない。衝突の有無はPR/MRの読み取りで分かり、GitHubの `Pull requests: Read`、GitLabの `api` スコープで足りる
- 理由：GitHubは衝突のあるPRで `pull_request` のCIを走らせないので、ADR-041の見張りは「CIが現れない」として黙って終わり、人が気付くまで止まっていた（PR #71）。直す実行に渡すのはPR/MRの番号とbaseの名前だけで、フォージから読んだ文は入れない。grillingの記録は `detect-change-request-conflicts` の第1ラウンドQ1〜Q5、第2ラウンドQ6〜Q8

## ADR-045 実装の実行に足す許可と追加の指示（採用、2026-11-02）
- 決定：ファイルを書く実行（直接の実装、承認のあとの実装、CIとpushの失敗を直す実行、baseとの衝突を直す実行）に、利用者が許可するツールと追加の指示を足せるようにする。許可は設定の `agent.allow_tools_extra` と `projects[].allow_tools_extra` に書き、全体、プロジェクトの順につなげる。指示は計画用の `plan.md` と別の `run.md` に置き、system promptの最後の節に入れる。計画の実行には、どちらも足さない
- 決定：許可は設定ファイルにだけ書け、受信箱のAPIとWeb表示からは変えられない。読み込みのときに、空の項目、制限の無い `Bash`、拒否している操作（`git push`、`git rebase`、`gh`、`WebFetch`）を名指しする項目を誤りにする。`Bash(git *)` のような広い項目は通す。denyがallowより優先される（V42）からである
- 決定：製品のコードと既定の設定では、OpenSpecとハーネスを扱わない。OpenSpecを使うプロジェクトでの書き方は、`docs/examples/openspec.md` に例として置く（ADR-021）。ADR-038の追加の指示は、計画用の `plan.md` のこととして残る
- 理由：利用者の `~/.claude/CLAUDE.md` は実行に届いていたが、実装の実行の許可にSkillツールと `openspec` のCLIが無く、`dontAsk` で拒否されていた。`allowed-tools` を持つスキルは、allowに `Skill` が無いと呼べない（V41）。実装の実行68件のうち、OpenSpecの変更を記録したのは13件だけだった。grillingの記録は `add-run-allow-and-instructions` の第1ラウンドQ1〜Q3、第2ラウンドQ4〜Q7、第3ラウンドQ8〜Q9

## ADR-046 順番待ちから取り出す順と、計画の実行を先にする設定（採用、2026-11-02）
- 決定：空いたスロットは、順番待ちに入った順にissueへ渡す。同じ時刻ならrefの文字列の順にする。設定にかかわらず、今までのrefの辞書順はやめる。順番待ちのあいだに種類が変わっても、入った時刻は変えない。エージェントを再起動すると時刻は消え、再評価で入り直した順になる
- 決定：端末の設定 `agent.prefer_plan`（既定はfalse）を足す。オンのときは、順番待ちのうち計画の実行（planRun）を先に取り出す。承認済みの計画の実装（approvedRun）、計画なしの実装（directRun）、返答による再開、doneからの再開は後に回す。CIの直し（fixRun）は順番待ちに入らないので対象外とする。並べ替えるのは順番待ちから取り出すときだけで、スロットが空いていれば実装もすぐに始まる
- 決定：ADR-039が読み直す範囲を `projects` と `agent.max_parallel` に加えて、`agent.prefer_plan` にも広げる。10秒ごとの読み直しで反映し、再起動は要らない
- 理由：要件づくりは何度もやりとりするので早く回したい。実装は後でまとめて動かしても困らない。同時実行の枠は端末全体で数えるので、優先も端末全体で決める。プロジェクトごとにすると、別のプロジェクトどうしの順が決まらない。directモードの返答の続きは実装そのものなので、先にしない。辞書順では `#10` が `#9` より先に動き、待った時間とも関係がない。計画が残るあいだ実装を止める形は、返答待ちの計画が1つあるだけで枠を遊ばせる（issue `gh:uskanda/switchboard` #74のQ1〜Q4）

## ADR-047 Androidのアプリと受信箱のサービスからのプッシュ通知（採用、2026-11-02）
- 決定：スマホのアプリは、Expo（SDK 58）で作るAndroidのアプリとし、受信箱のWeb表示（WUI）をWebViewで開く殻にする。画面のコードは `web/ui` の1つだけとし、アプリはWUIのURLの設定、プッシュ通知、戻る操作だけを受け持つ。コードは `app/` に置き、APKは利用者の鍵で署名して手で入れる。EASとExpoのアカウントは使わない。iOSと家の外からの利用は対象外とする
- 決定：プッシュ通知は、受信箱のサービス（`switchboard inbox serve`）がFCM HTTP v1で直接送る。受信箱のサービスは、`inbox.notify.fcm` があるとき、画面が無くても `inbox.refresh_interval` ごとに一覧を取り直し、新しく待ちか完了になったissueを知らせる。エージェントが送るTelegramの通知は変えず、両方を併用する
- 決定：通知でGoogleのサーバーに渡すのは、issueの参照、待ちの理由、issueのタイトル、待ちの開始時刻、PR/MRの番号とコミットだけとする。質問、計画、進捗、コメントの本文は載せない
- 決定：計画の承認待ちの通知に「承認」のボタンを、完了の通知に「マージ」のボタンを付ける。「承認」は、アプリを開かずに承認の語を投稿する。受信箱のサービスは、通知に載せた待ちの開始時刻が最新の待ちの投稿と一致するときだけ受け付ける。「マージ」はアプリを開き、WUIの確認のダイアログを経る。PRODUCT.mdの原則3（全文を読んでから返答する）は、計画の「承認」のボタンに限って例外とする
- 決定：アプリは、ネイティブの通信で送るPOSTに、設定したWUIのURLを `Origin` として付ける。`switchboard-web` の `Origin` と `Host` の検査は変えない
- 理由：WUIの変更に、アプリのビルドし直しなしで追随できる。Expo Routerとreact-native-webでの書き直しは、別のissueに分ける。Tailwind v4をネイティブで使うNativeWind v5はまだRCで、書き直すと画面とテストを全部作り直すことになる。受信箱のサービスが送れば、アプリのトークンとFCMの鍵の置き場が1か所で済む。全端末の待ちも1か所から知らせられる。`Origin` の検査は、ブラウザの上の別のページからのCSRFとDNS rebindingを防ぐためにある。LANの中の機器なら送れるという、ADR-036で受け入れた範囲は広がらない。grillingの記録は `add-android-app` の第1ラウンドQ1〜Q6、第2ラウンドQ7〜Q10、第3ラウンドQ11〜Q16、第4ラウンドQ17

## ADR-048 衝突で断られたマージを、衝突を直したあと自動でマージする（採用、2026-11-03）
- 決定：WUIで押したマージをフォージが衝突で断ったとき、受信箱のサービスは「マージの依頼」を覚え、202で答える。登録するのは、PR/MRがopenで、headが押した `sha` のままで、衝突しているときだけとする。衝突でない理由で断られたときは、今までどおり誤りを返す
- 決定：依頼は、受信箱のサービスの状態ディレクトリの `inbox/automerge.json` に置く。ラベルとコメントには触らない（ADR-043のまま）。終わった依頼は、結果と理由を付けて24時間残し、画面に知らせる
- 決定：受信箱のサービスは、依頼があるあいだ `inbox.refresh_interval` ごとに（マージの受付と中継のイベントでも）依頼を調べる。画面がつながっていなくても調べる。エージェントの直す実行が新しいdoneを投稿し、PR/MRのheadがそのマーカーの `sha` なら、その `sha` を指定して受信箱のトークンでマージする。CIの待ちなどで断られたら、依頼を残して次に試す
- 決定：ADR-043の「マージするのは画面で見た `sha` に限る」を改め、押したあとにエージェントの直す実行（衝突、CIの失敗、non-fast-forward）がpushしたコミットにも広げる。見分けるため、直す実行のdoneのマーカーに `fix=<ci|push|conflict>` を書く。押したあとに、信頼済みの人のコメントか、`reason=fix` でない着手が入ったら、依頼を打ち切る
- 決定：issueのclose、`waiting` への移行（衝突の直しが上限を超えた場合を含む）、PR/MRのcloseとマージ、人のpush、権限の不足でも打ち切る。時間の上限は設けない。WUIの詳細のペインから取り消せる。取り消しのPOSTには、マージと同じ検査をかける
- 理由：一度マージを押したのに、衝突の直しのあとで押し直す手間があった。フォージのauto-mergeは、リポジトリの設定が要り、`sha` を固定できないので人があとから積んだコミットまでマージする。エージェントのトークンでマージすると、botのマージとして残り「マージは人間が行う」に合わない。受信箱のサービスが受信箱のトークンでマージすれば、人の身元のまま、マージするコミットを直す実行の分に絞れる。直す実行は承認済みの範囲の直しに限られる（ADR-041、ADR-044）。ラベルやコメントで覚えると、ADR-043の約束を破る（issue `gh:uskanda/switchboard` #119のQ1〜Q5）

## ADR-049 WUIから開始ラベルなしのissueを作る（採用、2026-11-03）
- 決定：ADR-040の「issueには開始ラベルを1つ付ける」を「開始ラベルを1つ付けるか、付けない」に改める。ブラウザが選べる種別に `none` を足し、`none` ではラベルを付けずにissueを作る。ほかのラベルは今までどおり付けられない。作れる先も、設定のプロジェクトだけのままとする
- 決定：エージェントは、ラベルなしのissueには着手しない。あとで本人が開始ラベルを付けたときに着手する。開始ラベルの初期値は今までどおり `ready` とする。「ラベルなし（実装開始しない）」は選択肢の最後に置く
- 理由：「後で作りたい」ものを気軽に入れたい。種別の送り忘れがラベルなしのissueとして通らないよう、空の種別は今までどおり拒み、`none` という種別で表す。設定に無いリポジトリへの作成は、認めない。認めると、認証の無いWUI（ADR-036、ADR-040）から、受信箱のトークンで任意のリポジトリに書けてしまう（issue `gh:uskanda/switchboard` #107のQ1〜Q3）

## ADR-050 マージの確認ダイアログにCIとマージできるかを出す（採用、2026-11-02）
- 決定：WUIのマージの確認ダイアログに、PR/MRの衝突（なし／あり／フォージが計算中）、画面を読んだ後にheadが動いたか、マーカーの `sha` のコミットのCIを出す。CIは要約の1行（成功・失敗・実行中の数）と、失敗中と実行中のチェックの名前をフォージへのリンクにして出し、成功は数だけにする
- 決定：受信箱のサービスに新しい口 `GET /v1/merge-status`（WUIでは `GET /api/merge-status`）を足し、ダイアログを開くたびに1件だけ読む。一覧の要素は変えない。前提はマージと同じで、openで `agent:done` のissueの、最新のdoneの投稿のマーカーの `cr` と `sha` に限る。外れれば `stale` を返す
- 決定：ADR-043の「受信箱のサービスはCIを見ない」を、この点だけ改める。受信箱のサービスは、受信箱のトークンでCIを読む。GitHubの受信箱のトークンに `Actions: Read` と `Commit statuses: Read` を足す。どちらも読み取りだけである。GitLabは今の `api` スコープで足りる。権限を足さないうちは、ダイアログに「CIを読む権限がありません」と出るだけで、マージを含むほかの機能は変わらない。`switchboard doctor` が警告する
- 決定：表示は情報だけにとどめる。衝突やCIの失敗があっても「マージする」は押せる。読んでいる間と、読めなかったときも同じである。最後の判定はADR-043のとおりフォージに任せる。衝突の有無の判定はADR-044と同じ（GitHubの `dirty`、GitLabの `has_conflicts`）とする。計算中とみなすのは、GitHubの `mergeable=null` と、GitLabの `detailed_merge_status` が `checking` か `unchecked` のときである
- 決定：チェックの名前とURLはフォージから読んだデータとして扱う。文字列として出すだけにし、リンクはhttpかhttpsのURLに限る
- 理由：ダイアログには取り消せないことの1文とPR/MRのURLしかなく、CIと衝突を確かめるにはフォージを開く必要があった。一覧の要素へ足すと、一覧を読むたびに完了のissueの数だけCIのAPIを呼ぶことになる。ブランチの保護で必須のCIはフォージが強制しており、任意のチェックの失敗を承知でマージしたい場面もある。GitHubの `mergeable` は計算のあいだ `null` を返すので、受信箱の側で止めると誤って止めるおそれがある。足す権限は読み取りだけで、ADR-041のエージェントのトークンと同じ進め方である（issue `gh:uskanda/switchboard` #84のQ1〜Q4）

## ADR-051 実装の実行だけへの追加の指示と、スクリーンショットの添付（採用、2026-11-02）
- 決定：指示に3つめの種類 `implement.md`（全体用とプロジェクト用）を足す。渡すのは直接の実装と承認のあとの実装だけで、`run.md` のあとにつなげる。計画の実行と直す実行には渡さない。保存の検査、監査ログ、CLI（`--implement`）、受信箱のAPIの `kind`、設定の画面は、ほかの種類と同じ作りにする。撮影の方針は利用者がこのファイルに書き、撮影専用の設定の項目は作らない
- 決定：画像の置き場所 `.switchboard/screenshots/` は、switchboardとClaudeの間の取り決めとし、同じ2種類の実行のsystem promptにいつも入れる。switchboardは、実行の前に置き場所を `.git/info/exclude` に足して中を消す。doneで終わったら、`.png`・`.jpg`・`.jpeg`・`.webp` だけを1枚5MB、10枚まで、runのディレクトリへ移す。置き場所のファイルがコミットに入っていたら、pushせずに検査の失敗にする
- 決定：doneの投稿とラベルのあとに、画像だけのコメントを1件付ける。マーカーの状態は `attachment` で、待ちやdoneの判定には数えない。GitHubでは `gh issue comment --attach` を使い、`gh` にはエージェントのトークン（`GH_TOKEN`）と空の `GH_CONFIG_DIR` だけを渡す。GitLabではuploads APIを使う。添付に失敗したら理由だけのコメントを付け、doneは保つ。Claude側の `gh` の拒否は変えない
- 決定：撮影に要るコマンドの許可は、ADR-045の `allow_tools_extra` に書いてもらう。撮影専用の許可の項目は作らない
- 理由：GitHubには、コメントへ画像を付ける公開のAPIが無い。`gh` のv2.99.0の `--attach` は、Web画面で付けたときと同じ形で付けられるが、非公開のアップロードの仕組みに頼る。そこで、`gh` を呼ぶのは `internal/forge/github` の1つのファイルだけにする。画像をコミットしないので、リポジトリは大きくならない。エージェントのトークンで通るかは未確認で、V47として残す。`run.md` は直す実行にも入るので、「実装のときだけ撮る」を書けなかった。grillingの記録は `add-implement-instructions-and-screenshots`（issue `gh:uskanda/switchboard` #94のQ1〜Q11）

## ADR-052 実行に渡すツールを固定し、モデルとeffortを設定で選ぶ（採用、2026-11-03）
- 決定：エージェントは、`claude -p` に `--tools` で渡すツールを明示する。ファイルを書く実行は `Bash`、`Read`、`Edit`、`Write`、`Glob`、`Grep`、`WebSearch` とする。計画の実行は `Bash`、`Read`、`Glob`、`Grep`、`WebSearch` とする。`allow_tools_extra` の各項目のツール名（`Bash(openspec *)` なら `Bash`）も渡す
- 決定：`WebSearch` を、どの実行でも許可する。`WebFetch` は今までどおり拒否する
- 決定：設定の `agent.model` と `agent.effort` を既定にし、`agent.plan` と `agent.fix` で計画の実行と直す実行を上書きする。値が空のときは、`--model` と `--effort` を付けずにCLIとユーザーの設定に任せる。名前はClaude Code固有にせず、許容値の検査だけをアダプタが持つ
- 決定：`--setting-sources` によるユーザー設定の切り離しは、この決定に含めない。実行のsandboxの扱いと一緒に決める（#130）
- 理由：CLIの既定のツールは約25個あり、起動直後の文脈が約39kトークンになっていた。7個に絞ると約9kトークンになる（V49）。177回の実行で使われたツールは、ほぼBash、Read、Edit、Write、構造化出力だけだった。モデルとeffortは、ユーザーの全体設定（`opus[1m]` と `xhigh`）が無人の実行にもそのまま使われていた。WebSearchはページの本文を取ってこないため、WebFetchより出入りする情報が少ない。フォージの資格情報は渡さない（ADR-012）ので、検索語に秘密は載らない（issue `gh:uskanda/switchboard` #129のQ1〜Q9）

## ADR-053 利用上限とクオータは順番待ちとして扱い、自動で再開する（採用、2026-11-03）
- 決定：実行の結果に、サービスに依存しない上限の型（`internal/usage`）を設ける。上限の検出は実行器のアダプタの責務とし、Claude Codeのアダプタは、rejectedの `rate_limit_event` と、エラーのresultの `api_error_status=429` から埋める（V12）
- 決定：利用上限で止まった実行のissueは、`waiting(reason=limit)` にせず、`agent:ready` と順番待ちのコメント（`state=queued reason=limit run=<実行> until=<時刻>`）に戻す。DESIGN.mdの `waiting(reason=limit)` はこれで置き換える。端末は解除時刻（分からなければ `agent.limit_wait`、既定30分の後）まで新しい実行を始めず、その間に始まるはずだったissueも `reason=limit` の順番待ちにする。動いている実行は止めない。止めた状態は `pause.json` に書く
- 決定：エージェント自身が付け直した始めるラベルは、エージェントの最新の投稿が `run=` 付きの順番待ちのコメントのときだけ受け付ける。この再開は新しい周期を始めず、止まった実行の周期のモードのまま動く。計画の実行でなければ、プロンプトに上限で止まったことを足す
- 決定：`claude.auth: api_key` のとき、各実行の `total_cost_usd` を `cost.json` に日と月で積み、`quota.daily_usd` か `quota.monthly_usd` に達したら、次の日か月の0時（端末のローカル時刻）まで `reason=quota` の順番待ちにする。確かめるのは始める前だけとする
- 決定：直す実行が上限に当たったときは、端末を止めたうえで `waiting(reason=error)` にし、マーカーに `until` を付けて自動で直す回数に数えない
- 理由：ADR-019の「待ち」は人への質問を残した状態で、時間が経てば自動で解けるものを待ちにすると、その定義が崩れる。順番待ちなら、マーカー、コメント、受信箱の表示という既存の仕組みに乗れる。サブスクリプションの上限はアカウント単位なので、端末で新しい実行を止めないと同じ上限に当たり続ける。再開の印を端末のファイルでなくフォージのマーカーに置くのは、ラベルの付与者がエージェントになるため、信頼の判定にフォージ上の印が要るからである（issue `gh:uskanda/switchboard` #103のQ1〜Q7と計画のD1〜D3）

## ADR-054 スロットを待つ直す実行を順番待ちより先に始める（採用、2026-11-03）
- 決定：ADR-046の「fixRunは対象外」を補う。baseとの衝突を直す実行とCIの失敗を直す実行は、スロットが無ければ待ちとしてエージェントの内部で覚える。スロットが空いたら、順番待ちのissueより先に始める。`agent.prefer_plan` がオンでも、計画の実行より先にする
- 決定：待つ直す実行どうしでは、ADR-044のとおり衝突をCIの失敗より先にする。同じ種類なら待ち始めた時刻の早い順、同じ時刻ならrefの文字列の順にする。プロジェクトの上限に当たった直す実行は飛ばし、ほかのプロジェクトは止めない
- 決定：始める前にPR/MRとissueを読み直す。衝突だけを見る段でも `reconcile_interval` を待たない。衝突が消えた、headが動いた、issueがdoneでなくなったときは始めない
- 決定：直す実行は `pending` に入れず、順番待ちのコメント（queuedのマーカー）も付けない。待ち始めたことはログに1回だけ残す。設定の項目は足さず、動いている実行も止めない
- 理由：直す実行は順番待ちに入らず、スロットが無いと次の見張りの確認まで待っていた。一方、実行が終わると空いたスロットはすぐ順番待ちへ渡るので、順番待ちが続くかぎり、マージを待つPR/MRが衝突したまま止まっていた。直す実行は終わった作業を動ける状態に戻すもので、ふつうは短い。doneのissueにqueuedのマーカーを載せると、最新のマーカーからissueの状態を読む処理と受信箱の表示に影響が及ぶ。PR/MRを衝突したまま放っておきたい場面は思い付かないので、設定で切り替える余地も小さい（issue `gh:uskanda/switchboard` #121のQ1〜Q4）

## ADR-055 プロジェクトのアイコンの取り方と届け方（採用、2026-11-03）
- 決定：受信箱のWeb表示で、参照の前にプロジェクトのアイコンを出す。既定はフォージのアバターとする。GitLabはプロジェクトのアバター、無ければ属するグループのアバターを使う。GitHubのリポジトリには画像が無いので、オーナーのアバターを使う。設定のプロジェクトの `icon`（画像のURL、端末の画像ファイル、絵文字1文字）があれば、そちらを優先する
- 決定：画像はinboxサービスが受信箱のトークンで取り、状態の置き場の `project-icons/` に24時間保存する。取れなかったことは1時間覚える。switchboard-webは `/api/project-icon` で自分のオリジンから返し、CSP（`default-src 'self'`）は緩めない
- 決定：トークンを付けるのは、フォージのAPIのホストと、GitLabのインスタンスと同じホストだけにする。GitHubのアバターの画像のホスト、`icon` のURL、リダイレクトの先の別のホストには付けない。Goの標準のクライアントはリダイレクトで `Authorization` を外すが、GitLabの `PRIVATE-TOKEN` は外さないので、自前で外す
- 決定：画像はPNG、JPEG、GIF、WebPだけを先頭のバイトで見分けて受け付け、256KiBまでとする。SVGはスクリプトを持てるので受け付けない
- 理由：CSPに `img-src` でフォージのホストを足すと、ブラウザからフォージへの通信が増え、非公開のGitLabのアバターは認証が要るので出せない。inboxサービスはもともと受信箱のトークンを持つので、新しい権限は要らない。issueの本文や画像は中継を通らない（issue `gh:uskanda/switchboard` #105のQ1〜Q4）

## ADR-056 エージェントと信頼するユーザーが同じアカウントのとき、再開の印の無い始めるラベルは人のものとして扱う（採用、2026-11-03）
- 決定：ADR-053を補う。始めるラベルを付けたのがエージェントのアカウントで、再開の印（`run=` 付きの順番待ちのコメント）が無いとき、そのアカウントが `trusted_authors` にも含まれていれば、信頼するユーザーが付けたラベルとして判定する。新しい周期を始め、モードはラベルから決める。含まれていなければ、これまでどおり何も始めない
- 理由：個人で使う構成では、`agent_identity` と `trusted_authors` が同じアカウントになる。フォージのラベルの付与者からは、人が付けたのかエージェントが付け直したのかを見分けられない。ADR-053のままだと、人が付けた `agent:ready` がすべてエージェントのものと判定され、ログにも残らずに見送られていた（`gh:uskanda/switchboard` #138、#139、`gh:uskanda/Monolith` #28）。エージェントが自分で付け直すのは利用上限からの再開だけで、そのときは必ず再開の印を残すので、印の無いラベルを人のものとみなしても再開と取り違えない

## ADR-057 実行のsandboxと許可の決め方をswitchboardが持つ（採用、2026-11-03）
- 決定：`claude -p` に `--setting-sources project,local` を付け、ユーザーの全体設定のsandbox、フック、プラグイン、許可の規則を実行に使わせない。プロジェクト設定は今までどおり読み込む。ADR-028のうち、ユーザー層の設定を読み込むとした部分を置き換える
- 決定：実行ごとの設定ファイルでsandboxを有効にする。`failIfUnavailable` を有効にし、`allowUnsandboxedCommands` を無効にする。書き込みはworktreeと `$TMPDIR` だけに許し、ネットワークは許さない
- 決定：sandboxの中のBashのコマンドは、許可の規則が無くても実行させる（`autoAllowBashIfSandboxed`）。拒否の規則は残す
- 決定：sandboxの外で動かすのは、ファイルを書く実行では検証コマンドの全体と `git`、計画の実行では `git` だけとする。この2つは許可の規則で決める
- 決定：sandboxの中から、資格情報の置き場所、設定ファイルのディレクトリ、状態のディレクトリの `worktrees` 以外の項目を読めなくする。渡すのは端末に実在するパスだけとする
- 決定：Linuxでは、実行のたびにclaudeの起動の前にbwrapで名前空間を作れるかを確かめる。作れなければclaudeを起動せず、実行を誤りにして理由をコメントに書く
- 理由：213回の実行のうち76回で、許可の規則が無いためにコマンドが拒否された（計168回）。23回の実行は、sandboxの外での再実行を試みた。規則の一覧を広げても、パイプや `&&` でつないだコマンドは規則に当たらない。境界をsandboxに置けば、規則の一覧は拒否だけで足りる。`failIfUnavailable` は名前空間を作れない環境を検出しないため、エージェントが確かめる。検証コマンドを先頭の語でなく全体で外に出すのは、`make deploy` のようなほかのターゲットをsandboxに残すためである（V51、V52、issue `gh:uskanda/switchboard` #130のQ1〜Q10）

## ADR-058 計画の実行のセッションを引き継ぐ（採用、2026-11-03）
- 決定：ADR-005の再開を、計画の実行の次の計画の実行に限って使う。前回のセッションから `--resume <前回> --fork-session` で分岐し、分岐した先のIDは今までどおり `--session-id` で先に決める
- 決定：引き継ぐのは、issueの最新の待ちの投稿がこの端末の計画の実行の質問か計画で、その投稿から `agent.resume_within`（既定1時間、0で引き継がない）以内のときに限る。前回の実行の `launch.json` に残した追記する指示のSHA-256、ツール、モデル、effort、worktreeのHEADが、今回と同じであることも条件とする
- 決定：引き継いだ実行にも、プロンプトの全体を渡し、先頭に前のラウンドの続きであることを書く。前回のセッションが無いときは、同じ実行の中で新しいセッションとして起動し直し、`run.started` を2行残す
- 決定：この引き継ぎを「セッションの引き継ぎ」と呼び、返答や利用上限のあとの「再開」と区別する
- 理由：計画の実行の次の計画の実行は51件あり、34件が1時間以内に始まっていた。再開では追記するシステムプロンプトが差し替わらず、最初の実行のものが残る（V53）。そのため、規則の違う承認のあとの実行や直す実行は対象にできない。キャッシュの有効期間は1時間で、ツールを変えるとキャッシュは読まれない（issue `gh:uskanda/switchboard` #131のQ1〜Q9）

## ADR-059 受信箱のWeb表示にGitLabのOpenID Connectでログインする（採用、2026-11-03）
- 決定：ADR-036の「当面は利用者を認証しない」を、`config.yaml` に `inbox.auth` を書いた構成について改める。その構成では、Web表示の `/auth/` と画面の静的ファイルを除くすべての要求に、GitLabのOpenID Connectでのログインを求める
- 決定：OIDCの処理は受信箱のサービスが行う。認可コードとの交換、トークンの保持と更新、ログインできる人の判定は受信箱のサービスの中にとどめ、Web表示にはセッションIDだけを返す。Web表示はそれを `HttpOnly`、`SameSite=Lax` のcookieにする。トークンとセッションは受信箱のサービスのメモリーにだけ置き、再起動で全員がログインし直す
- 決定：ログインできるのは、`inbox.auth.member_groups` と `admin_groups` のグループ（その下位のグループを含む）に属する人と、`owner` の1人である。セッションは、最後の要求から24時間とログインから7日の早いほうで終わり、トークンを更新するたびにグループの所属を確かめ直す
- 決定：当面はHTTPのままにし、cookieに `Secure` を付けない。HTTPSはissue #155で、KeycloakのSSOはissue #151で扱う
- 理由：複数の人で受信箱を共有する（#146）には、誰が使っているかを先に確かめる必要がある。`api` のスコープのトークンはフォージのトークンにあたるので、Web表示に持たせない（ADR-037）。ソケットを使うのはWeb表示だけで、CLIは使わない。そのため、ソケットの全経路でセッションを求められる（grilling `add-web-multi-user`、`add-web-oidc-login`）

## ADR-060 中継のwebhookの受け口をLANのアドレスで待てるようにする（採用、2026-11-04）
- 決定：ADR-007の「受け口は `127.0.0.1` で待ち、同じ端末のGitLabからだけ受ける」を改め、`relay.webhook_listen` にこの端末のLANのIPアドレスを書けるようにする。LANの別の機械のGitLabからも受けられる。インターネットへの公開はしない。設定できるGitLabは1つのまま（ADR-030）とする
- 決定：`relay.webhook_listen` には、WUIの待ち受けと同じ検査（ADR-036）をかける。IPアドレスとポートの形でないもの、ホスト名、すべてのインターフェース（`0.0.0.0`、`::`）は、設定の誤りとして拒む。既定は今までどおり `127.0.0.1:8781` で、`webhook_url` の既定も `http://<webhook_listen>` のまま。`sse_listen` は変えない
- 決定：ADR-017を改め、受け口がループバックでないときは `gitlab_token: true` を設定の誤りとして拒む。`relay hook add --gitlab-token` も、シークレットを作る前に断る。LANでは署名トークン（GitLab 19.0以降）だけを使う
- 決定：送り元のアドレスは絞らない。受け口はHTTPのままとし、LANの中でwebhookのペイロード（issueの本文やコメント）が平文で流れることを受け入れる。私設のCAの証明書には新しい設定を足さず、OSの信頼ストアに入れてもらう
- 理由：GitLabが中継と別の機械にあると、受け口がローカル前提のままでは返答にすぐ着手できない。署名トークンはHMACとタイムスタンプで検証するので、シークレットは回線に出ない。`X-Gitlab-Token` は平文のシークレットそのもので、LANで見た機器が偽のイベントを送れる。偽のイベントでも、中継が配るのはIDだけで、エージェントがフォージから取り直すので指示の注入にはならない（ADR-004）。知らない `hook-key` は404で断り、署名で検証するので、送り元を絞って得るものは小さい。LANの中のHTTPは、WUIでも受け入れている（ADR-036）。HTTPSには証明書の運用とGitLab側での信頼が要り、得るものに比べて手間が大きい（issue `gh:uskanda/switchboard` #153のQ1〜Q10）

## ADR-061 受信箱を複数の人で共有する（採用、2026-11-03）
- 決定：ADR-015、ADR-040、ADR-043、ADR-056を、`inbox.auth` を書いた構成について改める。その構成では、Web表示とアプリからのGitLabのプロジェクトへの書き込み（返答、承認、issueの作成、マージ）を、ログインした人のOAuthのトークンで行う。共有の受信箱のトークンで書き込まない
- 決定：GitHubのプロジェクトは、`inbox.auth.owner` にだけ見せ、ownerだけがGitHubの受信箱のトークンで書き込める。ほかの人の書き込みは、issue #152で扱う
- 決定：GitLabのプロジェクトは、ログインした人が自分のトークンで読めるものだけを見せる。読めるかは、人とプロジェクトの組ごとに10分間覚える
- 決定：`admin_groups` のグループの人とownerをadminとし、追加の指示の編集とプロジェクトの追加をadminに限る。`trusted_authors` はログインとは独立に保ち、信頼されない人には返答の前に知らせる
- 決定：エージェントの身元（`agent_identity`）は `trusted_authors` に入れてはならず、入っていれば設定の誤りとする。ADR-056の特例は、`inbox.auth` の無い構成でだけ使う
- 決定：自動のマージ（ADR-048）は、頼んだ人のセッションをメモリーに持ち、その人の身元で行う。受信箱のサービスが再起動したら取り消して知らせる
- 決定：Web表示からの書き込みのたびに、監査ログに `web.action`（操作した人、操作、対象）を残す。認証を設定したとき、Androidの通知の「承認」はアプリを開いてから押す
- 理由：誰が指示したかをフォージに残し、トークンの持ち主でない人が持ち主の名前でエージェントに指示を出せないようにする。エージェントの書き込みはbotの権限、Web表示からの書き込みは人の権限で行う（grilling `add-web-multi-user`）

## ADR-062 公開リポジトリも対象にする（採用、2026-11-04）
- 決定：ADR-023のうち、対象を非公開リポジトリに限るとした部分を改める。公開リポジトリ（GitLabのinternalを含む）のプロジェクトも対象にする
- 決定：公開リポジトリでの守りは、`trusted_authors` の入力だけを指示に採ること、本文、タイトル、コメントの編集者の検査、`include_untrusted` の拒否、実行のsandbox（ADR-057）とする。`include_untrusted` を指定した公開リポジトリのプロジェクトは、今までどおり受け付けない
- 理由：ADR-023の制限は、Claudeが資格情報に届いたPhase 1の隔離を補うためだった。その後、sandboxを常に有効にし、資格情報の置き場所を読めなくし、編集者まで検査するようになった。コードはすでに、公開リポジトリで `include_untrusted` を指定したときだけを拒んでおり、このリポジトリも公開リポジトリとして運用している。ADR-023のとおりに直すと、今の運用が止まる（issue `gh:uskanda/switchboard` #28のQ3）

## ADR-063 Claude Codeのフックを使わない（採用、2026-11-04）
- 決定：Claude Codeのフック（PreToolUse、PermissionRequest、Stop、Notification）は使わない。待ちと完了の書き戻しは、`claude -p` の終了後にエージェントが行う（ADR-011）
- 決定：mainへのpush、マージ、リリースを権限の拒否の規則で止めることを、防壁としない。pushはエージェントだけがissueのブランチに行い、Claudeの環境にはフォージのトークンもpushの資格情報も渡さない。防壁は、sandbox（ADR-057）と、push前の検査（ブランチ、保護パス、秘密）とする
- 決定：AGENTS.mdの不変条件の「mainへのpush・マージ・リリース操作は権限設定で拒否する」を、この決定に合わせて書き換える。書き換えはリポジトリの管理者が行う
- 理由：`claude -p` は人の入力を待って止まらず、プロセスの終了が実行の終わりになる（ADR-019）。宣言は `--json-schema` で受け取れ（V8）、拒否は `permission_denials` に載る（V18）ので、StopフックとPermissionRequestフックは要らない。Notificationフックは `-p` で発火しない（V13）。拒否の規則は `sh -c` ですり抜けられ（V5）、文字列によるPreToolUseの拒否も境界にならない。文書がフックを前提に書かれたままだと、AGENTS.mdを読むClaudeが実装に無い不変条件に従う（issue `gh:uskanda/switchboard` #28のQ6）

## ADR-064 `agent:ready` で計画の段階を省くかをエージェントに決めさせる（採用、2026-11-07）
- 決定：プロジェクトの `plan_first` を、`always`、`auto`、`never` の3つの値にする。キーの名前は変えない。前の版の `true` は `always`、`false` は `never` として読み、キーが無ければ `never` とする。ほかの値は設定の誤りとする。`agent:plan` と `agent:go` の挙動は変えない
- 決定：`auto` のプロジェクトの `agent:ready` は、着手のマーカーに `mode=auto` を記録し、計画の段階として扱う。周期の最初の計画の実行（その周期に質問のコメントも計画のコメントもまだ無い実行）にだけ、宣言の `status` に `implement` を許す。基準は、issueと信頼済みのコメントで設計上の判断がすべて決まっていて、聞く質問が1つも無いことで、迷えば質問するよう指示する
- 決定：判断は、今までどおり読み取りだけの計画の実行で行う。`implement` を宣言したら、計画の本文と「要件が明確なので、質問と承認を省いて実装します」を書いたコメントを、`state=running mode=direct reason=plan-skipped` のマーカーで投稿する。そのうえで、スロットと着手を引き継いで、そのコメントを計画として名指しした実装の実行を始める。issueは待ちにしない
- 決定：省いたあとの返答による再開は、`mode=direct` の周期と同じく実装の実行にする
- 決定：受信箱のAPIは、`plan_first_mode` の文字列を足し、真偽値の `plan_first`（`always` か `auto` で真）も古いクライアントのために残す。Web表示で足すプロジェクトの初期値は `auto` とする
- 理由：要件が明確なissueでも、質問と承認の往復を待つと実装が遅れる。判断までは書き込みの権限を渡さず、計画の実行のあとの検査（`Restore`）を効かせたままにする。省いたときも計画をissueに残せば、何を作るつもりで進めたかを見て直せる。一度質問をしたissueでは、まとめた計画をマスターが確かめる値打ちがあるので、省くのは最初の計画の実行に限る。`mode=auto` で着手したissueを古い版のエージェントが読むと `direct` として扱うので、すべての端末を同じ版にそろえる（issue `gh:uskanda/switchboard` #168のQ1〜Q6）

## ADR-065 Web表示、アプリ、紹介ページ、利用者向けの文書を日本語と英語で用意する（採用、2026-11-08）
- 決定：ADR-025のうち、英語版のREADMEを公開の準備で作るとした部分と、PRODUCT.mdの「文言は日本語とする」を改める。Web表示、Androidのアプリ、紹介ページの文言を、日本語と英語の両方で用意する
- 決定：Web表示の言語は、既定ではブラウザの優先する言語の並びで決める。並びの先頭から見て最初に現れた日本語か英語を使い、どちらも無ければ英語にする。設定の画面の表示の節で「自動・日本語・English」を選べ、選んだ値はブラウザごとに保存し、サーバーには送らない。設定の画面は全員に開き、プロジェクトと追加の指示の節は管理者だけに出す
- 決定：Androidのアプリの画面と通知は、端末の言語に従う。Web表示が計画の質問への返答と再実行の依頼をissueに投稿するときは、表示の言語で書く。Telegramの通知は `comments.language` に従い、アプリのプッシュ通知は言語に依存しない形のまま残す
- 決定：紹介ページは英語をルートに、日本語を `/ja/` に置く。`README.md`、`docs/GUIDE.md`、`docs/SECURITY.md` を英語の版にする。日本語の版は、それぞれ `README.ja.md`、`docs/GUIDE.ja.md`、`docs/SECURITY.ja.md` に置く。この3つは、変えるときに両方の版を同じ変更で直す
- 決定：開発用の文書（SPEC、ARCHITECTURE、DECISIONS、ROADMAP、docs/DESIGN、OpenSpecの成果物）は、ADR-025のとおり日本語で書く
- 理由：CLI、エージェントのコメント、Telegramの通知は英語で出せたが、受信箱で返答する画面と導入の手順が日本語だけで、日本語を読めない利用者には使えなかった。言語を人ごとにブラウザで選べば、複数の人で共有する構成（ADR-061）でもサーバーを変えずに済む（grilling `add-english-support`）

## ADR-066 計画の質問の選択肢を構造で受け、問いの図をWeb表示で描く（採用、2026-11-08）
- 決定：計画の実行の宣言で、質問に選択肢の文（2〜6個）、推奨のラベル、理由の文、任意のMermaidの図を持たせる。選択肢のラベルはswitchboardがA、B、C…と振り、推奨のラベルが選択肢の範囲から外れた宣言は出力の誤りにする。ADR-038の質問の形と、`add-web-plan-answers` の「宣言のスキーマは変えない」を改める
- 決定：図はMermaidの `flowchart`、`stateDiagram-v2`、`sequenceDiagram` に限る。行頭の `classDef`、`style`、`linkStyle`、`click` か、`%%{` を含む図は、switchboardが捨てて監査ログに残す。強調には `:::focus` だけを使わせ、その見た目はWeb表示が決める
- 決定：Web表示は、最新の質問の問いのカードの図の位置にある図だけを、同じ検査をしてから `mermaid@12.2.0`（`securityLevel: 'strict'`）で描く。描いたSVGは、`DOMParser` で切り出した `<svg>` の要素だけをページに入れる。issueを経た文字列をマークアップとして入れるのは、この1か所だけとする
- 決定：ADR-055の「CSP（`default-src 'self'`）は緩めない」を、スタイルについてだけ改める。switchboard-webのCSPに `style-src 'self' 'unsafe-inline'` を足す。スクリプトと、ほかのすべての読み込みは、今までどおり自分のオリジンに限る
- 理由：今のCSPのままでは、Mermaidが描く途中で差し込む `<style>` とstyle属性が止められ、図は黒く塗りつぶされる（Chromiumで確かめた）。CSPを変えずに描く回避策は、Mermaidの内部の処理の順に頼り、図1つに70〜110件の違反の報告が出る。インラインのスタイルを許しても、スクリプトと外への読み込みは止まったままで、データを外へ送ることはできない。残る危険は見た目を偽られることで、スタイルの指示を含む図をGo側とWeb表示の両方で拒むことで小さくする。grillingの記録は `structured-plan-questions` の第1〜第3ラウンドQ1〜Q15（issue `gh:uskanda/switchboard` #190）

## ADR-067 計画の質問を、判断が要る問いと確認だけの問いに分ける（採用、2026-11-08）
- 決定：計画の実行の宣言で、各問いに必須の重み（`decision` か `check`）を持たせる。確認だけの問いとは、推奨の答えがissue、コード、既存の決まりから導けて、ほかの選択肢を選ぶ理由が見当たらない問いである
- 決定：質問のコメントでは、判断が要る問いを先に並べ、確認だけの問いは「推奨どおりで進めるもの」の見出しの下に全文のまま書く。Web表示は、確認だけの問いを、題と選んでいる答えの1行にまとめ、行を開くと全文と選択肢を出す
- 決定：PRODUCT.mdの原則3（返答の前に質問の全文を読めるようにする）に、確認だけの問いの例外を足す。全文は行を開けば読め、行には何が推奨どおりに決まるかを出す
- 決定：計画の実行への指示で、答えがほかの問いの選択肢を変える問いがあれば、そのラウンドではその問いだけを聞かせる。問いがすべて確認だけなら、問いを出さずに計画を出させる。どちらもswitchboardは検査しない
- 理由：返答のあった約200問のうち約9割は推奨どおりに答えていて、所有者はすべての問いを同じ重さで読んでいた。推奨と違う答えになった16問のうち5問は範囲や方向を決めるQ1で、その答えが変わると同じラウンドのほかの問いは前提を失った。確認だけの問いもフォージのコメントには全文で残るので、後から分け方の当否を数え直せる。grillingの記録は `weigh-plan-questions` の第1〜第4ラウンドQ1〜Q14（issue `gh:uskanda/switchboard` #191）

## ADR-068 GitLabの計画の質問に、問いと選択肢の画像を付ける（採用、2026-11-09）
- 決定：GitLabのプロジェクトの計画の実行は、問いに今の画面の画像を1枚、選択肢ごとにその案を選んだあとの画面の画像を1枚付けられる。1つの問いに付ける図は、Mermaidか画像のどちらか1つとし、画面の変化は画像、流れや状態の移り変わりはMermaidを目安に、実行が選ぶ。GitHubのプロジェクトは、今までどおりMermaidだけとする
- 決定：画像は実行が `.switchboard/plan-images/` に置き、宣言の `image` と `option_images` で名前を指す。switchboardは、実行のあとの検査でworktreeを戻す前に、画像を実行のディレクトリへ移す。上げるのはPNG、JPEG、WebPで、1枚5MB、1回の質問で10枚までとし、uploads APIを使う。問いの画像は本文と選択肢の間に、選択肢の画像はその選択肢の行の直後に置く。付けられなかった画像は、問いに1行書き、監査ログに `plan.image_dropped` を残す
- 決定：撮影はサブコマンド `switchboard shot` で行う。ホストのChrome/Chromium（`agent.browser`、無ければPATH）で、`localhost`、`127.0.0.1`、`[::1]` のページだけを開く。ページのほかの読み込みは、存在しないプロキシへ送って止める。撮る前のJSと注記（枠、矢印、文字）を引数で受ける。変更後の見た目は、次の順に試し、足りるところで止めるよう指示する。今の画面への注記、撮る前のDOMとCSSの書き換え、worktreeの一時的な試作の順である
- 決定：計画の実行にも `allow_tools_extra` を渡す。ADR-051の「撮影専用の設定の項目は作らない」を改め、`agent.browser` と、プロジェクトごとの `plan_prototype` を足す。`plan_prototype` を有効にしたプロジェクトだけ、計画の実行に `Edit` と `Write` を許す。書き換えは、今までどおり実行のあとの検査で捨て、そのことはコメントに書かない。「計画の実行は何も変えない」という前提は、このプロジェクトでは「変えても必ず捨てる」に改める
- 決定：受信箱の `/v1/issue-image` が返すのは、issueのGitLabのプロジェクトのアップロード（`/uploads/<secret>/<name>`）だけである。受信箱のトークンでGitLabのAPIから読み、画像の形式を検査して返す。Web表示は、最新の質問の問いのカードで、その画像を `switchboard-web` を通して描く。CSPは変えない
- 理由：利用者が図で知りたいのは、多くの場合「画面が実際にどう変わるか」であり、流れ図では伝わらない。GitLabはアップロードの記法を本文の好きな位置に置けるが、GitHubには公開のAPIが無く、`gh --attach` は画像を末尾に付ける。sandboxの中の1回のコマンドでサーバーを起動してChromiumで撮れることは、V58で確かめた。撮影を決まったサブコマンドにすれば、LLMにsandboxの外でスクリプトを動かさせずに済む。開けるページと読み込みの先も、switchboardが絞れる。試作は手間がかかり、worktreeを書き換えるので、利用者が選んだプロジェクトだけに許す。grillingの記録は `add-plan-question-images` の第1〜第4ラウンドQ1〜Q17
