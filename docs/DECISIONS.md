# 設計判断の記録（ADR）

形式：番号 / 状態（採用・保留・却下）/ 決定 / 理由。覆す場合は新しい番号で追加し、旧 ADR に「置換」を記す。

## ADR-001 自作する（採用）
- 決定：既存 OSS を採用せず、自作する
- 理由：要件（issue 駆動・複数端末・GitHub/GitLab 両対応・ローカル文脈）をそのまま満たす広く使われた製品がない。類似 OSS は小規模な個人プロジェクトで、保守継続性と監査コストに懸念がある。信頼境界を自分で引けることを重視する。既存 OSS は設計の参考に留める

## ADR-002 稼働中セッションへの直接注入はしない（採用）
- 決定：Channels 等による稼働中対話セッションへのメッセージ注入は採用しない
- 理由：外部からの注入口は実質的にリモート実行の入口になり、リスクが大きい。issue 駆動で同等の目的を達成できる

## ADR-003 issue を制御面とする（採用）
- 決定：作業単位・状態・応答経路を issue（ラベル・コメント）に統一する
- 理由：認証・認可・監査をフォージに委ねられる。フォージのモバイルアプリが応答 UI になる。トレンド（OpenAI Symphony 等）とも一致

## ADR-004 中継は ID 通知のみ（採用）
- 決定：中継は issue の識別子とイベント種別だけを流し、本文はローカルが再取得する
- 理由：中継が侵害されても内容を注入できない

## ADR-005 状態は issue とリポジトリに置き、resume は最適化扱い（採用）
- 決定：毎回まっさらな文脈で起動できる設計を基本とする。`--resume` は同一端末・新しいセッションに限り使い、失敗時は通常起動にフォールバック
- 理由：対話セッションとの競合リスクを避け、端末をまたいでも同じ状態から再開できる（Ralph 型ループの考え方）

## ADR-006 横断受信箱はローカルで集約（採用）
- 決定：受信箱は中継ではなくローカルの CLI が両フォージを直接検索して作る
- 理由：中継にタイトル等を持たせると ADR-004 が崩れる。フォージ単体のラベル検索で必要な情報は取れる

## ADR-007 中継の公開方法（保留）
- 候補：Tailscale Funnel / Cloudflare Tunnel / 小さなクラウド VM
- 論点：webhook 受信口だけ公開できること、エージェントへの配信は Tailnet 内に閉じられること

## ADR-008 受信箱用トークンの分離（保留）
- 論点：受信箱（読み取り＋コメント）とエージェント（PR 作成まで）でトークンを分けるか

## ADR-009 状態ラベル（採用）
- 決定：`agent:ready` / `agent:running` / `agent:waiting` / `agent:done` の 4 種。`switchboard labels sync` で全リポジトリに統一作成
- 理由：状態を少数に保ち、フォージの検索だけで受信箱が作れるようにする

## ADR-010 技術スタック（保留）
- 候補：Go（単一バイナリで配布しやすい、常駐向き）/ Python（試作が速い）/ TypeScript（Claude Code・gh 周辺との親和性）
- 論点：複数端末への配布のしやすさ、常駐プロセスの安定性、フォージ SDK の充実度
